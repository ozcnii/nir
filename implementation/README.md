# Реализация ВКР

Здесь находятся приложение Django, его окружение, тесты и инструменты запуска.
Принятый проект описан в [сводке](../bachelor-thesis/CONSOLIDATED-DESIGN-9.md).
Пояснительная записка находится в [thesis](../thesis/README.md).

Из этой папки, через uv 0.13.9:

```sh
uv sync --locked --dev
uv run --no-sync python manage.py check --settings=config.settings_base
bash scripts/check-style.sh --types
```

Для установки Git hook из корня репозитория:

```sh
uv --project implementation run --no-sync pre-commit install --hook-type pre-commit
```

Для задач с локальным стеком используется host runner. Из папки реализации:

```sh
uv run --locked python -m host_runner -- <команда задачи>
uv run --locked python -m host_runner --db-only -- <команда задачи>
```

Первый режим арендует app и PostgreSQL, второй только PostgreSQL. Команда
остаётся на переднем плане до окончания использования стека.

## Контейнеры

Из этой папки `docker compose build app` собирает локальный образ без запуска
сервисов. Для db используется штатный образ PostgreSQL. Docker Desktop 4.94.0
с Engine 29.8.2 и Compose 5.5.1 подходит для локальной проверки.

Для старта PostgreSQL оператор передаёт `POSTGRES_PASSWORD`. Для приложения
используются `DB_NAME` (по умолчанию `catalog`), `DB_APP_PASSWORD` и
`DJANGO_SECRET_KEY`. Секреты передаются из локального окружения или
игнорируемого файла `.env` и отсутствуют в образе.

### Первый запуск

Передайте `DB_APP_PASSWORD` и `DB_MIGRATOR_PASSWORD` через окружение
оператора. Если имя БД отличается от `catalog`, передайте там же `DB_NAME`.
Используйте выделенный Compose-проект под управлением host runner. Из папки
реализации:

```sh
uv run --locked python -m host_runner --db-only -- bash -ec '
    docker compose build app
    bash scripts/prepare-db.sh
    docker compose run --rm --no-deps app python manage.py createsuperuser
    docker compose run --rm --no-deps -T app python -m config.startup --check-only
'
```

Одноразовый процесс bootstrap проверяет подключение, существующие роли, владельцев
и схему до изменений. Он создаёт недостающие роли и выделенную БД. Затем скрипт
запускает штатный `migrate` под `migrator` и восстанавливает явную матрицу прав.
`createsuperuser` — отдельная команда оператора под ролью `app`. Введите пароль
в интерактивном запросе Django. При повторной подготовке используйте
`prepare-db.sh` и `config.startup --check-only`, чтобы сохранить созданного
администратора и данные.

После завершения DB-only аренды можно запустить app и базу обычным host runner.
При каждом запуске app проверяет применённые миграции и права роли `app`.
При ошибке проверка завершает процесс с причиной. После успешной проверки
стартует Django, и host runner публикует адрес после успешного healthcheck.
Обычный перезапуск не применяет миграции, не загружает справочники и не запускает
сбор. Для отдельной проверки первого запуска на новом проверочном томе из worktree
используйте `bash tests/startup/check-postgres.sh` с временными паролями.

### Восстановление стандартных записей

Начальная миграция заполняет справочники один раз. Восстановить выбранные
отсутствующие записи можно под ролью `migrator` из выделенного Compose-проекта.
Каждый параметр можно указать несколько раз.

```sh
uv run --locked python -m host_runner --db-only -- docker compose run --rm --no-deps -T \
    -e DB_MIGRATOR_PASSWORD -e DB_APP_PASSWORD= -e DJANGO_SECRET_KEY= app \
    python manage.py restore_reference_data --settings=config.settings_migrator \
    --source cian --property-type 1 --region 68
```

Команда сохраняет существующие значения и отменяет весь запрос, если подпись
восстанавливаемой записи уже занята другим ID. Конфликт можно устранить штатным
переименованием, затем повторить команду.

### Проверка прав PostgreSQL

Негативные SQL-проверки F25 запускаются только в отдельном worktree с новым
проверочным томом. Используйте отдельные временные пароли:

```sh
bash tests/db_roles/check-postgres.sh
```

Проверка резервирует новый том и запускает его через host runner. Существующий
том или контейнер этого worktree блокирует запуск до SQL-проверок.

## Управление сбором

Контейнер запускает `config.launcher` под Docker init. Лаунчер выполняет проверку
подготовки БД из `config.startup` и управляет дочерними web-процессом и
`collection.runner`. Внутренний интерфейс в `/run/app/control.sock` принимает
один JSON-пакет с завершающим переводом строки, до 4 КиБ, в пределах 250 мс.
Через `config.control.request` можно вызвать `{"action":"status"}`, старт
`{"action":"start","selection":{...}}` или остановку
`{"action":"stop","run_id":"..."}`. Снимок выбора содержит непустые списки
`sources`, `regions`, `categories` и `deal_types`. Успешный запрос старта
означает `starting`; состояние `running` появляется после подтверждения дочернего
процесса, взятой сессионной блокировки PostgreSQL и проверки выбора. Пока
адаптеры источников не реализованы, рабочий runner отклоняет все направления.

`catalog.services.delete_references` удерживает транзакционную блокировку того
же ключа, запрашивает свежее состояние и удаляет записи только после
подтверждённой очистки. Потеря сессии сбора запрещает дальнейшие операции
сбора и удаление справочников до подтверждения безопасного состояния.

Интеграционная проверка на отдельной PostgreSQL запускается через
`bash tests/launcher/check-postgres.sh`. Она проверяет реальный Unix-сокет,
дочерний процесс, блокировки и потерю DB-сессии, используя управляемый обход
без обращения к источникам.

Раннер открывает один Chromium в sandbox и один временный контекст. Выдача и
карточки используют две страницы этого контекста. `running` публикуется после
их открытия. Навигация и запись проверяют запрос остановки и сессию PostgreSQL
перед следующим шагом. Неудачную навигацию можно повторить один раз в рамках
принятых сетевых ошибок, пока остановка не запрошена.

Подтверждение окончания требует закрытия контекста, браузера, транспорта
Playwright и DB-сессии. Linux позволяет раннеру дождаться своих дочерних
процессов, включая осиротевших потомков Chromium. Временный профиль удаляется
после проверки детей. Если очистку подтвердить нельзя, лаунчер сохраняет
`unknown`. Принудительная остановка через pidfd адресуется раннеру.

`bash tests/browser/check-postgres.sh` проверяет штатный sandbox, локальные
страницы, остановку, транзакции, ошибки дочерних процессов и TERM контейнера
на отдельной PostgreSQL.

Служебные файлы запуска хранятся в `/var/lib/app/runs/<run_id>/`. Единственный
поток записи сохраняет `events.jsonl` и атомарно обновляет `state.json`. Лаунчер
начинает запуск после подтверждения начального снимка, а показывает `finished`
после завершения и подтверждения финального снимка. До этого stop и status
обслуживаются независимо от записи. Ошибка диска, переполнение очереди или
отсутствие подтверждения за 5 секунд оставляют состояние `unknown`.
Прогресс отражает уже подтверждённые транзакции PostgreSQL. Журнал событий
может отставать от базы при отказе хранения.

`bash tests/launcher/check-postgres.sh` проверяет в том числе запись журнала,
отказы до и после замены файла, позднее подтверждение и заполнение очереди.

При новом управляемом запуске host runner проверяет через Docker, что
контейнеры, использующие тот же том `app_data`, остановлены. Лаунчер держит
`.owner.lock` до выхода процесса. После проверки БД он восстанавливает только
читаемые прерванные снимки как `finished/error/app_restarted`. Их счётчики
помечаются неполными, прежние события сохраняются, сбор запускается вручную.

Writer хранит текущий сегмент JSONL до 5 МиБ и два предыдущих сегмента.
Сохраняются десять последних подтверждённых завершений и защищённые истории.
`config.journal_history.read_run` возвращает различимые состояния пустого,
частичного, повреждённого, недоступного и изменившегося журнала.

Проверки T12 из `implementation/` в отдельном worktree

- `PYTHONPATH=. uv run --no-sync python tests/journal/check_history.py`
- `bash tests/recovery/check-postgres.sh`

Внутренний `state.ack` сопоставляет финальный снимок с операцией, которая
успела успешно синхронизировать `state.json` и родительский каталог в отведённый
срок. Он не показывает, получил ли клиент ответ, и не свидетельствует отдельно
о завершении записи самого подтверждения. При разрыве между записью снимка и
подтверждением история показывается как неполная. После подтверждённого
перезапуска такой снимок восстанавливается как прерванный. Writer просматривает
старые журналы по одному, когда очередь записей пуста.
