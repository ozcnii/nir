# Как устроен сбор и что мы починили

Документ отвечает на два вопроса: каким был отказ и чем он вылечен, и как сбор
работает после правок. Относится к [задаче #36](https://github.com/ozcnii/nir/issues/36).

## 1. Отказы доступа: что было не так

Первая версия сборщика считала любой не-2xx ответ приговором площадки. Отсюда
брались ложные «баны» и потерянные прогоны.

| Симптом | Что происходило на самом деле | Решение |
| --- | --- | --- |
| HTTP 439 на Авито | Промежуточная антибот-проверка: контент появляется примерно через 6 секунд, а код падал за десятки миллисекунд | Статус 439/401/403 — состояние, а не приговор: окно наблюдения до 25 с, одна навигация |
| HTTP 429 | Троттлинг | Пауза 2 с, ровно один повтор |
| 5xx и обрывы | Временный сбой | Повтор как раньше |
| Пустая выдача вместо данных | Chrome не пускал CDP на профиль по умолчанию, а копия профиля не переносит cookie (DPAPI) | Отдельный каталог профиля, прогретый оператором один раз; канал `chrome`, headful |
| Авито «бан» | Кракозябры cp866 в консоли Windows были прочитаны как текст ошибки | Вывод только по скриншоту или файлу, не по консольному тексту |

Политика зафиксирована в `app/collection/browser.py` (`document_recovery`,
`reason_recovery`) и описана в
[`COLLECTION-4.3-PROPOSAL.md`](../bachelor-thesis/COLLECTION-4.3-PROPOSAL.md).

## 2. Капча

Челлендж — это не ошибка парсинга, поэтому он не наследует `RejectedCard` и не
путается с отказами карточек.

- Коллекторы (Циан, поиск Циан, комнаты, Домклик, Авито) поднимают
  `ChallengePending` со своим маркером.
- `app/collection/captcha.py` готовит челлендж (снимок экрана, центр элемента) и
  публикует запрос в каталог брокера.
- Оператор отвечает; решение применяется шагами мыши по центру челленджа.
- После ответа **чтение продолжается в той же итерации цикла** — без новой
  навигации и повторного клика.

Живой путь брокера пока не пройден: это пункт **S01** в
[`ACCEPTANCE-7.1-RESULTS.md`](../bachelor-thesis/ACCEPTANCE-7.1-RESULTS.md).

## 3. Домклик: смена публичного API

Площадка убрала `24.domclick.ru/api/offers/ad/v1` и переразметила выдачу.
Разбор по факту, а не по догадке:

- выдача рендерится сервером, объявления берутся из ссылок `/card/`;
- фильтр `offer_type` переименован: `new_flat` → `layout`;
- адрес новостройки не содержит цепочки `parents`, регион лежит в
  `locality.name`;
- `__SSR_STATE__` на выдаче **не содержит** ни фильтров, ни объявлений —
  попытка читать их оттуда была тупиковой и убрана.

## 4. Темп и лимиты

Обход больше не выгребает выдачу одним залпом. Параметры задаются окружением:

| Переменная | Смысл |
| --- | --- |
| `COLLECTION_MAX_PAGES` | страниц выдачи на источник; пусто — без лимита |
| `COLLECTION_MAX_CARDS` | карточек на источник; пусто — без лимита |
| `COLLECTION_PAGE_PAUSE` | пауза между страницами, `5-12` или `5` |
| `COLLECTION_CARD_PAUSE` | пауза перед карточкой, `3-8` или `3` |

По умолчанию лимитов нет: приёмка обязана обходить выдачу полностью. Живой
прогон включает человеческий темп сам. Достижение лимита завершает источник
штатно, с причиной `stopped_by_limit`.

## 5. Как проходит один запуск

Сбор — это команда, а не служба. Планировщика в приложении нет.

```
python -m app.manage collect --source <cian|avito|domclick> --region 68 \
    --property-type apartment --deal sale
```

Порядок:

1. `collect` строит маршруты источника (`routes_for`) для региона и типа объекта.
2. Открывается браузер: постоянный профиль, `channel=chrome`, headful.
3. Обход выдачи: страница → ссылки карточек → пауза по настройкам.
4. Каждая карточка читается своим адаптером, ответы площадки проходят политику
   отказов, челлендж уходит брокеру.
5. Нормализация в доменные поля и запись в PostgreSQL: объявление, объект,
   цена. Повторный запуск даёт `unchanged`, а не дубликат.
6. Итог печатается JSON-ом: `outcome`, `pages`, `unique_cards`, `results`,
   `issues`, `issues_by_stage`, `skipped_cards`, `scope`, `source`.

## 6. Что автоматизировано, а что нет

Автоматизировано: разбор ответов и решение о повторе или остановке, ожидание
поздней готовности, пагинация, обнаружение капчи и её передача брокеру,
нормализация, запись без дублей, отчёт о причинах отказа по этапам.

Не автоматизировано:

- **запуск по расписанию** — планировщика нет, сбор стартует только по команде;
- **прогрев профиля** — выполняется оператором один раз вручную;
- **решение капчи** — требует человека; автоматического обхода нет и не
  планируется.

Чтобы сбор шёл регулярно, нужен внешний планировщик (cron, systemd timer,
Celery beat) либо отдельная служба. Сейчас такого механизма в репозитории нет.
