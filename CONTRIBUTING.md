# Задачи, проверка и интеграция

Источник задач — GitHub Issues, источник оперативного статуса — доска Projects.
Принятые решения остаются в `bachelor-thesis/`, а не копируются в новые backlog-файлы.
Ссылки на доску и восемь этапов: [указатель](bachelor-thesis/IMPLEMENTATION-TRACKER.md).

## Статусы

| Статус | Условие |
|---|---|
| Backlog | Задача создана, ещё не выдана; зависимости/разрешение могут отсутствовать. |
| Ready | Критерии/границы/проверки понятны, зависимости приняты, работа разрешена пользователем. |
| In progress | Координатор назначил одного исполнителя с session ID и веткой. |
| Verification | Исполнитель закончил изменение и проверяет критерии на конкретном SHA. |
| Review | Доказательства приложены; другой агент проверяет соответствие, diff и поведение. |
| Done | Все обязательные критерии выполнены, findings устранены, актуальные проверки успешны и результат разрешённо интегрирован. |
| Blocked | Есть конкретный блокер/внешняя зависимость; указаны причина и условие продолжения. |

Все задачи реализации изначально Backlog: текущая настройка не разрешает писать код.
Родительский этап закрывается только после приёмки всех требуемых подзадач;
задача, снятая с плана, требует явного решения пользователя, а не Done по умолчанию.

## Назначение и зависимости

- Координатор — один агент текущей рабочей сессии, выбранный владельцем. Только он
  распределяет задачи и меняет назначение. Комментарий назначения: `agent/session`,
  ветка/worktree, границы, ссылка на разрешение выполнения и исходный SHA.
- Статус/assignee не обеспечивают атомарный захват. Самостоятельное соревнование
  агентов за Ready запрещено. При смене координатора сначала читается передача
  прежнего и проверяется отсутствие активного владельца, без выдачи дубля.
- Используются native blocked-by и sub-issues GitHub. Текст Dependencies в карточке
  объясняет их; при изменении связи координатор обновляет оба представления.
- Не использовать зависимость на родительский этап, если задача сама входит в этот
  этап или должна выполняться параллельно. Документные/формальные задачи могут
  начинаться раньше исследований, но финальные результаты требуют измерений.
- Если обнаружен цикл/неверная зависимость/новый продуктовый выбор, описать это в
  issue и поставить Blocked, не менять принятый проект молча.

## Что должно быть в задаче

1. Наблюдаемый результат и границы, включая исключённую соседнюю работу.
2. Принятые спецификации и зависимости с номерами issues.
3. Нумерованные критерии: начальные условия → действие → ожидаемый результат.
4. Проверки по риску: что/где/на каких данных проверять; F01–F25 при применимости.
5. Доказательства при завершении и явная граница разрешения выполнения.

Issue Forms помогают заполнению через интерфейс, но API/CLI не проверяют смысл
текста автоматически. Координатор проверяет готовность карточки до Ready.

Для агента через CLI используй `gh issue create --repo ozcnii/nir --body-file <файл>`
с явно заданными title/labels: `task` и `stage:N` (для ошибки — `bug`). Тело содержит
те же разделы результата, основания, зависимостей, AC и проверок. Не рассчитывай
на `--template task.yml` или обнаружение YAML-форм через `Repository.issueTemplates`:
при проверке этого репозитория API вернул пустой список для опубликованных форм.
Метки, native parent/blocked-by и добавление в Project задаются явно и проверяются
после создания. Файл тела — временный, не второй backlog. Новый task остаётся
Backlog до готовности/разрешения/назначения по этому процессу.

## Передача на ревью

Исполнитель оставляет один итоговый комментарий следующей структуры:

```text
Исполнитель / session:
Ветка / PR / проверяемый commit SHA:
Критерий AC1: PASS | FAIL | NOT RUN | N/A — доказательство/причина.
Критерий AC2: ...
Проверки: команда или ручные шаги; среда/данные; ожидаемое/фактическое.
CI: ссылка и SHA; PASS | FAIL | NOT CONFIGURED | NOT REQUIRED.
Непроверенное и остаточные риски:
Ресурсы/аренды: что уже работало, что запущено мной, что освобождено.
```

Для ручного сценария нужны конкретные шаги/результат, а не только «проверено».
Логи/снимки безопасные и относятся к тому же SHA; секреты/аудио/сырые страницы в
публичную issue не загружаются. Для каждого обязательного AC требуется PASS;
N/A допустимо только для действительно неприменимой проверки с обоснованием,
а не для отмены самого критерия приёмки. Заблокированный обязательный сценарий
оставляет задачу незавершённой.

Ревьюер — другая сессия/агент, не автор изменения. Он читает требования, baseline,
актуальный diff и применимые вызывающие; проверяет Standards и Spec отдельно,
воспроизводит ключевой риск либо явно отмечает, что не запускалось. Findings
содержат сценарий/влияние/место. После исправлений указывается новый SHA и что
перепроверено. Агенты одного GitHub-аккаунта фиксируют независимость в комментарии:
это не формальное GitHub approval от другого пользователя.

## PR, CI и Done

- Одна исполнимая задача — небольшой PR с её номером, без соседних изменений.
  Общие зависимости и отдельные worktree координируются до начала правок.
- PR не означает разрешение merge. Интегрирует координатор в пределах поручения
  владельца; исполнитель/ревьюер не расширяют права сами.
- До merge координатор сверяет все AC, ревью актуального SHA и применимые проверки
  реально введённого CI. После приёмки полного контура T13 обязательным результатом
  требуется успешный `quality` по 8.4 на актуальном кандидате и актуальная база
  `main`. После изменений координатор повторно проверяет затронутые выводы и
  сверяет проверку GitHub Actions с новым SHA.
- Bootstrap до T13 не получает вымышленный full-CI pass. **T01 (#9)** принимается
  только по своим AC: lock/инструменты/hook и начальные реализованные проверки,
  включая их положительные/отрицательные и docs-only случаи. Если начальный workflow
  уже появился, это не превращает его в полный контур 8.4. Будущие Django/миграционные/
  DB/browser-сценарии не требуются для Done T01: T02 зависит от T01, поэтому такой
  gate создавал бы цикл. До T13 для каждой задачи проверяются её AC и существующая
  область CI; отсутствующая область явно указана как NOT CONFIGURED.
- **T13 (#21)** вводит и проверяет полный нынешний контур 8.4, включая классификацию,
  docs-only, отрицательный тест, миграционные и ошибочные/skipped/cancelled состояния.
  Все существующие собственные тесты обязательны, ещё не реализованные функции
  будущих этапов не выдаются за проверенные. T13 не закрывается только по локальному
  проходу при неиспытанном CI. **T36 (#46)** включает защиту `main` после приёмки
  T13. GitHub требует PR и успешный `quality` от GitHub Actions на актуальной базе,
  блокирует force-push и удаление ветки. Координатор сверяет независимое ревью
  по сессии и SHA в комментариях к issue.
- Документные задачи не запускают БД/браузер без конкретного риска. Документы-only
  в рабочем CI дают честный успешный classify/quality без имитации app-checks.
- Сначала проверенная интеграция, затем issue close как completed и Done. Не добавляй
  `Closes #...` до завершённой приёмки: merge не должен скрыть недоделанную задачу.
  Встроенный auto-Done Projects не является проверкой; случайное закрытие/Done
  координатор исправляет, открывая issue и возвращая нужный статус.
- Число «9/10» не является универсальной заменой приёмки. Для текущей настройки
  пользователь отдельно потребовал >=9/10 и максимум три итерации независимого
  ревью; это ограничение этой работы, не бесконечный цикл всех будущих задач.

## Независимое ревью качества этапа

Координатор фиксирует SHA `main` перед первым слиянием этапа. Перед закрытием
координатор получает отдельное ревью интегрированного результата от человека
или агента, который его не реализовывал. Для проверки указывает SHA
интегрированного `main` и объединённые PR этапа. При чередовании этапов список PR
определяет область, а интегрированная версия нужна для проверки связей с
вызывающими и соседними модулями. Проверка дополняет приёмку задач и CI.

- Проверь владельца изменившихся правил и совместную работу интерфейсов.
  Предложи удалить лишнее и заменить дубли подходящим существующим решением.
  Проверь читаемость, границы модулей и обоснованность зависимостей по
  [правилам качества](CODING.md#читаемость-и-границы-модулей).
- Сверь ключевые риски между задачами с поведенческими доказательствами.
  Используй подходящие уже выполненные проверки. Запускай новые только для
  конкретного риска, который они ещё не покрывают.
- Зафиксируй в родительской issue диапазон SHA, ревьюера, оценку качества из 10,
  подтверждённые проблемы с местом и последствиями, доказательства и итог.
  Закрывай этап после публикации ревью и устранения существенных замечаний.
  После исправления перепроверь изменённое и связанные риски в пределах
  согласованных итераций.

## Прерывание работы

Перед паузой оставить прогресс/ветку/SHA, проверенное/непроверенное, блокер и
ресурсы в issue. На повторном входе читать GitHub и фактический checkout, не
восстанавливать статус по памяти чата. Никаких автоматических reset/clean/force-push.
Сервисы и аренды освобождаются по принятому lifecycle; данные сохраняются.
