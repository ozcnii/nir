# Правила реализации

Это исполнимые для агента правила принятого проекта, а не готовые конфигурации.
Источники: [8.2](bachelor-thesis/QUALITY-8.2-PROPOSAL.md),
[8.3](bachelor-thesis/QUALITY-8.3-PROPOSAL.md),
[8.4](bachelor-thesis/QUALITY-8.4-PROPOSAL.md),
[8.5](bachelor-thesis/QUALITY-8.5-PROPOSAL.md).
При расхождении сокращённого изложения проверяй принятый подробный контракт.

Все пути исходников и Python-команды относятся к [implementation/](implementation/README.md).

## Ответственность

- `collection.collectors`: чтение встроенных данных площадок через Playwright,
  извлечение исходных значений и фактических ключей. Никакой предметной записи ORM.
- `collection.normalization`: перевод представления источника в принятый P3,
  сохранение различий missing/NULL/ошибка, Decimal/единицы/адреса по 4.2.
- `collection.runner`: обход, повторы, остановка, технический singleton-lock,
  получение параметров через публичные queries простыми данными и вызов services.
- `catalog.services`: доменные инварианты, атомарный приём P3, порядок времени/ключа,
  допустимые обновления и история цены. Сеть площадки до транзакции.
- `catalog.queries`: ORM-чтение и выборка кандидатов, общие выборки HTML/JSON.
- `catalog.matching`: чистое сопоставление простых данных без ORM, сети и записи.
- Модели: поля/ограничения; views/forms: HTTP, ввод, права/CSRF и представление.
  Не копировать бизнес-правило между forms, views и services.
- Инфраструктурный launcher владеет процессами/служебной записью; семантику
  результатов формирует collection. Он не выбирает property_id и не меняет цены.

## Стиль и инструменты

- Принятые uv/точные версии/lock. Без молчаливого обновления или второго менеджера.
- Python: Ruff, 88 символов, 4 пробела, двойные кавычки/LF; набор правил и исключения
  точно по 8.2, без глобального ослабления. HTML: профиль Django djLint из 8.2.
- mypy strict для всего собственного Python, включая тесты/миграции; stubs/plugin
  по принятому профилю. Не скрывать ошибки глобальными Any/ignore/missing-imports.
- Имена отражают предметный смысл, функции владеют одним правилом. Сначала искать
  существующий аналог. Абстракция/общий helper нужны по реальной общей ответственности.
- Штатные Django ORM/auth/admin/forms и стандартная библиотека там, где подходят.
  Внешний текст экранируется, секреты не в Git/логах/fixtures. JSON-ошибки по 5.5.
- Не хранить цену вторым текущим полем в ads; не добавлять group_id/ручной merge,
  фотофайлы/хеши, run/log-таблицы или отдельный source Домклик24.

## Тесты и доказательства

- Сначала сценарий: начальные условия → действие → ожидаемый результат по контракту.
  AAA: Arrange / Act / Assert; один понятный сценарий может иметь несколько asserts.
- Применимые позитивные/негативные/граничные случаи, включая повтор, время, NULL,
  конфликт и отсутствие лишней истории. Не тестировать синтаксическую копию кода.
- Чистые правила — без БД/сети; ORM/ограничения/транзакции — на PostgreSQL;
  пользовательский проход — HTTP/Playwright. Не подменять интеграцию набором mocks.
- F25 проверяется реальной ролью app, а не привилегированной test-admin. Для гонок
  нужны самостоятельные соединения и видимые committed-данные по принятому протоколу.
- Browser-тесты изолируют контекст и данные, используют роли/подписи/ожидания
  состояния без случайных sleep. Живые площадки отдельно от детерминированного CI.
- Выполнять проверки по риску, не вводить квоту покрытия или полный прогон для
  каждого документа. Зафиксировать SHA, команду/шаги, данные и фактический результат.
- Test failure, NOT RUN, недоступность и N/A различаются. Обязательный AC без
  доказательства не выполнен. Независимое ревью не заменяет поведенческую проверку.
