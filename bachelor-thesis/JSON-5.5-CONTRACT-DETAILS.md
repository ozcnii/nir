# 5.5. Контекст поиска, типы JSON и валидация — принято

17 ноября 2026. По прямому запросу владельца уточняется JSON-ROUTES-LAYOUTS-PROPOSAL.md. Это спецификация и примеры формата, не прикладной код и не реальные ответы работающего приложения. Текущая редакция5.5 прямо принята владельцем17ноября2026. БД и принятые 5.1–5.4 не меняются.

## 1. Контекст поиска в URL

Ссылка из каталога на карточку всегда содержит from=catalog, текущие нормализованные фильтры и page исходной выдачи — даже если пользователь не менял исходные настройки. Условные примеры внутренних адресов:

- Каталог по умолчанию /catalog/ → /properties/123/?from=catalog&deal_type=sale&category=all&page=1
- Поиск квартир на второй странице → /properties/123/?from=catalog&deal_type=month_rent&category=flat&region_id=1&page=2
- Прямой вход → /properties/123/ без from=catalog.

123 и 1 в этих примерах — условные внутренние ID, не подтверждённые записи нашей ещё не созданной БД. from — только маркер контекста интерфейса, не поле БД и не факт, что пользователь действительно нажал ссылку. Переданный набор фильтров повторно проверяется общим валидатором и queries; совпадения не определяются одним маркером.

С from=catalog: кнопка «Назад к результатам» строит только внутреннюю ссылку /catalog/ с теми же фильтрами и исходной page; соответствие ads отмечается повторным применением условий каталога, включая active. Полная карточка всё равно содержит все ads. Без from: «В каталог», пометок соответствия нет. Не использовать Referer, браузерную историю, произвольный return_url, cookies или сессию как обязательный способ хранения поиска.

На HTML-карточке фильтры/page без from=catalog либо иное значение from — HTTP400 с объяснением ошибочного контекста. Просто отсутствие любого контекста — нормальный прямой вход. Отсутствующие внутри корректного контекста фильтры получают те же значения по умолчанию, что и каталог. page при чтении контекста карточки проверяется как целое >=1, но не сравнивается с текущим числом страниц: выдача могла измениться, это не повод скрыть сам объект. При возврате каталог заново проверяет существование страницы; если она исчезла, показывает принятую ошибку страницы и ссылку на первую с теми же фильтрами.

Кнопка JSON каталога переносит фильтры/page на /api/properties/. Кнопка JSON карточки ведёт на /api/properties/<id>/ без контекста: это полное чтение объекта, а не отфильтрованный список. API карточки не принимает from или фильтры. Для сохранения исходной выдачи в обычных переходах дополнительные поля БД не нужны.

## 2. Query: единый точный разбор HTML и API

Все query-значения приходят строками. Одинаковые правила применяются к каталогу HTML/API и к фильтрам контекста HTML-карточки.

| Параметр | Допустимые значения | Нет значения |
|---|---|---|
| deal_type | sale, month_rent, day_rent | Отсутствует → sale; пустая строка — invalid_choice |
| category | all, flat, resale, new_build, room, house | Отсутствует или пусто → all |
| region_id | Целое положительное <=9223372036854775807 и существующий regions.id | Отсутствует или пусто → все регионы |
| price_min, price_max | Точный decimal >=0, максимум99999999999999.99, до2дробных знаков | Отсутствует или пусто → соответствующая граница не задана |
| area_min, area_max | Точный decimal >=0, максимум9999999999.99, до2дробных знаков | То же; фильтр0 допустим, известная площадь самого объекта по БД >0 |
| rooms_min, rooms_max | Целое0..32767;0 — явно известная студия | Граница не задана |
| floor_min, floor_max | Целое-32768..32767, включая0 | Граница не задана |
| page | Целое >=1 | Отсутствует →1; пусто — invalid_integer |
| from, только HTML-карточка | Ровно catalog | Нет from и остальных параметров → прямой вход |

Числовые границы соответствуют принятым numeric(16,2), numeric(12,2), smallint и bigint, а не придуманным ограничениям числа этажей реальных домов. Ограничение существования номера страницы применяется в списке: page>числа страниц →400/out_of_range. При count0 допустима только page1.

После удаления пробелов по краям целое содержит только десятичные цифры; минус допустим только у floor. Дробная часть, знак плюс, экспонента не допустимы для целых: page=1.5 и rooms_min=1.5 → invalid_integer, а не округление. В decimal обязательна целая часть из одной или более десятичных цифр; после необязательной точки или запятой — одна либо две цифры. Знаки плюс/минус, разделители тысяч, экспонента, NaN/Infinity не допускаются. Поэтому +1, .5, ,5, 1. и 1, → invalid_decimal; 0.5, 0,5, 1 и 1.00 допустимы. Более2дробных знаков → invalid_decimal без округления. В канонических ссылках decimal использует точку.

Любая заданная пара min/max должна удовлетворять min<=max. При обратном диапазоне оба соответствующих поля получают inverted_range; если одно значение не разобрано, лишняя ошибка диапазона не добавляется. Неизвестные значения самих properties/цен не проходят заданный числовой фильтр, как принято ранее.

Повтор одного query-ключа → repeated_parameter, неизвестный ключ → unknown_parameter. Это относится и к переданному page_size: размер20фиксирован, изменяемого параметра нет. Для ошибочного региона: нецелый → invalid_integer, выход за bigint/положительность → out_of_range, отсутствующий в справочнике → not_found. Строковые перечисления с неизвестным значением → invalid_choice. Несколько независимых ошибок собираются в один ответ; обе версии HTML/API используют один набор результатов валидации, HTML показывает те же сообщения у полей.

## 3. Точные выходные типы JSON

Все перечисленные ключи обязательны в соответствующем типе; неизвестный scalar передаётся null, а не исчезает. Исключение — description/price_history отсутствуют в краткой публикации списка, поскольку присутствуют только в детальной версии. Новых колонок для этих представлений нет.

| Тип | Точная структура |
|---|---|
| Directory | Объект с id:integer>0, name:string непустая; id в пределах bigint |
| Price | Объект с price_rub:decimal-строка numeric(16,2)>=0, price_kind:строка listed/from, observed_at:строка даты UTC |
| PropertyBase | id:integer>0; region:Directory; property_type:Directory; address:string или null; latitude/longitude:decimal-строки7знаков или обе null; area_m2:decimal-строка2знака или null; rooms:integer0..32767 или null; floor:integer-32768..32767 или null; floors_total:integer1..32767 или null; land_area_m2:decimal-строка2знака или null |
| AdSummary | id:integer>0; source_code:строка cian/domclick/avito; external_id:непустая строка; url:непустая HTTP(S)URLстрока; deal_type:sale/month_rent/day_rent; market_segment:resale/new_build/null; is_active:boolean; observed_at:дата UTC; photos:массив URLстрок; photos_observed_at:дата UTC или null; latest_price:Price или null |
| AdDetail | Все ключи AdSummary плюс description:string или null; price_history:массив Price |
| PropertySummary | Все ключи PropertyBase плюс ads:массив AdSummary, только прошедшие фильтры активные ads |
| PropertyDetail | Все ключи PropertyBase плюс ads:массив AdDetail, все сохранённые ads |
| PropertyList | count:integer>=0; page:integer>=1; page_size:integer ровно20; next/previous:внутренняя относительная API-ссылка строкой или null; results:массив PropertySummary |
| FieldError | code:строка из перечисления ошибок валидации; message:понятная строка |
| ErrorResponse | Единственный верхний ключ error:объект с code:string, message:string, fields:объект-словарь имяполя→массив FieldError |

PropertyDetail возвращается непосредственно объектом, без results и page. PropertyList — только для списка. В next/previous сохраняются все нормализованные фильтры; путь начинается /api/properties/, номер меняется только на соответствующую страницу. results содержит не более20уникальных properties.

Время везде строка ISO8601UTC с завершающей Z; дробные секунды допустимы до6знаков, если есть в сохранённом значении. Примеры формата: 2026-11-17T10:00:00Z и 2026-11-17T10:00:00.123456Z — это примеры формата, не протокол измерений. Decimal-строки имеют фиксированную шкалу: деньги/площади2,координаты7. Не использовать JSON float для этих полей и строковые true/false для boolean.

Ограничения выходных данных сохраняются из БД: координаты парой в диапазонах широты[-90,90],долготы[-180,180]; area_m2/land_area_m2>0 при известном значении; area_m2 максимум9999999999.99, land_area_m2 максимум999999999999.99; при известной паре floor<=floors_total. Для целого дома floor=null. photos всегда массив; photos_observed_at=null означает неизвестный список с photos=[]. price_history — по observed_at от старых к новым, latest_price совпадает с последней записью или null при пустой истории. В кратком списке история не передаётся, но latest_price вычисляется тем же чтением. Не создавать копию цены в ads, не записывать «неполученную» цену отдельной строкой.

## 4. Ошибки

Для invalid_query: HTTP400, error.code=invalid_query, message=«Исправьте параметры запроса.», fields — все обнаруженные ошибки. Допустимые FieldError.code: invalid_integer, invalid_decimal, invalid_choice, out_of_range, not_found, inverted_range, repeated_parameter, unknown_parameter. Ключ fields — имя входного поля; неизвестный входной ключ также может быть ключом словаря ошибок. Для обратного диапазона запись находится у обоих min/max.

Неизвестный /api/properties/<id>/ или недопустимый по формату/положительности/bigint ID в этом маршруте: HTTP404, error.code=not_found, message=«Объект не найден.», fields={}. Неизвестный путь под /api/ также даёт JSON404 этой формы с сообщением «Ресурс не найден.», не случайный HTML-ответ Django. Неподдержанный метод на известных APIмаршрутах: HTTP405, error.code=method_not_allowed,message=«Метод не поддерживается.»,fields={}. Ошибка нашего сервера: HTTP500, code=internal_error,message=«Не удалось загрузить данные.»,fields={}; внутренние детали выводятся в лог Django, доступный оператору через Docker. Аутентификация административных HTML-страниц не превращается в новый публичный API.

Пустой поиск — HTTP200 с count0/results[]/page1/next=null/previous=null, не ErrorResponse. Все ads сняты — полная карточка HTTP200, is_active=false; она не попадает в обычную выдачу. Ошибка отдельного внешнего изображения не меняет HTTPкод нашей карточки/JSON.
