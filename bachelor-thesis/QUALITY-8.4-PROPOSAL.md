# 8.4 — локальные проверки, hooks и CI

**ПРИНЯТО, 8.4 ЗАКРЫТ.** 18 ноября 2026. Владелец принял 8.4; 8.1–8.3 также приняты и закрыты. Здесь проект автоматизации, а не созданные workflow/hooks/config. pre-commit как dev-зависимость и GitHub Actions приняты владельцем; установки, рабочие файлы и настройки репозитория не выполняются. Версии Python/Django/PostgreSQL/uv/actions и совместимые пакеты фиксируются отдельным решением до реализации.

## 1. Основа и существующие механизмы

Настройки Ruff/mypy/djLint остаются в едином pyproject.toml по 8.2, зависимости — uv.lock. Предлагаем pre-commit как готовый диспетчер быстрых Git hooks, без собственного runner проверок, Makefile-обёртки или второго стека тестов. Файл .pre-commit-config.yaml будет описывать только выбор/порядок команд и путей, не второй набор lint/style-настроек. Локальные hooks используют готовый режим внешней команды (в текущей документации language=unsupported; прежний system — устаревающий alias, окончательное имя соответствует выбранной версии) и запускают инструменты проектного uv-окружения, а не отдельные несовпадающие версии плагинов.

Фактически проверено в текущем checkout: приложения/pyproject/uv.lock/.pre-commit-config.yaml/workflow ещё нет; npm Playwright обслуживает документы и не становится runner приложения. .git/hooks/pre-commit отсутствует; .git/hooks/pre-push существует и вызывает git lfs pre-push. Его не заменяем, core.hooksPath не меняем, новый quality pre-push не устанавливаем. Будущий pre-commit install ограничивается стадией pre-commit. Если обнаружится другой hook этой стадии — сохранить и согласовать совместную установку, не применять overwrite молча.

После отдельного разрешения настройки окружения: uv sync --locked (включая согласованную dev-группу) проверяет соответствие lock и устанавливает окружение без обновления lock; при несовпадении — ошибка, не uv lock внутри проверки. Далее команды через uv run --no-sync используют это подготовленное окружение; no-sync сам не доказывает актуальность окружения, поэтому после изменения pyproject/uv.lock sync повторяется. Перед app-проверками hook выполняет штатный uv sync --locked --check с теми же dev-группами: при устаревшем окружении — диагностика, без установки/изменения lock. Конкретная совместимость этих флагов закрепляется выбранной версией uv. Пустой кэш может требовать загрузку пакетов при подготовке; отсутствие реальной сети источников в тестах не означает полностью offline-install.

## 2. Когда и что запускается локально

| Изменение/этап | Проверки | Граница |
|---|---|---|
| Только документы/доказательства | git diff --check по своим изменениям; статусы и реально затронутые локальные ссылки. | Приложение, БД, браузер и полный тестовый набор не запускаются. Новый Markdown-линтер не добавляем. |
| Python/тесты приложения | Ruff check и Ruff format --check по затронутым Python-файлам, включая миграции; mypy по всей собственной области manage.py/config/catalog/collection, затем выбранные поведенческие тесты затронутых сценариев. | mypy не ограничивается одним изменённым файлом: важны его вызывающие/контракты. При изменении общего lint/type-профиля — вся область 8.2. |
| Собственные Django-шаблоны | djlint --lint и --check по затронутым шаблонам; проверка соответствующего рендера/браузерного сценария, если меняется внешний вид/поведение. | Форматирование не заменяет рендер; изменение текста без риска поведения не требует всех UI-тестов. |
| Схема/ограничения/запись | Штатные Django check; makemigrations --check --dry-run; релевантные ORM/TransactionTestCase на тестовом PostgreSQL, применение миграций штатным Django test runner. | Не применяем миграции к пользовательской БД. Конкуренция/права БД проверяются по 7.1, не SQLite/моками. |
| Общий контракт/настройки/зависимости или широкий связанный риск | Вся статика приложения + check + отсутствие незаписанных миграций + полный собственный набор Django/Playwright тестов. | Версии меняются только согласованно, не как побочное действие проверки. |
| Перед коммитом | Автоматический быстрый pre-commit из §3. Остальные необходимые по риску проверки выполнены разработчиком/агентом до коммита. | Hook не является полной приёмкой и не запускает БД/браузер. |

Будущие команды, не выполняемые сейчас: uv run --no-sync ruff check <пути>; ruff format --check <пути>; mypy manage.py config catalog collection; djlint <шаблоны> --lint и --check; python manage.py check; python manage.py makemigrations --check --dry-run; python manage.py test <labels>. Во всех случаях инструменты после первого примера также запускаются через uv run --no-sync, Django — с согласованными test settings. Labels выбираются по 7.1; полный набор — catalog и collection, включая браузерные классы. Отдельный pytest не вводится.

Сервисы запускаются только для нужных поведенческих проверок и по уже действующим правилам владения ресурсами; собственного локального Docker runner и автоматической аренды этим документом не создаём. До реализации соответствующего механизма нельзя обещать работающую автоуборку. После проверки освобождаются только свои ресурсы с сохранением данных; чужой стек не останавливается.

## 3. Быстрый hook: только проверка, без исправлений

1. Предлагаем dev-зависимость pre-commit через uv.lock. Стадия только pre-commit, не pre-push. Стандартная установка hook — отдельное действие при разрешённой настройке окружения; Git clone сам его не включает.
2. Для staged Python-файлов своей области — Ruff check без --fix и Ruff format --check. Для staged собственных Django-шаблонов — djlint --lint и --check. Передаются имена нужных файлов; нет исключения всей migrations из hooks, даже если готовый upstream hook предлагает такой default.
3. Изменение pyproject/.pre-commit-config.yaml выбирает полную статическую область соответствующего инструмента; изменение pyproject/uv.lock также проверяет свежесть lock/подготовки окружения. Для lock-проверки использовать штатный uv lock --check без обновления. Вызов полного режима — pass_filenames=false; вручную прогнать проверку конфигурации pre-commit при изменении её файла. Удаление файла не передаётся линтеру как существующий файл; CI сверит итоговое дерево.
4. Mypy, Django checks/tests, PostgreSQL и браузер в commit hook не включаем. Их выбор — §2, полный проход — CI. Никакой скрытой сети к площадкам. Исправление/форматирование — отдельная явная команда с просмотром diff, не hook, пишущий и автоматически добавляющий файлы.
5. pre-commit временно убирает unstaged-изменения для проверки staged-снимка и восстанавливает их штатным механизмом; не добавляем свой git stash/reset и не меняем staged/unstaged. Это не проверка произвольных untracked-файлов и не гарантия от любого сбоя восстановления. Если восстановление не удалось, остановиться и сохранить патч/объяснить состояние, не чистить изменения.
6. Ошибка проверки останавливает commit. Локальный hook технически обходится и требует установки, поэтому CI независимо проверяет результат. Агент не обходит его ради зелёного статуса; отсутствие установленного hook не выдаётся за прохождение проверок. Git LFS pre-push выполняет прежнюю отдельную задачу загрузки LFS-объектов.

## 4. CI: GitHub Actions

Предлагаем один workflow с событиями pull_request в main, push в main и ручным запуском. Не требуем нового процесса веток/PR для каждой правки, не включаем деплой/публикацию. Для проверки изменений PR используем фактическую базу/merge-base; push — before/after; создание ветки/нулевой before, отсутствие доступной базы или ошибка классификации означают полный набор, а не «изменений нет». Обрабатываются удаления и переименования, не только существующие изменённые файлы.

Три коротких jobs нужны для условного запуска БД и достоверного итогового статуса, не для разделения приложения на новые сервисы:

- **classify:** всегда запускается; определяет документные изменения и затронутое приложение. Приложение — manage.py/config/catalog/collection, его tests/templates/migrations, pyproject.toml, uv.lock, .pre-commit-config.yaml и этот workflow. Изменения только .md-документации вне исполняемых областей, нормативных материалов и выбранных evidence не запускают приложение. Неизвестный путь или неверная классификация — полный набор. Новый файл под tests/ или шаблон не считается документацией по одному расширению. Используется штатный Git в коротком workflow step, не новая сторонняя dependency/runner. Имена файлов не исполняются как shell-текст.
- **app-checks:** только при затронутом приложении/общей конфигурации или ручном полном запуске. Один согласованный Linux/Python/PostgreSQL-профиль, без матрицы всех версий. Свежий checkout/uv sync --locked; вся Ruff/mypy/djLint-область 8.2, Django check, makemigrations --check --dry-run, полный собственный Django-набор catalog/collection с ORM/транзакционными и браузерными тестами. PostgreSQL — изолированный job service с health check; browser-тесты — одна согласованная Chromium-среда через Python library/LiveServer, без обязательного pytest. Browser устанавливается готовой Playwright-командой вместе с системными зависимостями. Миграции применяет test runner к временной test DB, не к внешней БД. Для F25 используется отдельная прикладная роль с принятыми правами; административная тестовая роль не заменяет её проверку.
- **quality:** всегда формирует итог по classify/app-checks, включая ошибки/отмену. Успех только если classify успешен и app-checks успешен либо действительно не требовался. Не называть skipped app-проверки выполненными. Предлагаем сделать quality обязательной проверкой main после отдельной разрешённой настройки ruleset/защиты; сейчас GitHub-настройки не меняются. Условия зависимости/always проверяются при реализации, чтобы skipped/failed upstream не дали ложный зелёный статус.

Не используем workflow-level paths/paths-ignore для обязательного workflow: иначе обязательная проверка может остаться Pending. При документах classify/quality завершаются с явным «проверки приложения не требовались», app-checks не создаёт PostgreSQL/browser. При ошибке полного набора CI красный; нет continue-on-error, повторов всего упавшего теста ради успеха или скрытого skip проблемных сценариев.

CI проверяет проект на фиксированных локальных fixture и временных данных. Контроль живых Авито/Циан/Домклик выполняется отдельно при изменении источника/перед показом по принятой 7.1; нестабильность внешней площадки не блокирует каждый commit/PR и не превращает fixture в доказательство живого сбора.

Минимальные permissions GITHUB_TOKEN: contents:read, checkout без сохранённых credentials, действия закреплены полными commit SHA; это фиксация выбранных действий, не гарантия неизменности их транзитивных зависимостей. Не pull_request_target с исполнением чужого кода, без production-секретов/доступа к локальному компьютеру пользователя. Изоляция временных job service/контекстов; закрытие ресурсов в cleanup/finally на штатных путях, ресурсы hosted runner исчезают с job. Кэш ускоряет подготовку, но не заменяет uv.lock и не является доказательством проверки. При падении сохраняются выбранные безопасные test-логи/trace, если были созданы, без секретов и сырых данных пользователя; диагностические материалы не коммитятся автоматически.

## 5. Что этим не считается выполненным

Это проект порядка запуска и состава проверок. pre-commit, workflow, ruleset и команды пока не установлены/не испытаны. Их первый реальный проход должен проверить staged/unstaged, ошибочный код, миграцию, отрицательный тест, документы-only, удаление/rename, отказ classify, skipped/failed/cancelled dependencies и сохранность LFS hook. Испытания автоматики не заменяют 7.1–7.4 или ревью архитектуры 8.3.

Первичные факты: [QUALITY84-PRIMARY-SOURCES.md](evidence/QUALITY84-PRIMARY-SOURCES.md), [pre-commit](https://pre-commit.com/), [uv lock/sync](https://docs.astral.sh/uv/concepts/projects/sync/), [GitHub required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks), [Playwright CI](https://playwright.dev/python/docs/ci). Состав/момент запуска, pre-commit, три jobs и выбор Chromium приняты владельцем в составе 8.4; это правила проекта, не требования университета. 8.4 закрыт 18 ноября 2026. Исторические слова «предлагаем» описывают теперь принятый вариант; установки и рабочие конфигурации по-прежнему не выполнялись.
