# 8.4 — локальные проверки, hooks и CI

## 1. Инструменты

Настройки Ruff, mypy и djLint находятся в [pyproject.toml](../implementation/pyproject.toml), версии закреплены в [uv.lock](../implementation/uv.lock). Подготовка выполняется из `implementation/` через `uv sync --locked --dev`. После изменения зависимостей или lock-файла окружение синхронизируется заново. Для проверок используется подготовленное окружение с `uv run --no-sync`.

## 2. Локальные проверки по изменению

| Изменение | Что проверить |
|---|---|
| Документы и доказательства | `git diff --check` по своим изменениям и затронутые ссылки. |
| Python, тесты и миграции | Ruff по изменённым файлам, mypy по всей собственной области и сценарии, затронутые изменением. |
| Django-шаблоны | djLint для изменённых шаблонов и рендер при изменении поведения или внешнего вида. |
| Схема, ограничения, транзакции, роли | Django check и `makemigrations --check --dry-run`, затронутые транзакции и права на настоящем временном PostgreSQL. |
| Общий контракт или профиль проверок | Полная статика через `bash tools/check-style.sh --types` и набор проверок приложения по риску. |

`bash tests/compose.sh` запускает сквозные проверки в отдельном проекте Compose с временным томом, проверкой принадлежности и уборкой своих ресурсов при выходе. Проверка использует прикладную роль для сценариев прав, штатную подготовку БД, сохранённую карточку Циан и сигналы контейнера для команды сбора. Успешная изолированная проверка не подтверждает живую доступность площадки.

## 3. Pre-commit

Конфигурация [pre-commit](../.pre-commit-config.yaml) подключает проверку staged-файлов на стадии коммита. Hook проверяет lock и свежесть окружения. Скрипт `tools/check-staged.sh` проверяет staged-файлы. При изменении профиля запускается полный lint и проверка форматирования. Форматирование и исправления выполняются отдельной явной командой. Pre-commit штатно изолирует и восстанавливает unstaged-изменения. Mypy, PostgreSQL и браузер остаются вне commit hook. Git LFS сохраняет отдельный pre-push.

## 4. GitHub Actions

[Quality](../.github/workflows/quality.yml) запускается для pull request в `main`, push в `main` и вручную.

- `classify` определяет, затронуто ли приложение или общая конфигурация. Для pull request используется merge-base, для push — предыдущий SHA. При отсутствии корректной базы запускается набор приложения. Документные изменения классифицируются отдельно, пути приложения имеют приоритет.
- `app-checks` подготавливает окружение с закреплёнными версиями, проверяет конфигурацию pre-commit и статические правила, затем запускает `tests/compose.sh`. Проверки охватывают Django, миграции, прикладные права PostgreSQL, браузерные тесты и текущую терминальную команду сбора. При ошибке сохраняется краткий отчёт о фазах без секретов.
- `quality` формирует итог. Успех требует успешной классификации и выполнения нужного набора. При документных изменениях в результате явно указано, что проверки приложения не требовались. Ошибка и отмена не дают успешного итога.

Workflow использует права `contents: read`, закреплённые SHA действий и checkout без сохранения credentials. Живые проверки площадок выполняются отдельно при изменении соответствующего адаптера или приёмке. Функциональные критерии и исследование определены в [7.1](ACCEPTANCE-7.1-PROPOSAL.md).

Обязательность итогового `quality` для защищённой ветки определяется настройкой GitHub. Состав проверок подтверждается выполнением workflow на оцениваемом SHA. [Первичные источники](evidence/QUALITY84-PRIMARY-SOURCES.md)
