**ПРЕДЛОЖЕНИЕ, НЕ ПРИНЯТО.** 18 ноября 2026. Контейнерный профиль принят, 1–8 закрыты; эта детализация 9 ещё не принята. Принятые P6/F25 уже требуют защищать историю даже от прямого SQL runtime-роли. Ниже способ обеспечить это и подготовить приложение. SQL/код/конфигурации/контейнеры не создавались; ничего не устанавливалось и не запускалось.

## 1. Минимальная схема ролей

Две прикладные LOGIN-роли; существующий администратор кластера PostgreSQL нужен только для первоначального создания ролей/БД. Это не третья прикладная роль, не таблица пользователей и не третий сервис Compose.

| Учётная запись PostgreSQL | Назначение | Граница |
|---|---|---|
| postgres / отдельные bootstrap credentials кластера | Однократная подготовка выделенной прикладной БД, двух ролей и их владельцев/прав. | Административный доступ остаётся у оператора/db, не попадает в web/runner. POSTGRES_USER официального image создаётся superuser: нельзя просто назвать его nir_app и выдать приложению. |
| nir_owner | Владелец прикладной БД и создаваемых объектов, служебное выполнение Django migrate, data migrations и явная выдача прав. | LOGIN, без SUPERUSER/CREATEDB/CREATEROLE/REPLICATION/BYPASSRLS. Работает в отдельном одноразовом вызове image app; его credentials отсутствуют у постоянно работающего app/runner. |
| nir_app | Все обычные соединения Django, admin сайта и сборщика. | LOGIN, без ownership БД/схемы/таблиц, SUPERUSER/CREATEDB/CREATEROLE/REPLICATION/BYPASSRLS. Не член nir_owner/административных ролей, не может SET ROLE в них и не получает GRANT OPTION. |

Администратор сайта Django (createsuperuser) — учётная запись в штатной auth-таблице, не PostgreSQL superuser. Даже Django superuser работает через nir_app и не обходит права истории. Скрипт bootstrap ограничен выделенным Compose-проектом/БД; существующие чужие роли/данные не переименовываются и не удаляются.

## 2. Права nir_app: достаточно для функций, без владения схемой

Предлагаем одну прикладную БД и обычную схему public, без дополнительного слоя schemas. Объекты создаёт nir_owner. Для runtime явно CONNECT к этой БД, USAGE схемы и USAGE необходимых последовательностей; без CREATE/TEMPORARY. Права PUBLIC и членства также проверяются: отсутствие личного GRANT не доказывает отсутствие эффективного права. У прикладной БД не оставляем доступ/временные объекты через PUBLIC, у public — CREATE через PUBLIC. Это изменения только своей БД/схемы, не глобальное отключение функций PostgreSQL.

| Объект | Разрешения nir_app | Почему |
|---|---|---|
| sources | SELECT и UPDATE только enabled | Три поддержанных источника создаются подготовкой; интерфейс меняет только enabled. code не редактируется. |
| regions, property_types | SELECT/INSERT/UPDATE/DELETE | Уже принятый CRUD справочников; FK и серверная защита удаления при run остаются обязательными. |
| properties | SELECT/INSERT/UPDATE | Получение и разрешённый property_patch; без физического удаления недвижимости. |
| ads | SELECT/INSERT; UPDATE только url, market_segment, description, is_active, observed_at, photos, photos_observed_at | Стабильные id/property_id/source_code/external_id/deal_type прежней публикации не переписываются. Новая публикация получает их при INSERT; обновление использует явный допустимый набор полей по P1/P7. |
| price_history | SELECT/INSERT | Никаких UPDATE/DELETE/TRUNCATE/ownership/владельческих обходов. Данные append-only для runtime, включая прямой SQL. |
| Штатные Django auth/contenttypes/admin/sessions | Необходимый штатный SELECT/INSERT/UPDATE/DELETE по конкретному списку таблиц | Авторизация/сессии/формы/журнал admin; не перенос истории цен в Django admin и не новая регистрация пользователей продукта. |
| django_migrations | SELECT | Runtime может проверить состояние схемы, но не отмечать миграции выполненными. |

TRUNCATE не выдаётся runtime ни на одной таблице; CREATE/ALTER/DROP/управление triggers не разрешаются через ownership или роли. USAGE последовательностей не означает UPDATE/setval. Для column-level UPDATE (sources/ads) ORM пишет только разрешённые поля через штатный update_fields/QuerySet.update, а не сохраняет повторно все колонки. Это не новый service-wrapper; правило приёма остаётся в catalog.services. Вся выдача прав — явный перечень по принятой схеме, не GRANT ALL ON ALL TABLES и не мутирующие default privileges для любых будущих таблиц.

После каждого migrate служебный шаг повторно приводит разрешения к этой матрице: новые объекты по умолчанию остаются у владельца, до применения прав web не запускается. Удаляются противоречащие runtime/PUBLIC grants, а не только добавляются новые. Миграции выполняет именно nir_owner, чтобы ownership не менялся случайно. Не нужно внедрять новый privilege-framework: используются штатные PostgreSQL роли/GRANT/REVOKE и обычные Django migrations.

Дополнительная защита смысла P6: FK используемых объектов не делают каскадного удаления/изменения истории (NO ACTION/RESTRICT, без CASCADE/SET NULL/SET DEFAULT по пути к price_history); приложение не получает доступ к SECURITY DEFINER-функциям, которые обходят эту матрицу. Это проверяется по реальным миграциям/F25, не объявляется автоматически доказанным одним отсутствием UPDATE. Владелец/администратор кластера — доверенный служебный доступ, его способность обслуживать БД не выдаётся за возможность обычного приложения.

## 3. Первый запуск: точный порядок

Только при отдельном разрешении реализации и настройки. Никаких новых постоянных Compose-сервисов: db и app; подготовительные команды используют то же image app как одноразовые процессы.

1. **Подготовить окружение.** Согласованный commit/контейнерный профиль, собранный app и uv.lock, отдельные credentials bootstrap/owner/runtime вне Git/image. Постоянный app получает только nir_app; owner/bootstrap не подмешиваются через общий env-файл или общий bind mount с секретами. У image правильные Python/uv/Playwright и браузерные зависимости, без host .venv.
2. **Запустить только свой db.** Дождаться healthcheck pg_isready и проверить целевую БД/соединение. Готовность PostgreSQL не доказывает существование ролей, миграций и прав. Не создавать/очищать volume, если ожидаемые данные уже существуют.
3. **Явная bootstrap-подготовка.** Под административными credentials создать недостающее nir_owner/nir_app/прикладную БД, назначить владельца и границы доступа. Повтор проверяет совпадение ожидаемых владельцев/атрибутов; не перезаписывает пароли, не DROP/CREATE существующую БД и не захватывает чужую роль. Противоречие — остановка с причиной. Не полагаться только на docker-entrypoint-initdb.d: он работает лишь на пустом PGDATA, а после частичного сбоя не повторяется автоматически на существующем volume.
4. **Применить миграции.** Одноразовым вызовом app под nir_owner выполнить штатный migrate из уже записанных миграций. Не makemigrations на старте, не migrate под runtime и не import/ready-сигналы с оркестрацией. Обычный migrate может писать через post_migrate даже без новых операций, поэтому всегда использует служебную роль. Ошибка не маскируется успешным стартом. PostgreSQL обычно поддерживает atomic migration, но весь набор миграций не обещается единой транзакцией: ранее завершённые шаги могут сохраниться, atomic=False возможен.
5. **Назначить и проверить права.** Под nir_owner применить явную матрицу §2 и проверить эффективные права, owners и членства. Стабильные defaults/прежние grants не считаются достаточным доказательством. Негативные SQL-тесты с существующими данными — только в отдельной проверочной БД, не на рабочем каталоге; на целевой БД — проверка метаданных/прав без разрушительных проб.
6. **Подготовить администратора и отдельно согласованные начальные данные.** Принятые справочники/источники — по §4. Создать Django superuser явной штатной командой через runtime credentials, без пароля по умолчанию/его публикации. Повтор не сбрасывает пароль и не создаёт второго администратора автоматически.
7. **Запустить app под nir_app.** Перед web/доступностью запусков — штатный migrate --check без --prune и прочих изменяющих опций: он проверяет отсутствие pending migrations и не выполняет обычный post_migrate. Неприменённая схема/ошибка подключения — остановка с причиной, без автоматического migrate и бесконечного retry. База всегда проверяется независимо от того, новый volume или старый. Чистые импорты/системные проверки по 8.3 обязательны: --check не обезвреживает произвольный startup-код проекта.
8. **Проверить фактический запуск.** Каталог/карточка/JSON, вход/права и согласованные справочники по 7.1. Полный старт/остановка сбора и журнал — после отдельного принятия начального наполнения/привязки поддержанных видов. Проверить текущую роль nir_app и реальные версии/схему. Пустой каталог допустим; успешный healthcheck без пользовательского прохода не считается готовым приложением. Реальные сборы источников проверяются отдельно от подготовленных тестовых данных.

## 4. Начальные данные без повторного сброса

Предлагаем обычную одноразовую Django data migration с историческими моделями по 8.2:

- sources: code avito/cian/domclick, при первоначальном создании enabled=true для поддержанных адаптеров. Это не автозапуск сбора; текущая доступность сайтов не обещается. Повторный запуск не меняет пользовательский enabled.
- property_types: конкретные числовые ID, seed поддержанных видов и восстановление поддержки после удаления не выбираются этим предложением ролей. Сохраняется принятый смысл стабильного ID и разрешённый CRUD; добавление нового названия само не создаёт поддержку маршрута. Начальное наполнение/привязка видов — отдельное открытое решение 9 перед реальным сбором, без новых колонок или молчаливого запрета удаления.
- regions: нет выдуманного полного официального списка/кодов; администратор добавляет нужные субъекты РФ штатной формой. До выбора хотя бы одного региона запуск сбора не предлагается как готовый. Автоматического сброса/повторного заполнения справочников при старте app нет.
- Демопубликации не подмешиваются автоматически в рабочую БД. Контролируемые fixtures/исследовательская разметка отдельно, не основание создавать новые таблицы или включать ручной merge.

Bootstrap, data migration и выдача прав — разные операции. Переход на повторный migrate не означает повторной перезаписи начальных данных; исходники/миграционная история контролируют, какие изменения нужны.

## 5. Повторный запуск и изменение версии

Обычный restart: прежний volume, те же пользователи/данные, runtime проверка migrate --check и запуск; ни миграций, ни seed/reset/очистки таблиц автоматически. Старый runner сам не возобновляется.

Обновление схемы: штатно остановить сбор и дождаться завершения текущей записи/освобождения run; остановить свой app; одноразовый migrate под nir_owner; повторная выдача/проверка прав; запуск runtime и относящиеся к риску проверки. При сбое не запускать старый/новый web автоматически, не удалять volume и не объявлять откат всех прежних миграций гарантированным. Backup не возвращается как обязательный шаг.

## 6. Тестовая БД и критерии проверки этой схемы

Нельзя дать nir_app CREATEDB/TRUNCATE или membership в nir_owner ради удобства TestCase. Общий Django test runner выполняется отдельными административными test credentials только в изолированном тестовом PostgreSQL/БД: он создаёт test DB, мигрирует и выполняет служебную очистку. Эта роль не попадает в web или рабочий volume. Для F25 и runtime-доступа нужны отдельные настоящие соединения nir_app с точно выданными правами; привилегированный test-runner не доказывает защиту приложения. Права тестовой схемы готовятся отдельно под те же P6/§2. При проверке через разные соединения данные видимы обеим ролям: для таких транзакционных сценариев применяется TransactionTestCase/явно завершённая подготовка. Успех migrate под test-admin не доказывает доступ nir_owner; служебный запуск nir_owner отдельно проверяется при smoke первого запуска.

Будущие проверки до заявления «первый запуск работает»:

- новая пустая среда: owner мигрирует/создаёт справочники, runtime открывает каталог/JSON, администратор сайта входит;
- положительные INSERT/UPDATE допустимых объявлений/patch/цены, изменение sources.enabled и CRUD справочников через обычный runtime; history INSERT успешен;
- под nir_app невозможно UPDATE/DELETE/TRUNCATE старой истории, DROP/изменение владельца, DDL и SET ROLE nir_owner; запрещённые операции не оставляют частичных записей, проверяется F25/F15;
- проверка путей FK/функций и PUBLIC/членств; успешный прямой GRANT/REVOKE аудит дополняется SQL-проверкой поведения в тестовой БД;
- повторная подготовка/перезапуск не меняют данные, enabled, подписи/ID и пароль Django-администратора;
- pending migrations, неудачный migrate или неправильные права не дают ложной готовности; повтор после исправления проходит без удаления volume;
- новый применённый migration не открывает runtime новые права на историю, а старая привилегированная роль не появляется в web/runner.

F01–F25 не переписываются; эти сценарии раскрывают эксплуатационные условия их исполнения. Начальное наполнение/привязка поддержанных видов и восстановление после удаления, браузерный sandbox/init, точные порты, хранение журналов/служебного состояния и учёт ресурсов остаются следующими деталями9, не объявляются здесь решёнными.

Первичные механизмы и ограничения: [FIRST-LAUNCH-ROLES-PRIMARY-SOURCES.md](evidence/FIRST-LAUNCH-ROLES-PRIMARY-SOURCES.md), [PG17 privileges](https://www.postgresql.org/docs/17/ddl-priv.html), [официальный Postgres image](https://hub.docker.com/_/postgres), [Django migrate5.2](https://docs.djangoproject.com/en/5.2/ref/django-admin/#migrate). Новые роли/права/порядок и seed defaults пока НЕ ПРИНЯТЫ; это не требования университета и не выполненная установка.
