# Пункт 9 — первый запуск, миграции и роли PostgreSQL

Подготовка выделенной БД, роли `migrator` и `app`, и порядок запуска используются для защиты истории цен по P6 и F25.

## 1. Минимальная схема ролей

Две прикладные LOGIN-роли; существующий администратор кластера PostgreSQL нужен только для первоначального создания ролей/БД. Это не третья прикладная роль, не таблица пользователей и не третий сервис Compose.

| Учётная запись PostgreSQL | Назначение | Граница |
|---|---|---|
| postgres / отдельные bootstrap credentials кластера | Явная подготовка выделенной прикладной БД, двух ролей и их владельцев/прав. | Административный доступ остаётся у оператора/db, не попадает в Django и сбор. POSTGRES_USER официального image создаётся superuser: нельзя просто назвать его app и выдать приложению. |
| migrator | Владелец прикладной БД и создаваемых объектов, служебное выполнение Django migrate, data migrations и явная выдача прав. | LOGIN, без SUPERUSER/CREATEDB/CREATEROLE/REPLICATION/BYPASSRLS. Работает в отдельном одноразовом вызове image app; его credentials отсутствуют у постоянно работающего сайта или команды сбора. |
| app | Все обычные соединения Django, admin сайта и сборщика. | LOGIN, без ownership БД/схемы/таблиц, SUPERUSER/CREATEDB/CREATEROLE/REPLICATION/BYPASSRLS. Не член migrator/административных ролей, не может SET ROLE в них и не получает GRANT OPTION. |

Администратор сайта Django (createsuperuser) — учётная запись в штатной auth-таблице, не PostgreSQL superuser. Даже Django superuser работает через app и не обходит права истории. Скрипт bootstrap ограничен выделенным Compose-проектом/БД; существующие чужие роли/данные не переименовываются и не удаляются.

## 2. Права app: достаточно для функций, без владения схемой

Используется одна прикладная БД и обычную схему public, без дополнительного слоя schemas. Объекты создаёт migrator. Для runtime явно CONNECT к этой БД, USAGE схемы и USAGE необходимых последовательностей; без CREATE/TEMPORARY. Права PUBLIC и членства также проверяются: отсутствие личного GRANT не доказывает отсутствие эффективного права. У прикладной БД не оставляем доступ/временные объекты через PUBLIC, у public — CREATE через PUBLIC. Это изменения только своей БД/схемы, не глобальное отключение функций PostgreSQL.

| Объект | Разрешения app | Почему |
|---|---|---|
| sources | SELECT и UPDATE только enabled | Три поддержанных источника создаются подготовкой; интерфейс меняет только enabled. code не редактируется. |
| regions, property_types | SELECT/INSERT/UPDATE/DELETE | Уже принятый CRUD справочников; FK и серверная защита удаления при run остаются обязательными. |
| properties | SELECT/INSERT/UPDATE | Получение и разрешённый property_patch; без физического удаления недвижимости. |
| ads | SELECT/INSERT; UPDATE только url, market_segment, description, is_active, observed_at, photos, photos_observed_at | Стабильные id/property_id/source_code/external_id/deal_type прежней публикации не переписываются. Новая публикация получает их при INSERT; обновление использует явный допустимый набор полей по P1/P7. |
| price_history | SELECT/INSERT | Никаких UPDATE/DELETE/TRUNCATE/ownership/владельческих обходов. Данные append-only для runtime, включая прямой SQL. |
| Штатные Django auth/contenttypes/admin/sessions | Необходимый штатный SELECT/INSERT/UPDATE/DELETE по конкретному списку таблиц | Авторизация/сессии/формы/журнал admin; не перенос истории цен в Django admin и не новая регистрация пользователей продукта. |
| django_migrations | SELECT | Runtime может проверить состояние схемы, но не отмечать миграции выполненными. |

TRUNCATE не выдаётся runtime ни на одной таблице; CREATE/ALTER/DROP/управление triggers не разрешаются через ownership или роли. USAGE последовательностей не означает UPDATE/setval. Для column-level UPDATE (sources/ads) ORM пишет только разрешённые поля через штатный update_fields/QuerySet.update, а не сохраняет повторно все колонки. Это не новый service-wrapper; правило приёма остаётся в catalog.publications. Вся выдача прав — явный перечень по принятой схеме, не GRANT ALL ON ALL TABLES и не мутирующие default privileges для любых будущих таблиц.

После каждого migrate служебный шаг повторно приводит разрешения к этой матрице: новые объекты по умолчанию остаются у владельца, до применения прав web не запускается. Удаляются противоречащие runtime/PUBLIC grants, а не только добавляются новые. Миграции выполняет именно migrator, чтобы ownership не менялся случайно. Не нужно внедрять новый privilege-framework: используются штатные PostgreSQL роли/GRANT/REVOKE и обычные Django migrations.

Дополнительная защита смысла P6: FK используемых объектов не делают каскадного удаления/изменения истории (NO ACTION/RESTRICT, без CASCADE/SET NULL/SET DEFAULT по пути к price_history); приложение не получает доступ к SECURITY DEFINER-функциям, которые обходят эту матрицу. Это проверяется по реальным миграциям/F25, не объявляется автоматически доказанным одним отсутствием UPDATE. Владелец/администратор кластера — доверенный служебный доступ, его способность обслуживать БД не выдаётся за возможность обычного приложения.

## 3. Первый запуск: точный порядок

Из каталога `implementation/` оператор задаёт `POSTGRES_PASSWORD`, `DB_MIGRATOR_PASSWORD`, `DB_APP_PASSWORD`, `DJANGO_SECRET_KEY` и при необходимости `DB_NAME` в окружении. Секреты хранятся вне репозитория и образа. Подготовку одной БД выполняет один оператор за раз.

```sh
docker compose build app
docker compose up -d --wait db
bash tools/prepare-db.sh
docker compose up -d --wait app
docker compose exec app python -m app.manage createsuperuser
```

[tools/prepare-db.sh](../implementation/tools/prepare-db.sh) под `postgres` проверяет атрибуты ролей и владельца БД и создаёт отсутствующие прикладные роли и БД. Затем одноразовый контейнер `app` запускает штатный `migrate` с настройками `app.config.settings_migrator`. Скрипт проверяет владение объектами схемы, приводит разрешения к матрице из §2 и проверяет соединение под `app`. Существующие пароли и БД сохраняются.

Django запускается под ролью `app` после `migrate --check`. Эта проверка выявляет неприменённые миграции. Подготовка прав выполняется до запуска сайта. Падение любого шага останавливает подготовку. При частично применённых миграциях оператор исправляет причину и повторяет подготовку на том же томе.

## 4. Начальные данные

Миграции загружают три источника, три вида недвижимости и 89 регионов со стабильными внутренними идентификаторами. Подписи и флаги сохраняются при обычном перезапуске. Восстановление исходных записей запускается явной командой. [Начальные данные](INITIAL-DATA-PROPOSAL.md)

## 5. Повторный запуск и изменение версии

Обычный запуск выполняется через `docker compose up -d --wait` с тем же томом. Оператор запускает сбор отдельно. При обновлении схемы он завершает сбор и останавливает свой `app`, обновляет образ, повторно выполняет `bash tools/prepare-db.sh` при работающем `db` и запускает `app`. Сохранённые данные остаются на томе.

## 6. Тестовая БД и критерии проверки этой схемы

Нельзя дать app CREATEDB/TRUNCATE или membership в migrator ради удобства TestCase. Общий Django test runner выполняется отдельными административными test credentials только в изолированном тестовом PostgreSQL/БД: он создаёт test DB, мигрирует и выполняет служебную очистку. Эта роль не попадает в web или рабочий volume. Для F25 и runtime-доступа нужны отдельные настоящие соединения app с точно выданными правами; привилегированный test-runner не доказывает защиту приложения. Права тестовой схемы готовятся отдельно под те же P6/§2. При проверке через разные соединения данные видимы обеим ролям: для таких транзакционных сценариев применяется TransactionTestCase/явно завершённая подготовка. Успех migrate под test-admin не доказывает доступ migrator; служебный запуск migrator отдельно проверяется при smoke первого запуска.

Сценарии приёмки первого запуска

- новая пустая среда: owner мигрирует/создаёт справочники, runtime открывает каталог/JSON, администратор сайта входит;
- положительные INSERT/UPDATE допустимых объявлений/patch/цены, изменение sources.enabled и CRUD справочников через обычный runtime; history INSERT успешен;
- под app невозможно UPDATE/DELETE/TRUNCATE старой истории, DROP/изменение владельца, DDL и SET ROLE migrator; запрещённые операции не оставляют частичных записей, проверяется F25/F15;
- проверка путей FK/функций и PUBLIC/членств; успешный прямой GRANT/REVOKE аудит дополняется SQL-проверкой поведения в тестовой БД;
- повторная подготовка/перезапуск не меняют данные, enabled, подписи/ID и пароль Django-администратора;
- pending migrations и неудачная подготовка схемы препятствуют штатному запуску. Права конкретных операций подтверждает проверка F25. TCP-проверка контейнера показывает, что Django принимает подключения.
- новый применённый migration не открывает runtime новые права на историю, а старая привилегированная роль не появляется в Django и сбор.

Сквозные проверки подготовки и прав запускаются в изолированном проекте Compose. [Команда проверки](../implementation/tests/compose.sh), [матрица приёмки](ACCEPTANCE-7.1-PROPOSAL.md)
