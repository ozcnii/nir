# Пункт 2. Рекомендуемая схема БД и контракт collection → catalog

Статус: предложение для согласования, включая описанные ниже уточнения повторов, снятия и объединения; схемы и миграции не реализованы. Основание: принятая структура A10 и функции НИР 5.1–5.5.

## 1. Предметное решение

Рекомендую `Object` как содержательную общую карточку недвижимости, `Publication` как полные факты конкретного источника и условия сделки в той же строке публикации. `Object` хранит согласованные физические характеристики, вычисленные из публикаций; это осознанная производная копия. Публикации остаются первичными сведениями. Отдельных `Offer`, «главной публикации» и записи приёма нет.

Это **предложение пересмотреть физическое размещение A4**, а не уже принятое решение: условия предложения хранятся в публикации, общая карточка содержит производные физические поля. Смысловое разделение сохраняется: объект — недвижимость, публикация — сообщение источника, предложение — текущие условия этой публикации. Продажа и аренда не объединяются в общую цену; самостоятельного жизненного цикла предложения заданием не предусмотрено.

Политика общих характеристик: среди текущих активных публикаций рассматриваются известные значения каждого нормализованного поля. Одно различное значение становится общим; несколько разных либо отсутствие известных значений дают `NULL`, то есть «единого значения нет». Неизвестное не опровергает известное, количество поддержавших источников не учитывается. Координаты рассматриваются как неразделимая пара; сопоставление кандидатов использует полные факты публикаций, а не обнулённые общие поля. Не применяются голосование, усреднение, выбор первого источника или произвольного «более надёжного». В карточке `NULL` не выводится как пустота: известные различающиеся значения показываются с источниками; отсутствие сведений обозначается отдельно. Если активных публикаций нет, общие поля пусты, сохранённые публикации доступны в карточке как неактивные.

**Конфликт не исключает объект из фильтров.** Все фильтры применяются целиком к одной активной `Publication`, затем результат объединяется по `object_id`. Общие поля `Object` не используются как ограничение такой выборки. Площадь одного источника и цена другого не образуют вымышленное подходящее предложение. Карточка в выдаче показывает условия подходящей публикации; при нескольких — самую дешёвую в том же типе сделки, валюте и периоде оплаты, с источником. При разных валютах суммы не сравниваются. Без поискового контекста показывается список предложений без одной «истинной цены».

Цена решения — пересчёт общих полей при каждом изменении фактов или активности публикации в одной транзакции. Это дополнительное состояние, которое надо поддерживать, а не способ уменьшить число таблиц. Его назначение — готовая общая карточка с явной границей достоверности. Вариант `ObjectGroup(id)` честнее, если такая карточка не нужна, но фактически возвращает отвергнутую пустую сущность и здесь не рекомендуется. Самоссылка на корневую публикацию экономит таблицу ценой искусственных ограничений корня/цепочек/удаления. Политика согласованных полей и цена производной копии остаются главным спорным решением для владельца; исходная претензия к выпадению конфликтных объектов из фильтров устранена именно запросом по публикации.

## 2. Таблицы и владельцы

Все PK — внутренние идентификаторы; FK ссылаются на PK. `Object.id` и `Publication.id` — UUID, остальные PK могут быть целыми. `?` означает допустимое отсутствие значения.

| Таблица / владелец | Поля, ключи и ограничения | Связь и назначение |
|---|---|---|
| `Source` / catalog | `id PK`, `code UNIQUE`, `name`, `enabled`, `settings JSON` | Один источник → много публикаций; настройка доступа сборщика |
| `Region` / catalog | `id PK`, `code UNIQUE`, `name` | Регион → много публикаций; управляемый справочник |
| `PropertyType` / catalog | `id PK`, `code UNIQUE`, `name` | Тип объекта → много публикаций; управляемый справочник |
| `Object` / catalog | `id PK`, `created_at`, `merged_into_id FK → Object?`, `region_id FK?`, `property_type_id FK?`, `address?`, `latitude?`, `longitude?`, `area_m2?`, `rooms?`, `floor?`, `floors_total?` | Объект 1:N публикаций; `merged_into_id` только у сохранённого старого ID после объединения; физические поля у действующего объекта |
| `Publication` / catalog | `id PK`, `source_id FK`, `external_id`, `object_id FK → Object`, `url`, `title?`, `description?`; `UNIQUE(source_id, external_id)` | Источник 1:N публикаций; объект 1:N публикаций |
| Те же `Publication`: факты | `region_id FK`, `property_type_id FK`, `address?`, `latitude?`, `longitude?`, `area_m2?`, `rooms?`, `floor?`, `floors_total?`, `extras JSON` | Полные нормализованные сведения этого источника; первичные данные для общей карточки |
| Те же `Publication`: условия | `deal_type`, `price_amount?`, `price_currency?`, `price_period?`, `deposit_amount?`, `deposit_currency?`, `commission_amount?`, `commission_currency?` | Одно текущее предложение публикации; продажа / длительная / посуточная аренда раздельны |
| Те же `Publication`: состояние | `status`, `source_published_at?`, `source_updated_at?`, `first_seen_at`, `last_seen_at`, `accepted_observed_at`, `payload_digest`, `normalization_version` | Даты источника отделены от даты наблюдения; служебные поля защищают обновление |
| Те же `Publication`: фото | `photos JSON`, `photos_observed_at?` — последний известный упорядоченный массив `{url, phash, hash_version}` и время его получения | Текущие внешние ссылки и признаки; массив заменяется при известном списке, сохраняется при недоступном, отдельных файлов и истории фото нет |
| `PriceChange` / catalog | `id PK`, `publication_id FK`, `observed_at`, `deal_type`, `amount?`, `currency?`, `period?`; `UNIQUE(publication_id, observed_at)` | Публикация 1:N реально наблюдавшихся состояний цены, включая первое |
| `CollectionRun` / collection | `id PK`, `started_at`, `finished_at?`, `status`, `stop_requested` | Запуск → много сообщений; один активный сбор по A10 |
| `CollectionMessage` / collection | `id PK`, `run_id FK`, `source_id FK?`, `external_id?`, `created_at`, `level`, `code`, `text` | Ошибки извлечения и итог приёма; не очередь сообщений и не копия ответа HTTP |

`Publication.photos` — JSON фиксированной схемы: у фото нет самостоятельных запросов или обновлений, список читается после отбора кандидатов и при успешном извлечении заменяется целиком. Отдельная `Photo` дала бы ограничения на каждую строку, но потребовала бы синхронизации списка без используемого преимущества; формат массива проверяет сервис каталога.

`Source.settings` — ограниченные параметры сборщика по известной схеме каждого источника, без паролей. `Publication.extras` — только разрешённые дополнительные признаки с именованными ключами и типами, например `building_material`, `balcony_count`, `renovation`, `seller_kind`. Неизвестные ключи отклоняются; исходная страница и произвольный EAV не сохраняются. Потребовавшийся общий фильтр получает обычное поле и миграцию, а не поиск по произвольным ключам.

Тип сделки, состояние публикации, коды ошибок и статусы хеширования — фиксированные перечисления. Отдельные таблицы нужны только для редактируемых справочников. Штатные таблицы Django auth обеспечивают авторизацию администратора.

Новая публикация связывается с существующим объектом только при уверенном результате сопоставления, иначе создаёт новый объект. Новые факты или успешно обработанные фото знакомой публикации повторно запускают сопоставление: ранее раздельные объекты могут объединиться. Неоднозначное соответствие либо существенное противоречие между членами предполагаемой группы не разрешаются цепочкой попарных совпадений: объединение откладывается. Конкретные признаки уверенности и противоречий задаются решением о matching, а возможность пересмотра связи предусмотрена уже здесь.

Простой merge в той же транзакции: заблокировать участвующие действующие `Object` в порядке ID, повторно проверить решение, оставить объект с минимальными `(created_at, id)`, перевести к нему все публикации, пересчитать общие поля. Старые строки не удаляются: их `merged_into_id` указывает прямо на оставшийся объект, производные поля очищаются. Все прежние ссылки-псевдонимы также перенаправляются прямо к нему, поэтому цепочек и циклов нет; запрос старой карточки перенаправляет на действующий ID. Старшинство выбирает лишь стабильный идентификатор, а не источник истины. Повтор merge той же группы ничего не меняет. Разделение ошибочно объединённых объектов не включено: поэтому уверенность и проверка противоречий обязательны, а отсутствие ручного исправления остаётся риском.

Объект и первая публикация создаются атомарно; пустые действующие объекты штатно не возникают. Для связей `Publication → Source`, `Publication → Object`, `PriceChange → Publication` и псевдонима `Object → Object` применяется `PROTECT`, не каскадное удаление. Снятие объявления меняет статус, а не удаляет строку. `PriceChange` — только добавление: редактирование и удаление запрещены в сервисе и админке, на уровне БД запрет `UPDATE/DELETE` обеспечивается триггером; цены существующих строк не исправляются при merge. История остаётся при своей публикации.

## 3. Значения, повторы и история

Денежная сумма — `Decimal`, не float; сумма и валюта либо обе заданы, либо обе отсутствуют. Суммы неотрицательны. Известной цене соответствует период: `total` для продажи, `month` для долгосрочной, `day` для посуточной аренды; при неизвестной цене период отсутствует. Депозит и комиссия — отдельные денежные пары. Процентная комиссия не превращается в сумму: хранится разрешённым `extras.commission_percent`, денежная пара остаётся пустой; оба способа одновременно запрещены. Нулевая сумма отличается от неизвестной.

`NULL` означает «источник не сообщает / значение неприменимо», но не «парсер сломался». Ошибка разбора известного формата — структурированная ошибка `collection`, такое объявление не отправляется на замену предыдущего. Неизвестные необязательные поля передаются явно как `null`; отсутствие обязательного ключа — ошибка контракта. Регион, тип объекта, тип сделки, идентификатор и URL необходимы для полного `upsert`; отдельное подтверждение снятия их не требует. Координаты передаются парой; площади положительны, комнатность неотрицательна, этаж может быть отрицательным.

`observed_at` назначается при получении данных, а не при записи в БД. Сравнение всегда с `accepted_observed_at`: старое наблюдение возвращает `stale` без записи; одинаковое время и содержимое — `unchanged`; одинаковое время с различным содержимым — `conflict`. Дайджест каталог считает по принятому входу, включая вид операции и состояние блока фото, без времени наблюдения. При **любом** принятом более новом наблюдении, включая `unchanged`, продвигаются `accepted_observed_at`, `last_seen_at` и дайджест. Поэтому цена 100 в t1, та же 100 в t3, затем запоздалая 200 в t2 оставляют 100, а t2 получает `stale`. Все денежные пары обновляются атомарно; повреждённая пара отклоняет `upsert`, не стирает прежнюю цену.

`PriceChange` добавляется только для `upsert`, при изменении `(deal_type, amount, currency, period)`, включая переходы к неизвестному и обратно, и при первой публикации. Неизменная цена, ошибка фото, снятие и повтор не создают строк сами по себе.

Сетевая работа заканчивается до транзакции. Каталог блокирует объект и существующую публикацию, проверяет наблюдение и атомарно применяет указанную операцию, обновляет известные блоки, историю и согласованные поля, при необходимости объединяет объекты. Уникальный ключ защищает и повторное создание; штатно одновременно работает один сбор. Сбой до commit оставляет прежнее состояние; после commit повтор распознаётся. Следующий запуск просто заново обходит источники, без брокера, `Acceptance`, сохранённого HTTP-ответа и восстановительной очереди.

Это история наблюдаемых цен, не журнал всех редакций: прежние тексты, депозит и фотографии не архивируются. `last_seen_at` само по себе не доказывает активность. Для явного снятия существует `mark_unavailable {source_code, external_id, observed_at, reason=explicit_removed}`: подтверждённая заглушка источника либо предусмотренный сборщиком однозначный ответ о снятии. Обычный 404, CAPTCHA, таймаут, ошибка парсинга или отсутствие в выдаче без такого подтверждения — ошибка сбора, не снятие. Для известной публикации операция только меняет статус, даты свежести, дайджест и общую карточку; прежние факты, фото и цена сохраняются, новая история не добавляется. Для неизвестного ключа возвращается `not_found` без создания неполной публикации. Последующий свежий `upsert` снова активирует публикацию; устаревший не активирует.

Новый внешний ID означает новую публикацию и обычное сопоставление. Повторное использование ID для другой недвижимости — ограничение сборщиков, которое нужно проверять отдельно; такое сообщение нельзя автоматически трактовать как новые факты прежнего объекта.

## 4. Фотографии и сопоставление

НИР 5.2 требует перцептивные хеши, но не подтверждает их точность на выбранных источниках. Рекомендую хранить их в `Publication.photos` как дополнительный признак, а не как уникальный ключ и не как единственное доказательство совпадения объектов. Порог и сочетание признаков относятся к следующему решению о дедупликации; наличие поля в БД не означает подтверждённую эффективность алгоритма.

`hash_version` обозначает алгоритм и версию подготовки изображения; сравниваются только совместимые версии. Элемент массива хранит `url`, `phash` и `hash_version`; при успешном расчёте хеш и версия обязательны вместе, при ошибке оба `null`. Порядок массива — порядок снимков источника. Ошибка загрузки отдельного фото записывается в журнал, но не отклоняет корректные факты объявления; такое фото не участвует в сопоставлении. Фотографии загружаются в память и удаляются после вычисления признаков. SHA-256, реестр алгоритмов и состояния обработки каждого фото не нужны текущему сценарию.

Блок фото имеет два явных состояния. `known(items)` означает полный успешно извлечённый список: он заменяет прежний целиком, включая `known([])`, который очищает фото. `unavailable` означает ошибку извлечения списка: прежний список и `photos_observed_at` сохраняются, остальные корректные факты и новая цена принимаются. Для `known` дата списка становится `observed_at`; ссылка с нескачанным изображением сохраняется с `phash=null`, старый хеш не подставляется. Ошибка снимка или списка записывается в журнал.

При `unavailable` сохранённые снимки доступны в карточке как ранее полученные, но не считаются свежими доказательствами нового наблюдения: фотосопоставление использует их только если `photos_observed_at = accepted_observed_at`; структурное сопоставление и обновление цены продолжаются. URL не доказывает неизменность содержимого. Не вводятся кеширование, отдельный повтор обработки фото или реестр версий. Внешние фото могут стать недоступны после изменения источника.

## 5. Внутренний контракт

`catalog.services.accept_publication(data) → AcceptanceResult` — обычный Python-вызов внутри монолита, не HTTP API. `AcceptanceResult` — возвращаемая структура, не таблица. Каталог не обращается к сети и не импортирует `collection`; все записи предметных данных проходят эту функцию.

Вход `operation=upsert`:

- `source_code`, `external_id`, `url`, `observed_at`, `normalization_version`;
- `title`, `description`, `source_published_at`, `source_updated_at`; `upsert` означает активное объявление;
- `region_code`, `property_type_code`, `address`, `latitude`, `longitude`, `area_m2`, `rooms`, `floor`, `floors_total`, `extras`;
- `deal_type`, `price {amount, currency, period}`, `deposit {amount, currency}`, `commission {amount, currency}`; неизвестные значения явно `null`;
- `photos = known([{url, phash, hash_version}, …]) | unavailable`; `known([])` разрешён, порядок устойчив внутри наблюдения.

Вход `operation=mark_unavailable`: только `source_code`, `external_id`, `observed_at`, `reason=explicit_removed`; полного набора фактов и фото нет. Обе операции проходят одинаковые проверки свежести и одну транзакционную границу.

Результат: `status = created | updated | unchanged | stale | conflict | rejected | not_found`, `publication_id?`, `object_id?`, `match? = new_object | matched | existing_publication`, `merged_object_ids[]`, `price_changed`, `errors[] {field, code}`. Для `rejected` идентификаторов может не быть; ошибки не записываются в предметные поля. `updated` означает изменение содержимого; повтор с новым временем и тем же содержимым возвращает `unchanged`, продвигая даты свежести и дайджест без новой цены. При merge возвращается действующий `object_id`, старые ID перечислены в `merged_object_ids`. `collection` сохраняет итог или ошибку в своём журнале; инфраструктурное исключение не маскируется под успешный результат.

## 6. Что требуется утвердить

1. Пересмотр физического A4: содержательный `Object` с согласованными физическими полями и первичные факты у `Publication`, условия в `Publication`, без таблиц `Offer` и `Acceptance`.
2. Производная копия общих физических полей с `NULL` при конфликте и показом исходных значений; общая карточка показывает происхождение расхождений, фильтрация выполняется по одной публикации с последующим объединением объектов.
3. Состав полей/таблиц, ограниченные JSON, правила неизвестного, цены, свежести, повторов и сокращённой истории; защиту связей от удаления и неизменяемость истории; переоценку и атомарное объединение объектов с сохранением старых ссылок.
4. Контракт функции приёма и место списка фото с версионированными хешами в JSON публикации как дополнительного признака; два состояния блока фото и отдельную операцию подтверждённого снятия; эффективность и пороги сопоставления остаются непроверенными.

Схема не обещает автоматического разрешения противоречий или разделения ошибочных групп. Не включены ручная модерация, архив фото, уведомления, курсы валют и воспроизведение старых HTTP-ответов.

Проверка проекта по сценариям: поздние фото могут объединить два существующих объекта без потери старых ссылок; явное снятие принимается без фактов; временный сбой списка фото сохраняет его и принимает новую цену; известный пустой список очищает его; цена 100@t1 → 100@t3 → 200@t2 остаётся 100; merge и снятие не изменяют сохранённую историю. Это прослеживание правил документа, не испытание реализации: кода и проверок источников пока нет.

Граница проверки свежести: операция снятия неизвестного ключа возвращает not_found без сохранения временного барьера. Глобальная защита от позднего старого создания неизвестного ключа не заявлена; текущий последовательный сбор не требует отдельного tombstone-журнала.
