# Пункт 2 — единый вариант связи квартиры и объявлений

Статус: показанный по прямому запросу пользователя вариант, пока не принят целиком; код/миграции не создаются. Этот документ имеет приоритет над прежними предложениями группировки. Пользователь потребовал показать properties, property_ads и связь через property_id без group_id и дальнейшей подмены схемы.

## Связь
properties(id BIGINT PRIMARY KEY).
property_ads.property_id BIGINT NOT NULL REFERENCES properties(id).
Все другие поля источника/характеристик/цены/фото находятся в property_ads по текущему предложению. property_group_id/property_group_key/group_id не существует. Отдельной главной публикации, кэша характеристик объекта и корневого объявления нет.

properties — идентичность недвижимости, не выбранная версия характеристик. Одна строка обозначает одну квартиру/комнату/дом, к ней привязаны публикации. У таблицы сейчас одна колонка; не добавлять фиктивные атрибуты ради количества. FK гарантирует существование квартиры для каждой публикации. Ошибочность алгоритмического совпадения FK сам не проверяет.

Характеристики являются утверждениями источников, поэтому хранятся в property_ads. Общая карточка выбирает объявления по property_id, показывает совпавшие значения совместно и расхождения с источниками. Фильтры применяются целиком к одной строке ad, затем DISTINCT property_id. Цена остаётся у объявления, history — у ad_id, а не у квартиры.

Пример, вымышленный: properties(id=7); property_ads(id101,property_id7,source_cian,external12345,addressСамараПримерная10,area45.20,rooms1,floor3,price_rub6800000); property_ads(id102,property_id7,source_domclick,external67890,тотжеадрес,area45.00,rooms1,floor3,price_rub6950000). В properties нет копии адреса/площади/цены. Разные площади сохранены как сведения разных площадок.

Уникальность source_code/external_id сохраняется. Сначала найденное новое объявление создаёт property либо связывается с найденным существующим property. Источник не задаёт property_id. Неуверенное совпадение не объединяет. При новых данных возможно повторное сопоставление и объединение существующих property в транзакции: переназначение ad.property_id не меняет ad.id/историю. Все операции группировки через catalog при одном писателе; после переноса всех объявлений лишняя пустая properties-строка может удаляться. Карточки открываются по стабильному ad.id, поэтому переназначение property не ломает эти ссылки; постоянные публичные ссылки на удалённые property.id не обещаны. Удаление properties с объявлениями запрещено FK. Ручных исправлений не добавляется.

Итого собственных таблиц теперь шесть: sources, regions, property_categories, properties, property_ads, price_history. Изменение затрагивает только представление принадлежности и добавление настоящей целевой записи FK; остальные проверенные поля/рубли/JSON/история/контракты остаются предложениями без группового UUID. В контракте ответа property_id вместо property_group_id. Прежние оценки схемы с UUID-меткой на этот вариант автоматически не переносятся.
