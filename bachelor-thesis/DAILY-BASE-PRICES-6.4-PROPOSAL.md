# 6.4 — базовые суточные цены: принятое решение

Статус: ПРИНЯТО владельцем17ноября2026: «Ок, принимаю цены, зафиксируй». Приняты каналы/контекст и результаты примеров. Ключи приняты отдельно. Код приложения не пишется. Ни схема price_history, ни число полей БД не меняются. Предложение основано на сохранённых первичных наблюдениях17ноября2026, не на новой сетевой проверке и не на догадках о комиссиях.

## Принятый контракт

price_history(id,ad_id,observed_at,price_rub,price_kind) хранит первую пригодную цену и последующие изменения пары (price_rub,price_kind). price_kind=listed — обычная опубликованная цена; from — опубликованный минимум «от». deal_type=day_rent хранится в ads. При unavailable строки цены нет, прежняя цена сохраняется. Неизменная пара не создаёт запись. У новой публикации без пригодной цены история пуста. Валюта только подтверждённыеRUB, без конвертации. Гости/даты проживания/комиссии отдельными полями не добавляются.

## Принятое правило

Храним опубликованный базовый тариф за сутки у конкретной публикации без выбранных дат и индивидуального расчёта проживания. Это история цены предложения, не обещание цены на любую дату и любой состав гостей. Одного названия basePrice/lowPrice недостаточно: должны быть подтверждены конкретная публикация, RUB и единица «за сутки».

1. При проектировании адаптера семейства выбирается один проверенный канал тарифа. Для партнёраЦиан — objectBasePrice.base_price с подтверждением JSON-LD «за сутки»; для Домклик24 — явная цена элемента основной выдачи с суточной подписью и ссылкой наключ. Этот выбор не пересматривается автоматически при каждом чтении. Отображаемая цена обычной выдачи/карточки без дат допустима, когда привязана к проверенному ключу. Цену не берём у соседнего объекта, рекламы, рекомендаций, итогов бронирования, залога или платежа за часть проживания.
2. Для выбранного метаданных-канала партнёраЦиан допустима базовая цена встроенных данных той же карточки, когда её сумма/валюта/суточная единица подтверждены другими явными данными страницы. Появление видимой цены само по себе не переключает этот канал. Наличие included_persons само по себе цену не запрещает. Это тариф публикации с условиями источника; расчёты доплат не выполняем и данные гостей вБДне добавляем.
3. listed ставится обычному опубликованному базовому тарифу. from — только если источник действительно обозначает цену как минимум/«от». Само имя lowPrice или отсутствие дат не доказывают минимум по всем датам и не создают from. listed также не означает фиксированную цену для любого бронирования.
4. Если отображаемая и встроенная суммы различаются, не считаем это несколькими изменениями цены. Берём только установленный по этому правилу тариф; несовместимые/необъяснимые варианты одного и того же тарифа означают price=unavailable. Не выводим процент комиссии из арифметического совпадения и не исправляем источник вычислением.
5. Способ получения и контекст тарифа должны быть одинаковыми при последующих наблюдениях. Для партнёраЦиан проверяется отсутствие дат и фиксированный контекст двух взрослых без детей/питомцев, наблюдавшийся в vuex.search; included_persons остаётся опубликованным условием конкретного базового тарифа, а не полем нашейБД. Для Домклик24 проверяется отсутствие выбранных дат и состояние поля поиска «1 гость», зафиксированное в том же снимке, что3910/за1сутки и ссылка карточки. Количество гостей карточки не подставляется вместо контекста выдачи. Адаптер открывает чистый контекст Playwright и проверяет фактическое состояние; неподтверждённые/другие параметры → price=unavailable. Ни сброспараметров, ни изменение состава гостей в UI не считаются изменением цены объявления. Если ранее использованная отображаемая цена временно исчезла, не переключаемся молча на другую метрику lowPrice/basePrice — price=unavailable. Ранее выбранный источник тарифа — фиксированное правило адаптера данного семейства, не новое поле price_history или индивидуальная настройка ads. Временная недоступность не становится изменением listed/from. Изменение канала разрешается только после отдельного подтверждения эквивалентности тарифа и контекста; до этого другой канал автоматически не продолжает историю.

По Циан включение именно базового опубликованного тарифа в listed — принятое владельцем толкование смысла истории, а не значение поля API. Оно не утверждает, что9000/5800 гарантированы для любого размещения. Название AggregateOffer/lowPrice само по себе не заменяет явную суточную подпись и значение базового тарифа.

По Домклик24 разница3910/3400 действительно наблюдалась. Причина не установлена: комиссия/наценка/разное состояние не заявляются фактами. Суточный смысл3910 подтверждён видимой подписью, у3400 только genericlowPrice. Поэтому предложение выбирает один подтверждённый канал, не минимальное число; считать две суммы доказанно разными метриками пока нельзя. Если новой проверкой обнаружится, что3910 является расчётом выбранных дат/гостей либо не базовым предложением, эта сумма не пройдёт правило; до этого нельзя заявлять такую причину как доказанный факт.

Правило требует его проверки при каждом чтении, а не полагается на default сайта навсегда.

## Пример строк истории

При первом допустимом приёме каждого примера — одна строка с существующимad_id, фактическимobserved_at и указанными суммой/listed. В этом документе не выдумываются точные время и новыеad_id. Повтор того же9000/listed ничего не добавляет. Если позже опубликован другой пригодный базовый тариф — новая строка. Если цена стала unavailable — ни нуля, ниNULLстроки; прежняя остаётся. Это проектные сценарии, не наблюдавшиеся изменения данных сайтов.

Гостиничные номера исключены принятым HOTEL-ROOMS-6.4-PROPOSAL.md. Поэтому конкретные1906598/1157449 не создают ads и price_history. Их9000/5800 остаются проверенными примерами извлечения/семантики тарифа, а не фактически сохраняемыми строками: пригоднаяцена не отменяет фильтр допустимости публикации. Схема не получает hotel/property_type. Остальные допустимые суточные публикации сохраняются по принятому правилу цены.
