Домклик и его партнёрский маршрут считаются одним источником domclick. Отдельного sources.code=domclick_sutochno не будет. Это принятое продуктовое представление источника; фактический URL сохраняет домен перехода. Авито отложен, не исключён из проекта.

## price_history — принята механика истории, политики приёма требуют уточнения

| Поле | Тип | Назначение |
|---|---|---|
| id | bigint PK | Ключ строки |
| ad_id | bigint FK → ads.id | Публикация, чья цена наблюдалась |
| observed_at | timestamptz | Момент нашего наблюдения |
| deal_type | text | sale / month_rent / day_rent |
| price_rub | numeric(16,2) NULL | Опубликованная сумма в рублях; неизвестная цена — NULL |
| price_kind | text NULL | Обычная опубликованная цена либо «от»; прежний stay_total больше не является предлагаемой ценой для этой истории |

Механика накопления истории принята. Состав ниже — текущий рабочий проект; последнее подтверждение механики не разрешает молча менять поля или политики приёма.

Удалены из схемы и контракта: check_in, check_out, adults, children, guest_count. Не переносить эти же поля в новую таблицу или JSON без решения владельца.

Оставшийся вопрос политики данных: на проверенной странице партнёра Домклик 1800 ₽ было итогом за выбранные даты и гостей, а Циан показывал «от 3000 ₽/сутки». Исключение дат и гостей не делает первый итог универсальным тарифом. Предложение для выбора: хранить в price_history только опубликованный тариф продажи/месяца/суток или цену «от»; результат расчёта проживания по выбранным условиям туда не записывать. Не принимать это предложение автоматически и не выдумывать базовый тариф, если сайт его не показал. Для такой карточки текущая пригодная цена может быть неизвестна. Условия получения пригодной посуточной цены остаются открытой частью контракта, без новой схемы бронирования.

## Принятая связь properties → ads

Прямой запрос владельца: связь квартиры и объявлений без duplicate_of_id, без таблицы только с ID и без повторных колонок физических характеристик. Принятые sources, regions, property_types и фото не меняются; Механика price_history принята; её открытые политики обсуждаются отдельно.

### properties — физическая недвижимость, характеристики в одном месте

| Поле | Тип | Смысл |
|---|---|---|
| id | bigint PK | Постоянный внутренний ключ недвижимости |
| region_id | bigint FK → regions.id | Регион |
| property_type_id | bigint FK → property_types.id | Квартира, комната или дом |
| address | text NULL | Опубликованные и согласованные части адреса |
| latitude, longitude | numeric(10,7) NULL | Согласованные координаты, если известны |
| area_m2 | numeric(12,2) NULL | Площадь предлагаемой квартиры/комнаты/дома |
| rooms | smallint NULL | Число комнат предлагаемого помещения |
| floor | smallint NULL | Этаж помещения; для целого дома NULL |
| floors_total | smallint NULL | Этажность здания |
| land_area_m2 | numeric(14,2) NULL | Участок дома |

Это содержательная таблица. Этих физических полей в ads нет. Неизвестные значения NULL; никаких произвольных усреднений. Не добавляется обязательный уникальный ключ по адресу/этажу/площади: эти признаки не гарантируют тождество квартиры.

### ads — публикация площадки

Принятые поля: id; property_id (обязательный FK → properties.id); source_code; external_id; url; market_segment; description; is_active; observed_at; photos; photos_observed_at.
Описание сохраняет текст публикации, а не вторые нормализованные колонки физических характеристик. Фото остаются у своей публикации. Сегмент новостройка/вторичка относится к предложению источника, а не безусловной вечной характеристике недвижимости.

UNIQUE(source_code,external_id) идентифицирует публикацию. properties.id не берётся с площадки. Объявление принадлежит ровно одной недвижимости; у одной недвижимости может быть несколько объявлений. price_history.ad_id → ads.id: отдельная история конкретной публикации, не общая цена квартиры.

### Реальные данные, демонстрационные внутренние ключи

properties:
| id | region_id | property_type_id | address | area_m2 | rooms | floor | floors_total |
|---|---|---|---|---|---|---|---|
| 1 | 1 | 1 | Самара, ул. Буянова, 120 | 110.00 | 3 | 12 | 20 |

latitude/longitude/land_area_m2=NULL в этом примере. regions.id=1 и property_types.id=1 — демонстрационные ссылки на уже принятые справочники, означающие «Самарская область» и «Квартира».

ads:
| id | property_id | source_code | external_id |
|---|---|---|---|
| 101 | 1 | cian | 333842107 |
| 102 | 1 | domclick | sale__flat__2080269220 |

У строк собственные реальные url, description и photos; собственные observed_at и состояние. У Циан market_segment=resale; у Домклик отдельная явная метка не подтверждена, поэтому NULL. Фото и состояние не объединяются в искусственную общую публикацию.

price_history в примере: ad_id=101 и ad_id=102 имеют собственные sale/24999000.00/обычная опубликованная цена. Это демонстрация будущей записи по проверенным страницам, не реально работающая БД.

### Ограничение этой модели

properties хранит один согласованный набор физических характеристик, а не отдельные показания площадок. В контрольной паре структурные поля совпадают. Если нормализованные характеристики разных источников расходятся, эта схема не сохраняет оба значения одного поля по отдельности. Тексты источников остаются в description, но не являются полноценной структурированной историей физических характеристик.

Нельзя автоматически обещать одновременно один экземпляр каждого физического поля и сохранение всех раздельных нормализованных показаний источников. Правило выбора значения/обновления properties при расхождении требуется отдельно согласовать; оно этим предложением не принято. Молча выбирать первый источник, усреднять или затирать конфликт запрещено. Не вводится ручная проверка/merge/split.

### Статус

Приняты properties и ads.property_id → properties.id с составом полей выше. duplicate_of_id, дополнительные group_id и самоссылка на корневое объявление отсутствуют. Способ хранения раздельных версий характеристик не добавлен. Механика price_history принята, её политики приёма ещё требуют уточнения.

## Принятая механика price_history

Предыдущий пример показывал только начальное состояние по каждой публикации и не демонстрировал накопление истории. В реальной предлагаемой таблице каждая строка — цена конкретного объявления, увиденная в определённый момент observed_at; одному ad_id соответствует несколько строк.

Условный пример механизма (это не новые реальные наблюдения площадок):
| id | ad_id | observed_at | price_rub | deal_type | price_kind |
|---|---|---|---|---|---|
| 1 | 101 | T1: первое наблюдение | 24999000.00 | sale | listed |
| 2 | 101 | T2: наблюдение после изменения | 24500000.00 | sale | listed |

T1/T2 обозначают разные моменты времени; в БД поле содержит конкретный timestamptz. Первая строка не перезаписывается второй. Если при следующем сборе цена остаётся24500000, новая строка по предлагаемому правилу не создаётся. Если затем цена возвращается24999000, создаётся третья строка с новым observed_at. Текущая цена читается из последней строки. У другого объявления той же квартиры своя история по его ad_id.
Даты проживания и гости здесь отсутствуют. observed_at — время наблюдения программы, а не дата заезда или заявленная дата изменения на сайте.
