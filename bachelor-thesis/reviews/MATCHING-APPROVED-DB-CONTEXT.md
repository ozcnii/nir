# Пункт 2: схема БД и контракт приёма данных

Обновлено: 17 ноября 2026. Реализация, SQL и миграции не создаются.
Документ заменяет прежний рабочий текст этого файла. Срез содержит только принятую схему и контракт.

## Статус решений

**Принято:** sources, regions, property_types; содержательная properties; ads.property_id → properties.id без копии физических колонок в ads; фото по URL и производные без постоянных файлов; отдельная история публикации; последняя известная цена; отсутствие гостей/дат проживания; единый domclick; повторный приём обновляет публикацию без создания копии.

**Новое прямое решение владельца:** deal_type хранится только в ads, из price_history удаляется. Следовательно, история сравнивает (price_rub, price_kind), не тройку с deal_type.

**Пункт 2 закрыт 17 ноября 2026 прямым подтверждением владельца. Приняты P1 и технический контракт P2–P8.** Это завершённое проектирование схемы/контракта, не реализация.

Авито отложен. Достоверность алгоритма сопоставления, его признаки/пороги, pHash, реализация адаптеров, UI и runner — следующие этапы, не условия готовности этого документа как проекта. Невозможность угадать все реальные совпадения принята как ограничение.

## 1. Шесть собственных таблиц

Штатные таблицы Django auth/admin в этот перечень не включены. PK — первичный ключ, FK — ссылка на другую таблицу. Все поля обязательны, кроме явно отмеченных NULL. ID bigint создаёт БД. Время — timestamptz в UTC; decimal/numeric — точные числа.

### sources — источники

| Поле | Тип / ограничение | Назначение |
|---|---|---|
| code | text PK | cian, domclick, avito — внутренние коды поддержанных сборщиков |
| enabled | boolean | Участие источника в новых запусках |

Домклик и его партнёрский маршрут имеют один code=domclick. Отключение сбора не удаляет уже собранные публикации и историю. Вторых id/name, runtime settings, timeout и дополнительных источников не добавляется.

### regions — регионы

| Поле | Тип / ограничение | Назначение |
|---|---|---|
| id | bigint PK | Внутренняя стабильная ссылка |
| name | text UNIQUE, непустое | Название региона |

Текущая семантика — субъект РФ. Город/район остаются частями address. Название можно изменить без изменения ID. Универсальные внешние mapping-таблицы не вводятся.

### property_types — физические виды

| Поле | Тип / ограничение | Назначение |
|---|---|---|
| id | bigint PK | Стабильная ссылка |
| name | text UNIQUE, непустое | Квартира, комната, дом |

Переименование не меняет программный смысл поддержанного вида. Добавление неподдержанного вида в справочник само по себе не создаёт парсер нового вида. Новостройка/вторичка относится к market_segment публикации.

### properties — физическая недвижимость

| Поле | Тип / ограничение | Назначение |
|---|---|---|
| id | bigint PK | Собственный ключ квартиры/комнаты/дома |
| region_id | bigint FK → regions.id | Регион |
| property_type_id | bigint FK → property_types.id | Физический вид |
| address | text NULL | Нормализованные опубликованные части адреса |
| latitude, longitude | numeric(10,7) NULL | Опубликованные координаты; обе известны либо обе NULL |
| area_m2 | numeric(12,2) NULL | Площадь предлагаемой квартиры, комнаты или дома |
| rooms | smallint NULL | Число комнат предлагаемого помещения; 0 только при явной студии |
| floor | smallint NULL | Этаж помещения, NULL для целого дома |
| floors_total | smallint NULL | Этажность здания |
| land_area_m2 | numeric(14,2) NULL | Площадь участка дома |

Площадь комнаты не заменяется площадью всей квартиры. Спальни дома не превращаются в число комнат без такого поля источника. Сотки переводятся в м². Номер квартиры/подъезд, если опубликованы, не теряются из address. Неизвестное не заменяется нулём или центром города.

Характеристики хранятся здесь в единственном нормализованном экземпляре. Несколько разных показаний площадок в отдельных колонках или JSON не архивируются. Тексты источников остаются в ads.description. UNIQUE по адресу/этажу/площади нет: совпадение этих признаков не гарантирует одну квартиру.

### ads — публикации

| Поле | Тип / ограничение | Назначение |
|---|---|---|
| id | bigint PK | Внутренний ключ публикации |
| property_id | bigint FK → properties.id | Ровно одна физическая недвижимость |
| source_code | text FK → sources.code | Источник |
| external_id | text, непустое | Стабильный ключ публикации внутри источника |
| url | text, непустое | Фактическая ссылка площадки |
| deal_type | text: sale/month_rent/day_rent | Тип сделки, известный независимо от наличия цены |
| market_segment | text NULL: resale/new_build | Явно установленная вторичка/новостройка |
| description | text NULL | Описание и опубликованные условия |
| is_active | boolean | Последнее подтверждённое состояние |
| observed_at | timestamptz | Время последнего принятого снимка публикации |
| photos | jsonb array | Последний известный список фото и производных |
| photos_observed_at | timestamptz NULL | Когда был получен именно этот список |

UNIQUE(source_code, external_id). Физических колонок properties в ads нет. duplicate_of_id, group_id, отдельного корневого объявления нет.

Элемент photos имеет фиксированную форму: url; phash; hash_version. URL обязателен. Хеш и версия либо оба NULL, либо оба заданы. Алгоритм/длина/пороги хеша определяются на следующем этапе; произвольный хеш не выдумывается. Файлы изображений в БД/на диск не сохраняются.

### price_history — история опубликованной цены

| Поле | Тип / ограничение | Назначение |
|---|---|---|
| id | bigint PK | Ключ состояния |
| ad_id | bigint FK → ads.id | История конкретной публикации |
| observed_at | timestamptz | Когда наша программа увидела это состояние |
| price_rub | numeric(16,2) | Пригодная опубликованная сумма в рублях |
| price_kind | text: listed/from | Обычная опубликованная цена либо минимум «от» |

deal_type здесь отсутствует по прямому решению владельца. Нет дат проживания и полей гостей. Нет копии текущей суммы в ads.

Первая пригодная цена и изменение хотя бы одного из (price_rub,price_kind) создают новую строку; старые не перезаписываются. Возврат к прежней сумме создаёт очередную строку. Неизменное состояние не добавляет строку. UNIQUE(ad_id,observed_at).

Нет пригодной новой цены — история не меняется. Нет ни одной цены — история пуста. Последняя известная цена читается из последней строки по observed_at; это не обещание свежести тарифа. Время строки — момент записи состояния, а не дата последней проверки и не заявленная дата изменения на сайте.

## 2. Принятый контракт P1–P8

### P1. Одна публикация имеет один тип сделки

Раз deal_type хранится только в ads, принято не менять его у уже сохранённой публикации с тем же (source_code,external_id). Иначе старые миллионы продажи могли бы быть прочитаны как месячная арендная плата.

Несовместимый повтор с другим deal_type возвращает conflict без изменения БД; reason=deal_type_changed. В причине и журнале указываются прежнее/новое deal_type и объяснение защиты: сохранённая цена не должна получить другой тип сделки задним числом. Разные публикации продажи/аренды одной квартиры нормально имеют разные ads с общим property_id. Смена типа в отдельном новом ключе создаёт новую ads. Если понадобится перенос типа внутри того же ключа, это отдельное новое решение; история не переинтерпретируется молча.

Это принятое правило защиты смысла истории при изменении ads.deal_type у того же внешнего ключа. Оно не утверждает, что сайт не может менять тип сделки, и не означает произвольное отклонение любых обновлений. Нового аналога deal_type в price_history не вводим.

### P2. Стабильный внешний ключ из реально проверенных маршрутов

Принятый внутренний формат external_id:
- cian: опубликованный числовой ID строкой, например 333842107;
- domclick, основной маршрут: путь /card/sale__flat__2080269220;
- domclick, партнёрский маршрут: путь /detail/2252883.

Пути взяты из реально открытых URL. Формат ключа — наше нормализующее правило, не якобы полученное поле API. У domclick пути разных семейств не смешиваются, source остаётся единым. Региональный поддомен основного сайта, UTM, даты и гости в query не меняют ключ. url сохраняет реальную ссылку; query выбранного проживания не становится идентичностью объявления. Нормализация обрабатывает trailing slash однозначно.

Формат Авито здесь не выдумывается: его адаптер при отдельной проверке обязан обеспечить этот же контракт стабильного внешнего ключа.

### P3. Вход collection → catalog

Один вход описывает одну конкретную публикацию, не сводную планировку, диапазон этажей или набор квартир.

Обязательные данные конверта: source_code, external_id, observed_at, state. Для полученной карточки также url и deal_type. state — временное поле сообщения, не новая колонка БД:
- active: получена действующая карточка;
- removed: получена явная отметка снятия;
- unavailable: страницу получить/разобрать как карточку не удалось.

active содержит нормализованные значения будущих properties и полей публикации; для каждого optional поля передаётся значение либо NULL. Ошибка разбора структурного scalar-поля отклоняет весь active-снимок как rejected, а не заменяет поле NULL. Статусы price/photos являются явно описанными исключениями частичного получения. Если обязательные source/key/type/region/property_type не определены, снимок rejected, он не создаёт пустую недвижимость.

price — часть сообщения, не таблица:
- known: price_rub, price_kind, currency=RUB. Сумма имеет смысл продажи целиком/месяца/суток согласно deal_type;
- unavailable: пригодную цену не получили, не разобрали либо опубликованная сумма является только расчётом выбранного проживания. Историю не меняем; диагностическая причина идёт в журнал.

Конвертации валют нет. Неподтверждённые рубли и произвольное первое число страницы не принимаются. Залог, комиссия, ипотечный платёж, цена за м², предоплата/остаток не подменяют стоимость предложения.

photos:
- known с полным списком; known=[] означает достоверно пустой список и очищает прежний;
- unavailable: список не получен, прежние photos/photos_observed_at сохраняются.
Если список известен, но байты одного фото не загрузились, сохраняется его URL с NULL hash/версией. Старый хеш того же URL не выдаётся за заново вычисленный.

Временные state/status/reason не являются скрытым JSON-хранилищем исходных характеристик в БД. collection не передаёт ORM-модели, не выбирает property_id и не пишет таблицы. Сеть/фото в памяти выполняются в collection до транзакции каталога.

### P4. Повтор, снятие и ошибка

- active с новым временем обновляет существующую ads, а не создаёт копию. observed_at продвигается даже при неизменной цене. Фото и цена обновляются по своим статусам.
- removed для известного ключа устанавливает is_active=false и обновляет observed_at, сохраняя характеристики, связи, фото и историю.
- removed для неизвестного ключа возвращает not_found, не создавая строку без физической недвижимости.
- unavailable только журналируется: не выключает объявление, не стирает цену/фото, не продвигает observed_at принятого снимка.
- более новое active после снятия восстанавливает is_active=true в той же ads.
- исчезновение из выдачи или HTTP-ошибка сами по себе не removed.

Минимальный режим collection — один активный обход и не более одного запроса одного ключа в работе; каждый результат сразу передаётся в catalog. Отдельной очереди повторной доставки старых пакетов нет. Это принятый простой режим исполнения, не новый координатор.

Для неизвестного снятого ключа временная граница не хранится. Гарантию отсечения старых событий даём только по уже существующим ads; не обещаем универсальный event store без его проектирования.

### P5. Порядок и атомарность

Сначала валидируется конверт (source/key/observed_at/state). Для существующей ads сначала проверяется время, затем совместимость deal_type и прочие данные. Старый несовместимый снимок возвращает stale, а не conflict; равный — ignored. Невалидный конверт не допускает сравнения и возвращает rejected.

Для существующей ads:
- входное observed_at меньше сохранённого — stale, изменений нет;
- равно сохранённому — повтор/ignored, изменений нет; при одинаковом времени действует первый принятый снимок, не обещается последующее обогащение;
- больше — новый снимок.

Время берётся в начале получения карточки; сравнивается время наблюдения, а не дата публикации источника. Такой порядок не доказывает свежесть кеша сайта.

Операция приёма выполняется одной транзакцией: решение по properties, ads и условная строка цены либо сохраняются целиком, либо целиком откатываются. Чтобы две операции одновременно не добавили одну новую цену/публикацию, используется общий транзакционный advisory lock PostgreSQL на запись каталога. Сеть внутри блокировки отсутствует. Блокировка снимается концом транзакции. Все писатели каталога используют один путь приёма.

Это простой последовательный приём внутри БД, без брокера, lock-таблицы или нового сервиса. Его фактическая производительность пока не измерена.

### P6. Целостность и чтение

FK защищают все ссылки; удаление используемых источников/справочников/недвижимости/публикаций запрещено. Снятие — изменение состояния, не удаление. История неизменяема: штатные UPDATE/DELETE отсутствуют, DB-права/ограничения должны запрещать их роли приложения.

Требования:
- source/key/url/name — непустые строки; ключ публикации и основные FK обязательны;
- deal_type и price_kind принадлежат перечисленным значениям; market_segment либо поддержанное значение, либо NULL;
- пригодная цена ≥0; площадь/участок >0; rooms≥0; floors_total>0;
- ноль не используется вместо неизвестного; явная опубликованная нулевая сумма не подменяет отсутствие;
- latitude/longitude известны парой, диапазоны [-90,90]/[-180,180];
- floor может быть нулевым/отрицательным; при известных floor/floors_total этаж не превышает этажность;
- photos — массив фиксированных элементов; photos_observed_at=NULL означает неизвестный список и photos=[]; известный пустой список имеет время; photos_observed_at≤ads.observed_at.

PK и UNIQUE создают свои индексы; не дублируем их. Нужны индексы ads(property_id) и свойств по региону/виду. UNIQUE(source_code,external_id) покрывает source_code; UNIQUE(ad_id,observed_at) — поиск истории и последней цены. Физические индексы фильтров уточняются по запросам при реализации, без обещания оптимизации всех комбинаций.

Чтение JSON: неизвестный scalar — null, пустая история/фото — [], отсутствующая последняя цена — null. Наличие [] фото при NULL photos_observed_at означает «не получены», а не «площадка не содержит фото». Денежные/площадные decimal передаются строками без потери точности. Время — ISO8601 с UTC.

Карточка недвижимости содержит properties и массив ads; у каждой публикации source_code/url/deal_type/состояние/свои фото/собственная последняя известная цена/история. История отсортирована по observed_at. Чтение карточки выполняется в одном согласованном снимке БД, не смешивает половины разных операций приёма.

Поиск по умолчанию использует активные ads. Тип сделки берётся из ads независимо от цены. Числовой фильтр цены не пропускает объявление без известной цены. Остальные условия объявления и его цена проверяются совместно по одной ads, потом сворачиваются по property_id. Характеристики берутся из properties. Снятая публикация остаётся доступна в карточке/истории с отметкой состояния.

### P7. Интерфейс с алгоритмом сопоставления без выбора его порогов

При уже известном (source_code,external_id) обновляется та же ads с прежним property_id: повтор не запускает поиск другого объекта и не перепривязывает публикацию. При необходимости этап согласования характеристик может вернуть явный patch для этого же property_id.

Для новой публикации внутри catalog сопоставление возвращает:
- ссылку на существующий property_id; либо
- решение создать properties с конкретным нормализованным набором характеристик.

Для существующей properties автоматическое копирование физических полей из очередного объявления запрещено. Если этап разрешения расхождений явно вернул допустимый property_patch, применяются только перечисленные им поля после той же валидации; без patch общие характеристики остаются прежними. Неопределённые значения не стирают известные сами по себе.

Решение и patch вычисляются на текущих данных в той же сериализованной операции. Правила уверенности, условия patch и выбор источника при расхождении относятся к следующему алгоритмическому этапу; запись не выбирает их самостоятельно. Неподтверждённое совпадение не вынуждает объединение. Разные объявления одной недвижимости сохраняются разными ads. Ручного merge/split не добавляется.

Это интерфейс между двумя частями catalog, не ещё один вход collection и не новая таблица/папка.

### P8. Выход приёма

Результат содержит outcome, ad_id/property_id при наличии, price_changed и причину отказа при наличии.
outcome: created/updated/unchanged/stale/ignored/conflict/rejected/not_found/unavailable.
Статусы принадлежат ответу операции и журналу, не новой таблице логов. updated означает изменение содержательных полей/состояния, цены, состава/хешей фото или разрешённого property_patch. unchanged означает то же содержание с продвижением только observed_at и/или времени подтверждения неизменного списка фото; это не отменяет сохранение этих времён.
Ошибка всей транзакции не возвращается как успешное частичное сохранение.

## 4. Контрольные сценарии проекта

Это логические ожидаемые результаты, не выполненные программные тесты.
- Первый приём: одна properties и ads, цена только если пригодна.
- Первый приём без цены: ads.deal_type известен, история[], фильтр сделки работает.
- Повтор по тому же ключу: та же ads/property_id, никаких копий.
- Изменение суммы или listed/from: новая строка; сумма вернулась к старой — ещё одна строка.
- Изменение deal_type у того же ключа: принятый P1 возвращает conflict с reason=deal_type_changed, история не меняет единицы задним числом.
- Цена unavailable: прежняя последняя известная сохраняется; неизвестная первая не становитсяNULL-строкой.
- Фото known=[] очищаются; unavailable сохраняет; ошибка байтов не создаёт выдуманный hash.
- Явное снятие сохраняет историю и связи; ошибка страницы не выключает публикацию.
- Старый/равный снимок не откатывает новое состояние.
- Конкурентный одинаковый приём сериализуется, оставляет одну публикацию и одно изменение цены; ошибка до commit не оставляет частичных записей.
- Решение matching явно указывает существующую/новую недвижимость; физические поля не переносятся автоматически между публикациями.
