## 1. Исходная граница проекта

Текущие ограничения: sources(code PK, enabled), regions(id PK, name UNIQUE), property_types(id PK, name UNIQUE). Новые колонки и таблицы соответствий не рассматриваются. Принятый 5.4 сохраняет добавление, переименование и удаление неиспользуемых справочников при отсутствии активного сбора; переименование — изменение подписи, а не предметного смысла. Код источника выбирает поддержанный адаптер; запись источника не создаёт реализацию адаптера. ## 2. Django 5.2: подтверждённые механизмы

| Вопрос | Подтверждённый факт |
| --- | --- |
| Автоматические начальные данные | Django документирует data migration как способ автоматического наполнения при миграциях. Fixtures требуют отдельной загрузки; повторный loaddata повторно загружает значения и может затереть последующие изменения. Это не безопасная безусловная команда восстановления пользовательских справочников. [Initial data](https://docs.djangoproject.com/en/5.2/howto/initial-data/) |
| Исторические модели | RunPython работает с реестром моделей в состоянии соответствующей миграции. Нужны исторические модели через переданный apps; прямой импорт текущих моделей способен сломать воспроизведение старых миграций. Исторические модели не имеют пользовательских методов save/конструкторов/экземплярных методов. [Migrations: historical models](https://docs.djangoproject.com/en/5.2/topics/migrations/#historical-models), [RunPython](https://docs.djangoproject.com/en/5.2/ref/migration-operations/#runpython) |
| Вставка без обновления | get_or_create ищет по kwargs и применяет defaults при создании; существующий результат возвращает без применения defaults. Атомарность относительно гонки предполагает ограничение уникальности используемых ключей в БД. При ручном PK конфликт вставки может дать IntegrityError. [QuerySet API](https://docs.djangoproject.com/en/5.2/ref/models/querysets/#get-or-create) |
| Именованные числовые значения | IntegerChoices позволяет дать имена целочисленным значениям. choices предназначен для относительно статичных вариантов; для динамических данных Django предлагает таблицу с ForeignKey. Поэтому кодовое перечисление не обязано заменять редактируемую таблицу или ограничивать её допустимые строки. [Field choices](https://docs.djangoproject.com/en/5.2/ref/models/fields/#choices), [Enumeration types](https://docs.djangoproject.com/en/5.2/ref/models/fields/#enumeration-types) |
| Явная служебная операция | Проект может зарегистрировать собственную manage.py-команду через management/commands и BaseCommand. Документация подтверждает механизм; название и политика восстановления справочников — решение проекта. [Custom management commands](https://docs.djangoproject.com/en/5.2/howto/custom-management-commands/) |
| Явные ID и последовательность PostgreSQL | Ручная вставка значения автоинкрементного PK не двигает его последовательность. Позднейшая обычная вставка может столкнуться с уже существующим ключом; документация требует согласовать последовательность и указывает sqlsequencereset как генератор соответствующего SQL. [Manually specifying primary keys](https://docs.djangoproject.com/en/5.2/ref/databases/#manually-specifying-values-of-auto-incrementing-primary-keys) |

Проектный вывод: штатная data migration подходит для первоначального снимка; повторный restart не должен восстанавливать удалённое. Уже применённая миграция не становится командой ремонта отсутствующей строки. Восстановление может быть отдельной явной management-командой под migrator. Сам Django не выбирает такую политику за проект.

Для воспроизводимости рекомендуется хранить снимок seed непосредственно в исторической миграции: зависимость старой миграции от изменяемого runtime-реестра привела бы к изменению результата новой установки после редактирования реестра. Это инженерное следствие исторического исполнения, а не требование Django запретить любые импорты. Runtime может использовать один текущий кодовый реестр; миграция хранит его зафиксированную версию.

## 4. Следствия для привязки по ID — рекомендации, не принятый контракт

Возможен один текущий кодовый реестр известных внутренних ID и их смыслов. Именованные константы либо перечисление позволяют не рассеивать числа по адаптерам. Редактируемые name остаются подписями из БД. Реестр не требует добавления колонок или таблицы соответствий; конкретный формат, значения и набор поддержанных видов ещё выбираются.

Внутренний ID не равен native ID площадки или коду ФНС. Назначение чисел 1/2/3 само по себе не обеспечивает правильный маршрут. Преобразование внутреннего ID в параметры площадки относится к существующему адаптеру и подтверждается по каждому реально поддержанному маршруту. Этот документ не устанавливает и не придумывает внешние идентификаторы.

Для seed и восстановления важны разные случаи:

| Состояние | Безопасное следствие предлагаемой политики |
| --- | --- |
| Строки по ожидаемому внутреннему ID нет, начальная подпись свободна | Можно создать строку с этим ID, если реестр и его пространство ключей предварительно согласованы. |
| Строка с известным происхождением по ID есть, подпись пользователь изменил | Оставить подпись. Поиск только по прежнему name ошибочно принял бы её за отсутствующую. |
| name уже занят другим ID | Конфликт: не переносить строку на нужный PK, не переписывать FK и не сливать записи. Сообщить оба идентификатора; требуется отдельное предметное решение. |
| Ожидаемый ID занят строкой неизвестного происхождения | Схема id/name не доказывает её смысл. Нельзя автоматически объявить её нужным видом только по совпадению числа или «исправить» подпись. Требуется явное разрешение исходного конфликта. |
| Пользователь удалил неиспользуемую поддержанную строку | Обычный restart её не возвращает. Если выбрана явная команда восстановления, она создаёт отсутствующий известный ID, а не дублирует значение с новым ID. |
| Пользователь добавил запись с новым ID | Запись остаётся допустимой записью справочника; поддержка сбора не возникает из её подписи. Неподдержанная область отклоняется существующей проверкой запуска. |

get_or_create по PK с name в defaults подходит для ветки создания без обновления уже известной строки; это не полноценная проверка всех конфликтов таблицы. Поиск по сочетанию id/name также не решает задачу: изменённая подпись превратит существующий PK в конфликт новой вставки. update_or_create с пользовательским name/enabled в обновляемых значениях не соответствует требованию сохранения правок.

Заранее необходимо согласовать пространство ID для добавляемых пользователем строк и известных seed-значений, включая будущие пополнения. Одного перемещения sequence выше текущего максимума недостаточно, чтобы навсегда зарезервировать ещё не назначенные будущие ID. Если зарезервированы только 1/2/3, следующая выдача не должна повторно использовать эти ключи после удаления всех трёх; служебный расчёт учитывает и зарезервированный набор. При существующих пользовательских строках последовательность нельзя понизить ниже занятого диапазона. Эти операции выполняет migrator, без расширения прав app на setval.

Резервирование стабильного смысла ID не равно запрету удаления строки. Сохранение CRUD требует различать удалённую строку и возможность позднее восстановить прежний поддержанный смысл. При ручной вставке произвольных PK в обход согласованного пути гарантии этой политики не доказаны.

Для sources ключом восстановления служит code: начальный enabled относится только к создаваемой строке, существующий флаг сохраняется. Само включение источников в первом seed и исходные значения флагов требуют согласования с фактической готовностью адаптеров; факт наличия кода не доказывает доступность источника.

Восстановление через migrator, если оно будет выбрано, не обходит принятый запрет удаления/согласованность со сбором. Для изменения справочников во время служебного обслуживания нужна область без активного сбора; работающий runner не должен получить молча изменённую область.

## 5. Что остаётся выбрать и проверить при отдельной реализации

Открыты: содержимое первоначального набора видов и sources.enabled; числовая схема внутренних ID; полный региональный seed по выбранному первичному перечню; резервирование ключей при пользовательском CRUD; точное поведение явного восстановления и сообщение конфликтов. Никакая политика этим исследованием не выбрана.

Минимальные будущие проверки должны закрыть конкретные риски: новая установка получает выбранный снимок; повторный migrate/restart сохраняет изменённые подписи и enabled; разрешённое удаление не отменяется restart; явное восстановление не меняет существующие ID/FK/подписи/флаги; конфликт уникального имени и занятого ID не вызывает remap; обычное добавление после seed/удаления не сталкивается с зарезервированным PK. Маршруты источников требуют самостоятельной фактической проверки выбранных сочетаний, не проверки одного перечня регионов.
