# 8.3 — ответственность модулей и устройство тестов: проверка источников

Проверено 18 ноября 2026. Исследовательская записка для углубления НЕ ПРИНЯТОГО предложения 8.3. Это проверка документации и принятых проектных контрактов, не испытания приложения. Код, конфигурации, зависимости и действующие инструкции не создавались. Django 5.2 — версия документации, а не согласованная runtime-версия. URL Python `/3/` и Playwright обновляются; возможности нужно сверить с выбранными версиями перед реализацией.

## 2. Что уже принято в проекте и имеет приоритет

Основания: [принятая структура](../INDEPENDENT-STRUCTURE.md), [контракт БД P3–P8](../DB-POINT2-VERIFIED-DRAFT.md), [принятая приёмка 7.1](../ACCEPTANCE-7.1-PROPOSAL.md). Это источники требований проекта, а не внешние рекомендации.

- Два Django-приложения сохранены. collection извлекает и нормализует данные, catalog принимает P3, сопоставляет и сохраняет результат. Сеть выполняется до транзакции каталога; catalog не зависит от collection.
- Более поздний P3 прямо уточняет: collection не передаёт ORM-модели, не выбирает property_id и не пишет таблицы. Запрет любого чтения ORM из collection дословно не принят. Старое дерево collection/models.py с запуском и журналом не разрешает возвращать собственные таблицы журналов. P8 прямо определяет outcome как ответ операции/журнал, не новую таблицу.
- Один вход — одна публикация. active/removed/unavailable, price/photos known/unavailable, NULL, ноль и ошибка разбора различаются по P3. Внешний адаптер не решает идентичность properties.
- P5/P7 требуют решений matching/разрешённого property_patch по текущим данным внутри той же сериализованной операции catalog. Запрет сети у matching не означает запрета читать необходимые текущие данные каталога. Нельзя вынести окончательное решение за транзакционную границу ради «чистого слоя».
- P6 задаёт единый согласованный снимок чтения и совместную проверку условий одной ads; HTML/JSON используют общий путь queries. История цены сравнивает price_rub/price_kind; deal_type хранится в ads.
- 7.1 — матрица F01–F25 и применимых ветвей, а не уже выполненные тесты. Реальные проходы источников, UI и состояние БД нельзя заменить зелёными локальными fixtures.

## 3. Предлагаемые обязательные правила 8.3

Следующие формулировки — рекомендации на согласование, не новое принятое устройство приложения.

| Место | Обязанность и граница |
|---|---|
| collectors / normalization | Извлечь и нормализовать в P3; не обращаться к catalog ORM для записи/назначения property_id; не угадывать цену, единицы, неизвестные поля и снятие. |
| runner | Управлять последовательным обходом и его жизненным циклом по принятому 4.3; передавать результаты в единственный приём catalog; не дублировать сохранение и matching. Новая детализация на согласование: получать параметры через публичную queries-функцию простыми данными; сборщики не используют ORM. Это строже дословного P3, а не уже принятый запрет любого чтения ORM. Точную сигнатуру сейчас не вводить. |
| catalog.services | Оркестрировать существующий сценарий: валидировать P3 в согласованном порядке, учитывать stale/ignored, запускать matching и допустимый patch, атомарно сохранять результат/историю, возвращать P8. Все писатели пользуются одним путём. |
| catalog.matching | Сопоставлять по принятым правилам и текущим данным; не обращаться к внешним площадкам; не менять физическую идентичность повтора и не придумывать ручной merge/split. Новая детализация на согласование: queries получает кандидатов, matching выполняет сравнение переданных данных без ORM; services сохраняет всю последовательность внутри принятой сериализованной операции. Чистота сравнения — предлагаемая конкретизация, не дословный P7. Решение не дублируется в views/admin/collectors. |
| catalog.models / queries | Модели описывают согласованные данные/инварианты и уместное поведение записи; queries объединяет принятые выборки HTML/JSON. Не создавать Repository только для обёртывания QuerySet. |
| views / admin / management command | Проверить транспортный ввод и права, вызвать существующий сценарий, отобразить результат. Не копировать сопоставление, правила изменения цены и транзакционный приём. Простая обработка формы или чтение ORM не запрещаются абстрактным требованием «тонкого слоя». |

Обязательны направление зависимостей и единое место предметного правила. Не обязательны дополнительная папка на каждый слой, базовый сервис, интерфейс на каждую функцию и независимая от Django модель предметной области. Новый механизм обосновывается конкретным повтором/риском, который не закрывает существующий аналог.

## 4. Предлагаемые правила разработки тестов

1. Имя теста описывает условие и наблюдаемый исход. AAA читается как «исходное состояние — действие — последствия». Один тест проверяет один связный сценарий; последствия могут включать несколько assert: результат операции, прежний property_id, число ads, сохранность history и observed_at. Обязательное деление на три комментария не нужно, если структура ясна.
2. Arrange содержит минимальные данные, существенные для сценария. Общий setUp/setUpTestData хранит только общий понятный контекст. Разные состояния не маскируются огромной универсальной фабрикой. Фактические сохранённые страницы имеют происхождение/версию; синтетические случаи так и помечены. Секреты в fixtures не входят.
3. Независимые ветви имеют самостоятельное состояние. Для однотипных входов допустим subTest с понятными параметрами; перед каждым изменяющим вариантом восстановить нужное исходное состояние. Для проверки последовательной истории допустима явно заданная цепочка наблюдений, потому что порядок и накопление — предмет сценария F11.
4. Unit-проверки нормализации и правил используют контролируемый ввод без живой сети. Подменять внешнюю границу там, где код ищет имя; не подменять исследуемый алгоритм его ожидаемым ответом. Проверка конкретного числа вызовов оправдана, когда это сам контракт, например отсутствие повторного запроса после остановки.
5. Сохранение, ограничения, запросы и HTML/JSON проверяются с настоящим ORM/тестовой БД. Commit/rollback, advisory lock и конкуренция F15/F22 требуют управляемых отдельных операций/соединений и подходящего TransactionTestCase на PostgreSQL; SQLite и замок-двойник не предъявляются как это доказательство. Ограничения роли приложения F25 проверяются именно с её правами, а не только привилегированным тестовым пользователем.
6. Права и прямые POST проверяются серверным Client; для доказательства CSRF отдельно включить enforce_csrf_checks и проверить допустимый и недопустимый запрос. Вход в браузере и Client не считаются взаимозаменяемыми доказательствами.
7. Браузерные сценарии проверяют действия пользователя, переходы и видимые состояния. Независимые контексты и подготовка серверных данных исключают зависимость от предыдущего теста. Предпочтительны локаторы по роли/имени/label и expect состояния; sleep не заменяет условие окончания. Браузер и сервер закрываются владельцем проверки даже при ошибке. Использование Python library API не требует принятия pytest.
8. Для исправленного дефекта воспроизвести именно нарушенный контракт и добавить подходящий регрессионный сценарий. Ожидание берётся из согласованной спецификации, не вычисляется копией алгоритма. Успешные, отрицательные и граничные варианты выбираются по риску и ветвям F01–F25, без тестов на каждую строку реализации.
9. Результат привязан к ID/ветви 7.1: вход, исходное состояние, ожидаемое, фактическое, доказательство и статус. Fixture-проверка, локальная интеграция, живой источник и браузерный проход обозначаются отдельно. Недоступный источник/непроверенная ветвь остаются непроверенными; покрытия строк недостаточно для принятия сценария.

Риски формулировок: «ровно один assert» теряет проверку целостного результата; «всё mock» скрывает БД/конкуренцию; «всё TestCase» скрывает commit; «отдельный service для каждого действия» множит обёртки; старое дерево collection.models возвращает отвергнутую схему. Предлагаемые правила устраняют эти неоднозначности, сохраняя принятую архитектуру и объём 7.1.
