# Журнал, служебное состояние и ручной перезапуск: первичные источники

Проверено 18 ноября 2026. Это доказательная записка к проектированию Python 3.13 / Django в Linux app-контейнере. Приведённые ниже проектные выводы — предложения, а не реализованные или автоматически принятые механизмы. Код, Compose, SQL и сервисы не менялись и не запускались.

## 1. Атомарность состояния и сохранность после сбоя

**Факты.** Успешный `os.replace` атомарно заменяет имя; операция может не работать между файловыми системами. Для буферизованного Python-файла перед `os.fsync` требуется `flush`. На Linux `fsync` файла не гарантирует сохранение записи каталога: требуется отдельный `fsync` его дескриптора. Это разные требования: атомарная видимость замены и сохранность после сбоя. Источники: [Python 3.13 os.replace / fsync](https://docs.python.org/3.13/library/os.html#os.replace), [Linux fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html).

**Проектный вывод.** Каждый снимок `state.json` целиком сериализует launcher. Последовательность: создать уникальный временный файл **в том же каталоге volume**, записать UTF-8 JSON, `flush`, `fsync` файла, закрыть, `os.replace`, `fsync` каталога. Для создания подходит штатный `tempfile` с явно заданным `dir`; временный файл в `/tmp`/tmpfs для такой замены не подходит. [Python tempfile](https://docs.python.org/3.13/library/tempfile.html#tempfile.mkstemp) позволяет задавать каталог и предупреждает, что SIGKILL не выполняет автоматическое удаление именованных временных файлов.

Ошибки записи, замены и синхронизации нельзя считать успешно сохранённым состоянием. До замены сохраняется прежний снимок; после успешного replace, но ошибочного directory-fsync новый снимок может уже читаться, однако его сохранность после сбоя не подтверждена. Остаток временного файла не становится состоянием автоматически. Гарантия зависит от фактической Linux-файловой системы и хранилища Docker; это не транзакция с PostgreSQL и не обещание пережить любую аппаратную неисправность.

## 2. Один писатель для каждого файла

**Факты.** Python Logging Cookbook прямо указывает: запись нескольких процессов в один файл штатными файловыми обработчиками не поддерживается; их блокировки не являются межпроцессными. Открытие одного файла несколькими обработчиками также может нарушить ротацию. [Logging Cookbook](https://docs.python.org/3.13/howto/logging-cookbook.html#logging-to-a-single-file-from-multiple-processes).

**Проектный вывод.** В `/var/lib/app/runs/<run_id>/state.json` пишет только launcher; Django читает через управляющий слой и не обновляет этот файл из web workers. Минимум снимка: версия формата, generation владельца, run_id, состояние, зафиксированная область сбора, этап, счётчики и итог/причина. Счётчики — диагностический снимок полученных сообщений, а не точная копия committed-данных БД после аварии.

В актуальном предложении единственный процесс-писатель `events.jsonl` также launcher. Runner передаёт структурированные события через свой stdout PIPE, который непрерывно читает выделенный reader-поток launcher. HTTP workers и runner не создают собственный файловый handler. Штатный logging поддерживает потоки одного процесса; snapshot между потоками сериализуется отдельным локальным lock. Так исключается ранее рассматривавшаяся передача владения log-файлом runner→launcher. Это выбранное проектное предложение, не предписание Python. [Logging thread safety](https://docs.python.org/3.13/library/logging.html#thread-safety), [subprocess PIPE warning](https://docs.python.org/3.13/library/subprocess.html#subprocess.Popen.wait).

Launcher получает ready (после PG-блокировки), progress и result от своего runner. Нужны ограниченные JSON-сообщения и строки, непрерывное чтение и обработка недопустимых сообщений без исполнения. PIPE не становится очередью заданий или новым сервером. Формат/валидация реализуются позже, сейчас выбран именно этот транспорт. run_id/instance_id отвергают устаревшие сообщения, но сами не запрещают старому процессу писать.

## 3. JSONL, ротация и честное чтение

**Факты.** JSON не имеет встроенного разделения последовательных объектов: повторные `json.dump` в один файл не создают корректный единый JSON-документ. Для неверного документа декодер выдаёт `JSONDecodeError`; документация также рекомендует ограничивать размер входа. [Python json](https://docs.python.org/3.13/library/json.html). `RotatingFileHandler` использует ненулевые `maxBytes` и `backupCount`; при ротации сохраняет нумерованные старые файлы, а лишние удаляет. Это не журнал с гарантией доставки или межфайловая транзакция. [Python logging.handlers](https://docs.python.org/3.13/library/logging.handlers.html#rotatingfilehandler).

**Проектный вывод.** Одна строка журнала — один ограниченный JSON-объект плюс `\n`; переводы строк в значениях экранирует сериализатор. Поля: run_id, время события, уровень, источник, этап, ключ публикации при наличии, результат и безопасная причина. Не дописывать отдельную неэкранированную traceback-строку. Последовательный номер события помогает показать пропуск, но не восстанавливает потерянные записи.

Предлагаемая настройка — `5 * 1024 * 1024` байт и две резервные копии **на run**, с отдельным пределом размера сериализованного события. Число 5 MiB само по себе не является строгим пределом при огромной одиночной записи. Читатель идёт от `.2` к `.1`, затем к текущему файлу; ограничивает объём чтения и учитывает ротацию во время обновления, не выдавая исчезнувший файл за пустой журнал. Старые записи одного длинного run будут удаляться ещё до его окончания — интерфейс должен показывать, что доступен только сохранённый хвост. Ротация не обеспечивает сохранность последних строк при аварии и не является резервным копированием.

Различать: (1) доступный пустой журнал; (2) ещё не созданный журнал; (3) удалённый по retention; (4) ошибка доступа/чтения; (5) повреждённый JSON; (6) последняя строка без завершающего `\n`. В активном файле последний случай может быть незавершённой записью; после подтверждённого завершения писателя — возможным обрывом. Даже если последний JSON разбирается, отсутствие терминатора не доказывает завершённую запись. Некорректная полная строка посередине — повреждение, а не обычный хвост. Сохранять читаемые строки с предупреждением; не скрывать ошибку и не ремонтировать файл при HTTP-чтении. Некорректный или обрезанный `state.json` целиком невалиден; не превращать его в idle/успех.

## 4. Volume, UID и временный socket

**Факты.** Docker volume сохраняется независимо от контейнера. Пустой volume по умолчанию получает содержимое каталога образа; непустой скрывает содержимое образа. Один volume может одновременно использоваться несколькими контейнерами. Это не механизм единственного владельца. [Docker volumes](https://docs.docker.com/engine/storage/volumes/). `tmpfs` удаляется при остановке контейнера, его права могут сбрасываться после перезапуска; память может попасть в swap. [Docker tmpfs](https://docs.docker.com/engine/storage/tmpfs/).

**Проектный вывод.** Именованный `app_data` монтируется в `/var/lib/app` для служебных снимков и журналов. Подготовить каталог с принятым app UID/GID и закрытыми правами при сборке образа; при первом и повторном подключении проверить действительную доступность записи этим UID. Copy-up не является гарантией исправления прав уже существующего volume: пересборка образа не меняет его содержимое. Если права не подходят, сообщить ошибку; отдельное исправление принадлежности только своего volume согласовывается при реализации, без рекурсивного изменения чужих данных и без удаления volume.

Control socket находится отдельно: `/run/app` в tmpfs, каталог 0700 и socket 0600 для app UID создаются/проверяются при каждом старте. Наличие socket-файла не доказывает живой launcher. PID/pidfd/socket не восстанавливаются из volume как рабочие адреса управления.

## 5. Ручное восстановление и срок хранения

**Факт.** Compose `restart: "no"` означает отсутствие автоматического перезапуска по политике контейнера. Это не запрещает явный `start/up/restart` оператором и не задаёт логику возобновления collection. [Compose restart](https://docs.docker.com/reference/compose-file/services/#restart).

**Проектный вывод.** После ручного запуска app не возобновлять collection. Перед новым владельцем volume host runner под своим существующим учётом владения должен подтвердить остановку конкретного старого app-контейнера/generation и запретить его параллельный повторный запуск; только затем новый launcher может пометить прежний активный run как прерванный. Если это не доказано — unknown, запрет нового сбора и удаления справочников. Возраст записи, пропавший socket, другой PID, новый generation и отсутствие PG-lock по отдельности не являются такой защитой. У нового ручного сбора новый run_id; обход начинается сначала, уже committed-предметные данные PostgreSQL сохраняются.

`state.json` описывает последний известный служебный результат. Он не доказывает живой процесс, очищенный Chromium, полученную PG-блокировку или наличие committed-записи; для этого сохраняются соответствующие проверки принятого lifecycle. После SIGKILL итог/счётчики могут отставать. Некорректный снимок не даёт восстановить точную область/итог: показывать «состояние недоступно», сохраняя доказательства ошибки, а не выдумывать успешное завершение.

Предложение retention: оставить 10 завершённых запусков; текущий, unknown и повреждённые каталоги автоматически не удалять. Удалять только собственные подтверждённо завершённые каталоги под сериализацией launcher, без следования произвольным путям/симлинкам. Это не строгая квота volume: protected-каталоги могут накапливаться, а при переполнении запись может отказать. Удаление старых журналов окончательно убирает возможность их просмотра; это ограничение должно быть явно видно пользователю.

## 6. Диагностика контейнера и чувствительные данные

**Факты.** Docker `local` собирает stdout/stderr, вращает файлы, допускает `max-size`/`max-file` и сжатие; по умолчанию хранит 20 MB × 5 файлов. Читать внутренние файлы драйвера напрямую Docker запрещает. [Docker local driver](https://docs.docker.com/engine/logging/drivers/local/). В режиме доставки `blocking` возможна задержка приложения, в `non-blocking` при переполнении буфера новые сообщения теряются. [Docker logging configuration](https://docs.docker.com/engine/logging/configure/#configure-the-delivery-mode-of-log-messages-from-container-to-log-driver).

**Проектный вывод.** Для stdout/stderr app/db предложить локальный ограниченный Docker logging driver на уровне этих сервисов, без изменения общего Docker daemon. Это техническая диагностика контейнера, не источник административного журнала run. Не дублировать каждое событие collection в stdout и JSONL и не пытаться объединять два потока в историю. В текущем предложении выбраны max-size10m/max-file3 и non-blocking/max-buffer-size1m на каждом app/db: медленная Docker-диагностика не должна блокировать shutdown; при переполнении буфера возможна потеря строк, это не надёжный аудит. Объём Docker-логов учитывается отдельно от `app_data`.

До любого обработчика формировать только разрешённые поля: не записывать пароли, DSN, cookies, токены, заголовки авторизации, полные страницы/ответы, контактные данные и URL с секретными query-параметрами. Причины ошибок нормализовать, динамические значения ограничивать и очищать; не сохранять сырой `str(exception)`/traceback без проверки. Это проектное правило минимизации, а не гарантия библиотек. Те же ограничения относятся к stdout/stderr и самим снимкам области. Журнал доступен только администратору; очистка журнала не удаляет предметные данные БД, а удаление каталога не гарантирует физическое уничтожение байтов на носителе.

## Граница доказанности

Источники подтверждают возможности и ограничения библиотек/Docker. Предложенный протокол владельцев, сохранение данных при аварии, права volume и чтение при ротации ещё не проверены в образе проекта. Эти проверки относятся к будущей реализации; сейчас работа ограничена документированием.

Ошибка logging emit не обязана пробрасываться caller: штатный handleError при raiseExceptions=false может её скрыть. Предложение требует явно переводить отказ файлового writer в ошибку состояния/остановку, а не надеяться на except вокруг logger.info. [logging.handleError](https://docs.python.org/3.13/library/logging.html#logging.Handler.handleError).

## Уточнение после независимой критики: отделение control от writer

Синхронные logging/fsync могут блокироваться; выделенный PIPEreader сам этого не устраняет. Актуальное предложение использует один отдельный writer-поток в launcher, ограниченный native queue.Queue (256сообщений) и put_nowait. Full означает отказ без ожидания: control/reader продолжают работу, фиксируют storagefault и инициируют stop. Это внутренний буфер сообщений процесса, не taskqueue. Значения256/5секундACK — проектные параметры. [Python Queue.put_nowait/Full](https://docs.python.org/3.13/library/queue.html#queue.Queue.put_nowait), [logging с отдельным потоком](https://docs.python.org/3.13/howto/logging-cookbook.html#dealing-with-handlers-that-block), [time.monotonic](https://docs.python.org/3.13/library/time.html#time.monotonic).

Главный цикл не вызывает filesystemI/O и не удерживает handlerlocks; SIGTERM/KILL/status/stopdeadlines не ждут writer/EOFPIPE. ACK записи initial/finalsnapshot проверяются асинхронно с пределом5секунд; позднийACK не снимаетfault, initialfail не запускаетrunner. Очередь не гарантирует доставку при зависшемдиске; при переполнении потерянныесобытия помечаются, новыйrun блокируется. Неограниченныйjoin/заполнениеsentinel/logging.shutdown непригодны в этомуправляющемпути. При невыходящемwriter сохраняетсяunknown; крайняя граница очистки — разрешённое завершение своегоapp контейнера, не небезопасное убийствоPythonпотока. Обычныйexit/atexit при такомзависании нельзя обещатьуспешным. Это проектныйконтракт, runtimeнепроверен.
