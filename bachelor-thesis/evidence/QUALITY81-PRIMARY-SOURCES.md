# 8.1. Первичные источники для предложения инструментов качества

Проверено 17 ноября 2026 года по документации авторов и их репозиториям. Основа предложения — будущий модульный монолит Python/Django/PostgreSQL. Новые инструменты и их роли остаются предложением владельцу; версии, профиль правил и совместная конфигурация не утверждены и не проверены на приложении. Установки, создание конфигураций и запуск проверок приложения не выполнялись. Ссылки на Django 5.2 фиксируют версию прочитанной документации, а не выбор версии проекта.

## Подтверждённые возможности и границы

| Инструмент или штатный механизм | Факт из первичного источника | Предлагаемая роль и ограничение |
| --- | --- | --- |
| uv и `uv.lock` | `uv.lock` содержит точные разрешённые версии пакетов и предназначен для хранения в Git; `.venv` хранить в Git не рекомендуется. [Structure and files](https://docs.astral.sh/uv/concepts/projects/layout/#the-lockfile) | Один менеджер Python-зависимостей и один lockfile будущего приложения. Lockfile не фиксирует состояние PostgreSQL, внешних сайтов или браузерных бинарных файлов. |
| Locked-режим uv | `uv run --locked …` отказывает при неактуальном lockfile вместо его обновления; `uv lock --check` проверяет актуальность. `--frozen` пропускает эту проверку. Обычные `uv run` и `uv sync` могут обновить lockfile автоматически; `uv sync` по умолчанию удаляет лишние пакеты окружения. [Locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/) | Предложить locked-режим для воспроизводимых запусков после согласования окружения. Он не означает режим только чтения: синхронизация окружения остаётся возможной. Обновление зависимостей требует отдельного изменения. |
| Ruff: lint и исправления | `ruff check` проверяет Python; `--fix` включает исправления. Safe fixes задуманы как сохраняющие поведение; unsafe fixes могут изменить поведение или удалить комментарии и требуют отдельного включения. [The Ruff Linter](https://docs.astral.sh/ruff/linter/) | Поиск типичных ошибок Python одним линтером. Для проверки без изменения файлов — запуск без `--fix`; автоматическое применение unsafe fixes не предлагать. Выбор конкретных правил относится к 8.2. |
| Ruff: формат и импорты | `ruff format --check` проверяет формат без записи. Форматтер сам не сортирует импорты: это делает линтер с правилами `I`. Авторы не рекомендуют постоянное попеременное форматирование Ruff и Black из-за различий. [The Ruff Formatter](https://docs.astral.sh/ruff/formatter/) | Один Ruff для lint, формата Python и порядка импортов; параллельные Black/isort для тех же ролей не нужны. Ни форматирование, ни порядок импортов не проверяют предметные алгоритмы. |
| mypy и django-stubs | mypy допускает динамические участки: неаннотированные функции по умолчанию не проверяются, `Any` существенно ослабляет проверку. [Dynamically typed code](https://mypy.readthedocs.io/en/stable/dynamic_typing.html). django-stubs добавляет stubs и mypy plugin для Django; это независимый от Django проект. Plugin использует Django runtime для информации о моделях и может падать при сломанной загрузке приложения. [README авторов](https://github.com/typeddjango/django-stubs#readme) | Проверка типов Python и распространённых шаблонов Django ORM. Это отдельная роль относительно Ruff. Наличие plugin не делает всю динамику Django статически доказанной; настройки уровня проверки и подавлений — 8.2. |
| Совместимость django-stubs | Авторы публикуют матрицу Django, Python и mypy, отдельно отмечая partial support. Пример текущей таблицы: django-stubs 5.2.9 — Django 5.2, Python 3.10–3.13, mypy 1.13–1.19; у django-stubs 6.1.2 Django 5.2 указан лишь как partial support. [Матрица авторов](https://github.com/typeddjango/django-stubs#version-compatibility) | Перед фиксацией версий проверить всю связку Python/Django/mypy/django-stubs. Приведённые строки иллюстрируют ограничение, а не задают pins. Нельзя объявить совместимость только по совпадению номера Django или слову latest. |
| djLint | Linter проверяет шаблоны; профиль `django` включает соответствующие правила. Форматирование поддерживается отдельно. [Linter](https://djlint.com/docs/linter/), [репозиторий авторов](https://github.com/djlint/djLint). Опция `format_js` умеет форматировать JS/JSON внутри `<script>` через js-beautify, по умолчанию выключена; шаблонный синтаксис внутри поддерживается неполностью. [Configuration](https://djlint.com/docs/configuration/#format_js) | Lint и формат Django HTML-шаблонов, которые не покрывает Python-линтер. Это не замена анализатору JavaScript, выполнению JS, проверке страницы в браузере или компиляции Django-шаблонов. Отдельный JS-инструмент до появления соответствующей задачи не выбирать. |
| Штатные тесты Django | Django использует `unittest`, штатный запуск — `manage.py test`. [Writing and running tests](https://docs.djangoproject.com/en/5.2/topics/testing/overview/). `TestCase` изолирует тесты транзакциями; для проверки реальных эффектов commit/rollback и специфического транзакционного поведения предусмотрен `TransactionTestCase`. Test client не заменяет браузер и не проверяет выполнение JS. [Testing tools](https://docs.djangoproject.com/en/5.2/topics/testing/tools/) | Начать со штатного runner для логики модулей, ORM и HTTP-сценариев. Для рисков, связанных с PostgreSQL, проверять на PostgreSQL, а не считать другой backend эквивалентным. pytest не требуется только ради обычных Django-тестов. |
| Django system checks | `manage.py check` ищет распространённые проблемы проекта. Проверки, требующие БД, по умолчанию не выполняются; для них указывают `--database`. `--deploy` добавляет проверки развёртывания и требует соответствующих settings. [System check framework](https://docs.djangoproject.com/en/5.2/ref/checks/), [check](https://docs.djangoproject.com/en/5.2/ref/django-admin/#check) | Использовать встроенный механизм для конфигурации и объявлений Django. Успех не доказывает корректность бизнес-логики, схемы реальной БД, браузерного интерфейса или безопасность целиком. |
| Проверка забытых миграций | `makemigrations --check` возвращает ненулевой код при изменениях моделей без миграций и уже подразумевает `--dry-run`. [makemigrations](https://docs.djangoproject.com/en/5.2/ref/django-admin/#makemigrations). Применение миграций выполняет отдельная команда `migrate`. [Migrations](https://docs.djangoproject.com/en/5.2/topics/migrations/) | `manage.py makemigrations --check --dry-run` — понятная проверка отсутствия забытых миграций без создания файлов. Она не применяет миграции и не доказывает успешное обновление существующей БД. |
| Playwright Python | Python API поддерживает sync/async и браузеры Chromium, Firefox, WebKit. Авторы рекомендуют pytest plugin для end-to-end тестов, но отдельно документируют библиотеку, используемую без pytest. Для работы нужны браузерные бинарные файлы. [Introduction](https://playwright.dev/python/docs/intro), [Library](https://playwright.dev/python/docs/library) | Браузерные пользовательские сценарии и поведение JS, когда появятся страницы приложения. Способ интеграции с тестовым runner согласовать отдельно; рекомендация plugin не делает pytest обязательной заменой штатным Django-тестам. |

## Существующий npm Playwright

В корневом `package.json` Playwright объявлен как вспомогательная dev-зависимость `nir-thesis-tools`; команда `screenshots` запускает `scripts/screenshots.mjs`. Скрипт открывает сайты аналогов и сохраняет снимки в `thesis/screenshots`. Это проверено чтением файлов, без запуска браузера.

Этот механизм обслуживает иллюстрации пояснительной записки. Сам факт его наличия не означает наличия браузерных тестов будущего Django-приложения. Предлагаемый Playwright Python выполняет другую задачу; решение о нём не требует переносить или заменять существующие npm-скрипты.

## Вывод о минимальности предложения

Для 8.1 предлагаются готовые роли: uv с lockfile — зависимости; Ruff — Python lint/format/импорты; mypy с django-stubs — типы; djLint — Django-шаблоны; штатные Django tests/checks и проверка миграций — поведение и механизмы фреймворка; Playwright Python — браузерные сценарии. Эти роли покрывают разные риски. Не требуется добавлять параллельные Black/isort, отдельный runner для обычных Django-тестов или собственный механизм system checks.

pre-commit — готовый менеджер Git hooks, а GitHub Actions — платформа автоматического запуска workflows. Это возможные последующие способы запуска уже выбранных проверок, не самостоятельные проверки качества; в 8.1 они не выбираются и не настраиваются. [Документация pre-commit](https://pre-commit.com/), [GitHub Actions](https://docs.github.com/en/actions/get-started/understand-github-actions).

Минимальность здесь означает отсутствие дублирования ролей, а не доказательство необходимости немедленно включить весь перечень. Окончательный состав, версии и правила требуют решения владельца; работоспособность общей конфигурации остаётся непроверенной.
