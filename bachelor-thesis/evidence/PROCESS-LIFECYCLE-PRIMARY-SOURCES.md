# Завершение процессов, аренда стека и выбор порта

Проверено 18 ноября 2026. Исследовательская записка: факты источников и предложения для будущей реализации. Код, конфигурация и Git не изменялись; установки и запуски не выполнялись. База: Python 3.13, Compose app/db, `init: true`, сборщик отдельным процессом внутри app, один браузер на запуск, PostgreSQL advisory lock, без Celery и новых таблиц.

## Что действительно обеспечивают штатные механизмы

- `init: true` добавляет PID 1 для передачи сигналов и подбора завершившихся процессов. Конкретный init зависит от платформы. Это не контракт завершения всего дерева приложения. Tini по умолчанию передаёт сигнал непосредственному ребёнку; `-g` отдельно включает сигнал группе. [Compose init](https://docs.docker.com/reference/compose-file/services/#init), [Tini process groups](https://github.com/krallin/tini#process-group-killing).
- Docker stop передаёт сигнал главному процессу, затем после grace period принудительно завершает контейнер. Для Linux без переопределения timeout — 10 секунд. Это крайняя граница остановки app, не доказательство выполнения Python `finally`. [Docker stop](https://docs.docker.com/reference/cli/docker/container/stop/).
- `Popen(start_new_session=True)` вызывает `setsid()` на POSIX. `poll()` сообщает завершение непосредственного ребёнка, `wait(timeout)` ждёт его и при timeout бросает исключение; ожидание само не убивает процесс. `terminate()`/`kill()` относятся к ребёнку; для группы есть `os.killpg`. Необслуживаемые PIPE могут заблокировать ожидание, поэтому обычные логи здесь проще наследовать в stdout/stderr контейнера. [Python 3.13 subprocess](https://docs.python.org/3.13/library/subprocess.html), [os.killpg](https://docs.python.org/3.13/library/os.html#os.killpg).
- Python выполняет signal handlers в главном потоке; установка обработчиков также разрешена только там. SIGKILL нельзя перехватить. Обработчик должен передать управление обычному пути остановки, а не выполнять длительное закрытие браузера внутри обработчика. Последнее — проектная рекомендация. [Python signal](https://docs.python.org/3.13/library/signal.html).
- `browser.close()` закрывает запущенный браузер и страницы. Явно созданные contexts рекомендуется закрыть раньше для корректного сохранения артефактов. Это API-операция: при убийстве Python исполнение `finally` не гарантируется. [Playwright Browser](https://playwright.dev/python/docs/api/class-browser#browser-close). Для async-кода отмена доставляется в следующей доступной точке; очистку размещают в `try/finally`, затем обычно распространяют `CancelledError`. [Python cancellation](https://docs.python.org/3.13/library/asyncio-task.html#task-cancellation).

## Существенная граница: группа runner не равна дереву браузера

В просмотренном upstream `main` Playwright запускает браузер с `detached: true` на POSIX, то есть браузер получает отдельную группу. Сам Playwright при форсированном закрытии посылает SIGKILL отрицательному PID браузера. Поэтому обещание «`killpg(runner_pid)` гарантированно удалит Chromium» неверно. Это чтение upstream, не проверка driver из фиксированного пакета проекта. [Playwright processLauncher.ts](https://raw.githubusercontent.com/microsoft/playwright/main/packages/utils/processLauncher.ts).

В том же upstream driver при закрытии transport pipe вызывает штатное закрытие браузеров, затем выход; обработчик SIGINT специально оставляет driver работающим ради такого закрытия. Следовательно, при смерти runner следует дать driver время обработать EOF, а не немедленно убивать всю группу. Это путь восстановления, а не гарантия против зависания/одновременного SIGKILL. [Playwright driver.ts](https://raw.githubusercontent.com/microsoft/playwright/main/packages/playwright-core/src/cli/driver.ts).

## Минимальное предложение для app

Один foreground launcher — непосредственный ребёнок init — запускает web-команду и по запросу отдельный runner на один сбор. Выбор HTTP-сервера этим не делается. Launcher хранит `Popen`/идентичность своих детей и состояние одного активного запуска; web не создаёт runner самостоятельно. Docker допускает wrapper как главный процесс для управления несколькими процессами. [Docker multiple processes](https://docs.docker.com/engine/containers/multi-service_container/).

Для web → launcher достаточно локального Unix socket в приватном runtime-каталоге, с правами 0600: короткие запросы старта, остановки и состояния. Содержимое внутреннего сообщения не меняет пользовательский JSON-контракт. `socketserver.UnixStreamServer` входит в Python; цикл `handle_request()` с timeout позволяет между запросами проверять детей и флаг завершения. Каждый handler только валидирует ограниченное по размеру сообщение, запускает/сигнализирует ребёнка и быстро отвечает; выполнение сбора и ожидание его завершения не держат соединение. Нужен timeout чтения принятого соединения. `serve_forever().shutdown()` из того же потока может зависнуть, поэтому здесь этот путь не нужен. [Python socketserver](https://docs.python.org/3.13/library/socketserver.html).

Это необходимая небольшая координация родителя и web, не отдельный брокер, очередь или supervisor-пакет. `multiprocessing.connection` тоже штатный, но `send/recv` сериализуют объекты через pickle; для короткого ограниченного сообщения AF_UNIX socket не требует нового authkey и особенностей multiprocessing. [Python multiprocessing connections](https://docs.python.org/3.13/library/multiprocessing.html#listeners-and-clients).

Предлагаемый порядок остановки:

1. Launcher прекращает принимать новые старты. Обработчики SIGINT/SIGTERM и обычный выход сходятся в один идемпотентный cleanup/finally.
2. Посылает SIGTERM непосредственно runner, чтобы тот отменил сбор и в своём `finally` закрыл context, browser и Playwright. Одновременно инициирует штатную остановку web. Время ожидания ограничено общей монотонной deadline, а не суммой произвольных бесконечных ожиданий.
3. При аварийной смерти runner даёт его driver обработать EOF. `wait()` ребёнка и освобождение DB-lock сами не доказывают отсутствие браузера.
4. Если по deadline завершение всей работы не подтверждено, фиксирует неопределённое завершение, сохраняет рабочий каталог и запрещает новый сбор и удаление затронутых данных. Только PGID runner для доказательства очистки недостаточен. Не добавляются сканер процессов, `pkill` или привилегии ради неподтверждённой гарантии.
5. Жёсткая конечная граница — остановка управляемого app-контейнера через Docker. Она допускается после освобождения всех host leases либо отдельной согласованной координации обслуживания; другие пользователи общего app не прерываются автоматически. Постоянные volumes сохраняются. До разрешённой очистки app остаётся в неисправном состоянии и не принимает новые сборы.

Строгий учёт detached browser groups не предлагается как готовый механизм. После переподчинения процессов init дерево PPID прежнего runner перестаёт быть полным доказательством происхождения; один retained PGID также не охватывает все отдельные группы Playwright. Доступность `/proc` внутри собственного namespace не устраняет эту задачу идентификации. До отдельного подтверждения поведения фиксированного Playwright сохраняется консервативный путь неопределённого завершения и координированной остановки app. Заменять этот пробел утверждением о возможностях init нельзя.

## Два разных вида блокировки

**Блокировка приложения:** runner до запуска браузера берёт `pg_try_advisory_lock` с постоянным ключом singleton на отдельном живом DB-соединении. Функция возвращает false без ожидания, если блокировка занята. Session lock держится до явного unlock или окончания DB-сессии, независимо от commit/rollback. Это не новая таблица; нужны одно приобретение и одно освобождение. [PostgreSQL advisory functions](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS), [session lifetime](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS).

**Аренда локального стека:** внешний task runner учитывает каждого пользователя app и db, включая общие зависимости; DB singleton этого не делает. Предложение: локальный реестр lease-файлов под коротким `fcntl.flock` для атомарного acquire/release/recovery. `flock` — штатный Unix API; Linux освобождает lock при закрытии всех соответствующих дескрипторов. Реестр сам по себе не становится автоматической уборкой. [Python fcntl](https://docs.python.org/3.13/library/fcntl.html), [Linux flock](https://man7.org/linux/man-pages/man2/flock.2.html).

Lease содержит task token, PID и время рождения владельца, heartbeat, идентичность Compose project/сервисов/контейнеров и признак «запущено runner» либо «уже работало». Истёкший heartbeat только инициирует проверку. Удаление lease допускается после подтверждения отсутствия исходного PID либо несовпадения birth/ownership; permission error и невозможность проверки не означают смерть. Linux `/proc/PID/stat` содержит starttime; это не macOS API. Для Mac нужен отдельно проверенный системный способ получения birth, без объявления `kill(pid,0)` достаточной идентификацией. [Linux proc stat](https://man7.org/linux/man-pages/man5/proc_pid_stat.5.html).

Acquire, recovery и решение об остановке сериализуются одним host lock. Последний активный lease освобождает только управляемые сервисы, запущенные этим механизмом, с повторной проверкой владения; ранее работающие сервисы сохраняются. Release вызывается из finally и SIGINT/SIGTERM; после SIGKILL уборка возможна только внешним живым владельцем или при следующем запуске/recovery, а не убитым процессом. Команда `compose stop SERVICE...` не удаляет контейнеры; сохранность volumes не требует `down -v`. [Compose stop](https://docs.docker.com/reference/cli/docker/compose/stop/).

## Свободный host port без bind/close гонки

Сначала под host lock ищется совместимый уже запущенный управляемый app и присоединяется lease; порт повторно не выделяется. Для нового app Compose позволяет не указывать published host port: runtime выделяет свободный порт при создании публикации. Для локального доступа задаётся `host_ip: 127.0.0.1`, внутренний `target: 8000`, published отсутствует. Это предложение конфигурации, ещё не проверенное локальным Compose. [Compose ports](https://docs.docker.com/reference/compose-file/services/#ports).

После запуска фактический адрес читается через `docker compose -p <project> port app 8000` и показывается пользователю. Такой выбор не обещает именно host 8000; внутренний 8000 сохраняется. Он исключает собственную схему «найти свободный socket → закрыть → попросить Docker занять тот же порт», поскольку порт назначает сам runtime. Если нужно предпочитать ровно host 8000, сначала выполняется реальная публикация Docker, а обработка именно конфликта привязки и безопасный повтор требуют отдельного решения; проверка свободности до публикации гарантии не даёт. [Compose port](https://docs.docker.com/reference/cli/docker/compose/port/).

Не проверены экспериментально: работа IPC, сигналы выбранного в будущем HTTP-сервера, штатное/аварийное завершение фиксированного Playwright, идентификация browser groups, Mac birth API, восстановление lease после SIGKILL и публикация порта локальным Engine. Источники подтверждают API, но не заменяют эти проверки.

## Уточнение безопасной адресации сигнала

В Linux app Python3.13 предоставляет os.pidfd_open и signal.pidfd_send_signal для ссылки на конкретный процесс, устойчивой к повторному использованию числовогоPID. Предложение основной схемы: получить pidfd своего непосредственного ребёнка сразу после Popen до reap и использовать его дляTERM/KILL. Не заменять им механизмMaclease: это Linux API. [os.pidfd_open](https://docs.python.org/3.13/library/os.html#os.pidfd_open), [signal.pidfd_send_signal](https://docs.python.org/3.13/library/signal.html#signal.pidfd_send_signal).

Предпочтение8000 и fallback на Docker-назначенный loopbackпорт уже отдельно принято владельцем в CONTAINER-RUNTIME-PROPOSAL.md; обсуждавшийся выше вариант сразудинамическогоhostпорта — только техническая возможность, не новый принятый режим. Повтор выполняется только после подтверждённого конфликтаbinding, не после произвольного падения app.
