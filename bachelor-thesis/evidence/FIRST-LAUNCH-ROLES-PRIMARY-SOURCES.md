# Первый запуск, миграции и роли PostgreSQL: первичные источники

Проверено 18 ноября 2026 года. Область: PostgreSQL 17, официальный образ PostgreSQL, Django 5.2. Это исследовательская записка для согласования; она не утверждает новый порядок запуска или роли проекта. SQL, конфигурация и код приложения не менялись; контейнеры и миграции не запускались. Принятый контейнерный профиль повторно не пересматривался.

## Подтверждённые свойства PostgreSQL

| Вопрос | Подтверждённый факт и следствие |
| --- | --- |
| Владелец объекта | Владелец может менять и удалять объект и повторно выдавать себе права. Отзыв у владельца UPDATE/DELETE не обеспечивает запрет обхода. Поэтому runtime не должен владеть защищаемыми объектами. [PostgreSQL 17: Privileges](https://www.postgresql.org/docs/17/ddl-priv.html) |
| Атрибуты роли | LOGIN разрешает вход; SUPERUSER обходит проверки прав; CREATEDB и CREATEROLE дают отдельные возможности создания БД и ролей. Владение уже созданной прикладной БД не требует превращения migration-роли в суперпользователя. [Role Attributes](https://www.postgresql.org/docs/17/role-attributes.html) |
| Членство | Права могут наследоваться, а SET позволяет переключиться на другую роль. Запрет SET ROLE сам по себе не делает безопасным наследование прав владельца: документация предупреждает о манипуляции принадлежащими ему объектами. Предложение: runtime вообще не включать в роль владельца, прямо или через цепочку. [Role Membership](https://www.postgresql.org/docs/17/role-membership.html), [GRANT](https://www.postgresql.org/docs/17/sql-grant.html) |
| PUBLIC и временные таблицы | PUBLIC означает все роли. Базы по умолчанию дают PUBLIC CONNECT и TEMPORARY; обычные таблицы и последовательности не получают публичных прав. Отсутствие прямого GRANT роли не означает отсутствия доступа. Для запрета TEMP нужно учитывать PUBLIC. [Privileges](https://www.postgresql.org/docs/17/ddl-priv.html) |
| Схема public | По умолчанию public доступна всем по USAGE; CREATE может сохраниться при обновлении с PostgreSQL 14 и старше. Схема в search_path с чужим CREATE является доверенной поверхностью исполнения SQL. Проверять фактические права, а не только номер сервера. [Schemas](https://www.postgresql.org/docs/17/ddl-schemas.html) |
| Владение public | Изначально public принадлежит pg_database_owner; неявный участник этой роли — владелец текущей БД. Следовательно, отдельная новая прикладная схема не обязательна только ради разграничения owner/runtime; выбор схемы остаётся проектным решением. [Predefined Roles](https://www.postgresql.org/docs/17/predefined-roles.html) |
| Колонки | Право на таблицу действует и при отсутствии права на отдельную колонку. Нельзя дать UPDATE на всю таблицу и затем запретить одну колонку её локальным REVOKE. Для узкого изменения источника нужны права только на разрешённые колонки, без широкого UPDATE через PUBLIC/членство. [GRANT](https://www.postgresql.org/docs/17/sql-grant.html) |
| Последовательности | Права таблицы автоматически не распространяются на связанные последовательности. nextval требует USAGE либо UPDATE, setval — UPDATE. Минимальный кандидат для последовательностей, используемых вставкой, — USAGE; проверять реальный способ генерации ключей, не выдавать UPDATE ради nextval. [GRANT](https://www.postgresql.org/docs/17/sql-grant.html), [Sequence Functions](https://www.postgresql.org/docs/17/functions-sequence.html) |
| Очистка | DELETE и TRUNCATE — разные права. TRUNCATE удаляет строки и не вызывает ON DELETE triggers; его нельзя оставлять runtime ради служебной очистки. [TRUNCATE](https://www.postgresql.org/docs/17/sql-truncate.html) |

## Будущие объекты и повторные миграции

ALTER DEFAULT PRIVILEGES влияет только на будущие объекты, созданные текущей ролью либо указанным target_role. Наследуемые роли не подставляются как создатель. Настройки на уровне схемы добавляются к глобальным; локальный REVOKE не отменяет глобальный GRANT. Изменение defaults не исправляет ACL существующих объектов. [ALTER DEFAULT PRIVILEGES](https://www.postgresql.org/docs/17/sql-alterdefaultprivileges.html)

Вывод для предложения: не использовать общий default GRANT ALL или общий UPDATE/DELETE на будущие таблицы. После каждого успешного migrate отдельным явным шагом приводить существующие объекты к согласованной матрице прав. Неизвестная новая таблица должна остаться недоступной runtime до классификации. Повторное применение должно убирать несовместимые прежние выдачи, включая колонки и членства, а не только добавлять недостающие права. Это рекомендация, не готовая реализация.

## Официальный образ PostgreSQL

POSTGRES_USER задаёт bootstrap-суперпользователя, по умолчанию postgres. Поэтому назначение POSTGRES_USER=nir_app не создаёт ограниченную прикладную роль. Переменные начальной инициализации действуют на пустой каталог данных; изменение переменной не переименовывает существующую роль в сохранённом volume. [Official Image: Environment Variables](https://hub.docker.com/_/postgres#environment-variables)

Файлы docker-entrypoint-initdb.d исполняются только при пустом каталоге. Если файл завершился ошибкой после initdb, перезапуск с уже заполненным каталогом не продолжит оставшиеся файлы. Следовательно, initdb.d может быть начальной точкой, но не единственным механизмом повторного bootstrap/выдачи прав. Нужен отдельно вызываемый повторяемый этап с проверкой результата; удалять постоянный volume ради повторения нельзя считать штатным восстановлением. [Official Image: Initialization Scripts](https://hub.docker.com/_/postgres#initialization-scripts), [официальный entrypoint](https://github.com/docker-library/postgres/blob/master/docker-entrypoint.sh)

Ограничение: документация образа и master entrypoint изменяемы; здесь проверены общие свойства, не digest конкретного PostgreSQL 17 image и не его фактический запуск.

## Django 5.2: migrate и тестовая БД

При установленном django.contrib.auth migrate создаёт стандартные разрешения моделей через post_migrate. Сигнал отправляется даже при отсутствии новых миграций и после flush. В исходниках create_permissions читает существующие разрешения и выполняет bulk_create недостающих; create_contenttypes также читает и создаёт отсутствующие записи. Следовательно, «миграции уже применены» не означает «migrate больше ничего не пишет». Migration-роли нужны права на эти служебные записи и применяемые миграции; обычный старт runtime не следует связывать с автоматическим migrate. [Authentication](https://docs.djangoproject.com/en/5.2/topics/auth/default/#default-permissions), [post_migrate](https://docs.djangoproject.com/en/5.2/ref/signals/#post-migrate), [auth management](https://github.com/django/django/blob/stable/5.2.x/django/contrib/auth/management/__init__.py), [contenttypes management](https://github.com/django/django/blob/stable/5.2.x/django/contrib/contenttypes/management/__init__.py)

Адресная проверка исходников тега Django 5.2.19: обычный `manage.py migrate --check` без `--prune` вычисляет план и завершает работу до `pre_migrate`, `sync_apps`, `executor.migrate` и `post_migrate`: при непустом плане — `sys.exit(1)`, при пустом — `return` (migrate.py, строки 227–247). Следовательно, штатная ветка проверки не применяет миграции/DDL и не вызывает post_migrate при любом плане; обычный migrate проходит дальше к post_migrate и при пустом плане (строки 336–368). Штатный PostgreSQL backend не переопределяет пустой prepare_database базового класса. Это основание для проверки готовности runtime без автоматических миграций, но не безусловная гарантия отсутствия записи в произвольном проекте: до развилки выполняются импорты management и системные проверки; пользовательский код этих механизмов отдельно не исследован. Комбинация с `--prune` сюда не относится: её обработка расположена раньше развилки `--check` и может писать django_migrations. [Django 5.2.19 migrate.py](https://github.com/django/django/blob/5.2.19/django/core/management/commands/migrate.py#L177-L247), [post_migrate в той же команде](https://github.com/django/django/blob/5.2.19/django/core/management/commands/migrate.py#L336-L368), [базовый prepare_database](https://github.com/django/django/blob/5.2.19/django/db/backends/base/base.py#L597-L602), [PostgreSQL backend](https://github.com/django/django/blob/5.2.19/django/db/backends/postgresql/base.py), [BaseCommand.execute](https://github.com/django/django/blob/5.2.19/django/core/management/base.py#L405-L429)

Стандартный Django test runner создаёт отдельную БД, используя USER и остальные параметры подключения; пользователь должен иметь право создания БД, для PostgreSQL также нужен доступ к встроенной postgres. --keepdb всё равно создаёт отсутствующую БД и применяет миграции. Поэтому стандартный запуск под nir_app без CREATEDB не следует считать работоспособным по умолчанию. [The test database](https://docs.djangoproject.com/en/5.2/topics/testing/overview/#the-test-database)

Кроме того, PostgreSQL backend Django реализует flush через TRUNCATE, с возможными RESTART IDENTITY/CASCADE. Это несовместимо с постоянной выдачей runtime только SELECT/INSERT на историю. [Django PostgreSQL operations, sql_flush](https://github.com/django/django/blob/stable/5.2.x/django/db/backends/postgresql/operations.py)

Предложение: общий тестовый администратор/владелец допустим только в отдельном тестовом окружении; его успех не доказывает F25. CREATEDB не ограничивается префиксом имени test_: если runner сам создаёт БД, безопаснее отдельный тестовый кластер без рабочих данных. Альтернатива — заранее подготовленная тестовая БД и отдельно выбранный порядок подготовки/очистки. Приёмку SQL-обхода выполнять отдельным подключением с реальными правами nir_app после подготовки схемы владельцем. Создание, миграции и очистка тестовой БД остаются вне runtime-подключения. Не выдавать CREATEDB/TRUNCATE nir_app ради удобства runner. Конкретный тестовый механизм пока не выбран и не проверен. Основание для границы CREATEDB: [Role Attributes](https://www.postgresql.org/docs/17/role-attributes.html).

## Существенные обходы, которые матрица ACL сама не закрывает

1. Действия внешних ключей: ON DELETE/UPDATE CASCADE, SET NULL и SET DEFAULT могут менять ссылающуюся историю при изменении разрешённого родителя. PostgreSQL выполняет RI-запросы с правами владельца затронутой таблицы. Следствие: запрета прямых UPDATE/DELETE истории недостаточно; нужно проверить реальные FK и изменения ключей родителей. Не утверждается, что такой обход уже имеется в проекте. [Constraints](https://www.postgresql.org/docs/17/ddl-constraints.html#DDL-CONSTRAINTS-FK), [PostgreSQL 17 ri_triggers.c, ri_PerformCheck](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/utils/adt/ri_triggers.c)
2. SECURITY DEFINER исполняется с правами владельца функции; новые функции по умолчанию доступны PUBLIC по EXECUTE. Такая функция может дать косвенный путь к изменению истории. В будущей реализации необходимо проверить доступные функции и search_path, не добавляя привилегированную универсальную функцию для runtime. [CREATE FUNCTION: Security](https://www.postgresql.org/docs/17/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY)
3. SELECT/INSERT защищают сохранённые строки от прямого изменения, но не доказывают истинность новых событий. Для F25 отдельно определить, означает ли требование неизменяемость существующей истории или также достоверность её происхождения. Сам по себе append-only ACL не подтверждает второе; это ограничение предлагаемой модели.

## Минимальный кандидат на согласование

- существующий bootstrap postgres остаётся отдельно от двух прикладных LOGIN-ролей;
- nir_owner владеет прикладной БД и объектами схемы, выполняет migrate; без SUPERUSER/CREATEDB/CREATEROLE;
- nir_app не владелец, без членства/SET ROLE к owner, без grant option и широких предопределённых ролей;
- для истории runtime получает только SELECT/INSERT и необходимые права генерации ключей; без UPDATE/DELETE/TRUNCATE/TRIGGER, без общего ALL для будущих объектов;
- для источников узкое UPDATE разрешённого enabled, если эта граница утверждена на уровне SQL; для регионов/типов согласованный CRUD, для объектов/объявлений обычная запись без придуманной функции жёсткого удаления;
- bootstrap создаёт/проверяет роли и владение, owner выполняет migrate, затем явный этап применяет матрицу прав; приложение запускается отдельно с nir_app;
- пароли bootstrap/owner не передаются среде runtime и его дочернего runner; повторное выполнение не зависит только от initdb.d.

Это предложение архитектуры запуска. Оно требует согласования и будущей проверки на выбранном образе PostgreSQL 17: пустая и сохранённая БД, повторный migrate, восстановление после частичного bootstrap, реальные записи приложения и запрет прямого/косвенного изменения истории под nir_app. В этой записке подтверждены источники, а не выполнена такая проверка.
