# 8.2 — первичные источники для профиля качества

Проверено18ноября2026. Это исследовательская записка для предложения8.2, не утверждение профиля и не рабочая конфигурация. Инструменты не устанавливались; проверки приложения не запускались. Возможности сверены с текущей документацией авторов; версии будущего окружения ещё нужно выбрать совместно.

## Ruff: явный набор и формат

Рекомендуемый **проектный выбор**: `E4,E7,E9,F,I,UP,B`. `E` — pycodestyle, `F` — Pyflakes, `I` — сортировка импортов, `UP` — современные конструкции Python, `B` — flake8-bugbear. Это ограниченный набор групп, а не все правила и не обещание обнаружения всех ошибок. Авторы рекомендуют явный `select` и постепенное расширение. `ALL` при обновлении автоматически включает новые правила; поэтому для согласованного профиля его лучше не выбирать. Источник: [Ruff linter: Rule selection](https://docs.astral.sh/ruff/linter/#rule-selection).

Не называть этот набор «default Ruff»: текущая [Configuration](https://docs.astral.sh/ruff/configuration/) отсылает к отдельной [Default Rules](https://docs.astral.sh/ruff/default-rules/), а не фиксирует старый четырёхэлементный список как полный современный default. Наш список нужно задать явно. Параметры форматирования из документации: `line-length=88`, `indent-width=4`, `quote-style="double"`, `indent-style="space"`, `line-ending="auto"`. Это разумная основа без собственного стиля. `auto` определяет окончания строк по входу, а не гарантирует LF во всех файлах. Python target надо согласовать с выбранной версией приложения, не копировать из примера документации. [Configuration](https://docs.astral.sh/ruff/configuration/).

Предлагается стабильный режим без preview. Preview включает нестабильные правила, исправления, стиль formatter и другие изменения. Группа в `select` при выключенном preview не означает включение её preview-правил; стабильный набор всё равно может расшириться после обновления версии. [Preview](https://docs.astral.sh/ruff/preview/).

`ruff format --check` не изменяет файлы; обычный `ruff format` форматирует на месте. Formatter не сортирует импорты: это роль линтера `I`. Длина88 — цель переноса, а не жёсткая гарантия; поэтому `E501` способен ругаться даже после форматирования и в предлагаемый набор не входит. `COM812` входит в официальный список конфликтующих правил и здесь не нужен. **Не писать, что `ISC001` обязательно конфликтует:** текущая документация такого общего утверждения не содержит; список отдельно оговаривает сочетание `ISC002`, отсутствия `ISC001` и `allow-multiline=false`. В наш набор ISC вообще не включён, поэтому предварительные ignore для него не нужны. [Ruff formatter](https://docs.astral.sh/ruff/formatter/#conflicting-lint-rules), [ISC001](https://docs.astral.sh/ruff/rules/single-line-implicit-string-concatenation/).

## Nullable строки: граница DJ001

`DJ001` проверяет строковые Django-поля с NULL, включая `CharField`/`TextField`; основание — двойное представление отсутствия через `None` и пустую строку. Это соглашение Django, а не доказательство неверности любого nullable текста. [DJ001](https://docs.astral.sh/ruff/rules/django-nullable-model-string-field/).

Локальный принятый контракт в `DB-POINT2-VERIFIED-DRAFT.md` явно содержит `properties.address text NULL`, `ads.market_segment text NULL`, `ads.description text NULL`. Следовательно, при прямом отображении на стандартные nullable строковые поля модель конфликтовала бы с DJ001. Это вывод из контракта и определения правила; кода модели ещё нет, реальное срабатывание не проверялось. Не менять NULL на пустую строку ради линтера. Для начального набора не включать всю группу `DJ`/`ALL`; DJ001 тогда не включён и отдельное подавление не требуется. Будущие Django-правила можно согласовать отдельно.

## mypy: строгий handwritten Python и точная граница Any

В прочитанной stable-документации **mypy2.4.1** `strict` включает13 флагов: `disallow-any-generics`, `disallow-subclassing-any`, `disallow-untyped-calls`, `disallow-untyped-defs`, `disallow-incomplete-defs`, `check-untyped-defs`, `disallow-untyped-decorators`, `warn-redundant-casts`, `warn-unused-ignores`, `warn-return-any`, `no-implicit-reexport`, `strict-equality`, `extra-checks`. Состав меняется по версиям; это справка текущей версии, не выбранный pin. `warn-unreachable` в strict не входит. `strict-bytes` с2.0 является поведением по умолчанию, его не следует приписывать этому списку. Strict не запрещает любой `Any`: например, полного запрета `disallow-any-expr`/`disallow-any-explicit` в списке нет. [mypy command line](https://mypy.readthedocs.io/en/stable/command_line.html#miscellaneous-strictness-flags).

Предложение политики: один глобальный strict для всего собственного Python приложения — `catalog`, `collection`, проектных settings/URL/ASGI/WSGI-модулей, команд управления и тестов. Название будущего пакета конфигурации пока условное; фактические пути задать после появления структуры. Не ограничивать типизацию только сервисами и DTO, оставляя views/forms/tests без неё. Это проектная рекомендация, не требование mypy/Django и не ранее принятое решение.

`ignore_errors` подавляет все нефатальные ошибки; предлагается запретить его глобально и для целых собственных приложений. Глобальный `ignore_missing_imports` также не выбирать. Исключение по конкретному внешнему нетипизированному модулю рассматривается только после проверки stubs и сохраняет явную границу Any. `exclude` управляет рекурсивным обнаружением: он не гарантирует исключение явно переданного или импортированного модуля. Поэтому «исключить migrations» нельзя описывать как полную изоляцию типов одним regex. [mypy configuration](https://mypy.readthedocs.io/en/stable/config_file.html), [mypy import discovery](https://mypy.readthedocs.io/en/stable/command_line.html#import-discovery).

Текущий вариант 8.2 не исключает папку миграций из Ruff/mypy. Для генерируемых деклараций используется вывод типов; конкретная несовместимость разбирается локально, а не отключением всей папки. Рукописный `RunPython` проверяется как собственный код, с `StateApps` и обоснованным динамическим типом исторических моделей. Это предложение проекта; совместная работа будущей конфигурации ещё не проверена.

`warn_unused_ignores` уже есть в strict. Дополнительно разумен `ignore-without-code`: подавление должно называть конкретный код, например `type: ignore[код]`, и сопровождаться понятной причиной по проектному правилу. Проверка ненужных ignore имеет ограничение для статически недостижимых веток. Наличие кода подавления не доказывает его обоснованность; это предмет ревью. [Optional error codes](https://mypy.readthedocs.io/en/stable/error_code_list2.html#check-that-type-ignore-include-an-error-code-ignore-without-code).

## django-stubs: использовать plugin, не переписывать ORM-типизацию

Plugin использует runtime Django для моделей; нужны подходящие импортируемые settings. `strict_settings=true` и `strict_model_abstract_attrs=true` — значения по умолчанию; разумно сохранить их. Отключение первого ослабляет вывод динамических settings до Any; отключение второго может скрывать ошибки доступа к атрибутам абстрактных моделей. `models.Field` имеет два generic-параметра: принимаемый при присваивании и возвращаемый при чтении типы; README показывает их прежде всего для собственных полей. Это не основание вручную дублировать тип каждой обычной модели: сначала использовать вывод plugin. Runtime generic-поддержка и `django_stubs_ext.monkeypatch()` — отдельный вопрос конкретных аннотаций/классов; включать patch заранее без требующего его кода не предлагается. В `RunPython` документация рекомендует `StateApps` для исторических моделей: их тип динамический, а современная модель не заменяет историю. [README django-stubs: settings и FAQ](https://github.com/typeddjango/django-stubs#settings).

## djLint: профиль, параметры и область

Для Django templates авторы рекомендуют профиль `django`. Это выбор синтаксиса/правил шаблонов, а не инструмент выполнения шаблонов. [Django profile](https://djlint.com/docs/languages/django/).

Конкретное предложение: `indent=2` — проектный выбор (default4); `max_line_length=120` — имя настоящего параметра и его default. Не писать `line_length`: такого параметра для этого предложения нет. Это параметр раскладки, не обещание абсолютной верхней длины любой строки. `blank_line_before_tag` — список тегов, default отсутствует; «выключен» означает оставить список пустым/не задавать, а не присвоить boolean false. `format_js=false`, `format_css=false` — defaults: оставить их, не добавляя форматирование вложенных script/style с неполной поддержкой шаблонного синтаксиса. [djLint Configuration](https://djlint.com/docs/configuration/).

`djlint <свои-шаблоны> --check` показывает изменения formatter без записи; `--reformat` записывает их. Флага `--format`, аналогичного `ruff format`, здесь не подставлять. Сам djLint прямо предупреждает, что не является HTML parser/syntax validator. [Formatter usage](https://djlint.com/docs/formatter/).

Отдельно `djlint <свои-шаблоны> --lint`: проверить правила профиля Django. Большинство правил включены по умолчанию; `include`/`ignore` меняют выбор, поэтому не переносить sample ignore из документации без причины. [Linter rules](https://djlint.com/docs/linter/).

Область — собственные HTML-шаблоны будущего приложения, включая свои overrides, а не скопированные страницы источников, evidence, экспорт отчёта, внешние/vendor HTML или установленные пакеты. Это проектная граница. Не запускать рекурсивную обработку всего нынешнего документного репозитория. Существующие шаблоны Django/vendor не переписываются; overrides, которые проект создаёт сам, входят в проверку. Загрузка/рендер страниц и браузерные сценарии остаются самостоятельными проверками.

## Что передать в предложение8.2

Рекомендуется включить явный Ruff-набор и стабильное форматирование88/4, mypy strict для всего собственного Python с адресными кодированными подавлениями, defaults строгого django-stubs и djLint django/2/120 для своих шаблонов. Не включать ALL, DJ001 вопреки принятому NULL-контракту, глобальные подавления, необоснованный runtime patch и предварительные ignore для невключённых правил. Все перечисленные области, включая миграции без общего исключения, — **предложение8.2**, до решения владельца не приняты. Совместная работа версии plugin, выбранных библиотек и будущего приложения остаётся непроверенной.
