# Пункт 1 — предложение о разделении ответственности

Статус: предложение, пользователь ещё не принял. Это одно Django-приложение с PostgreSQL, не пять отдельных сервисов. Реализации нет. Здесь выбираем функциональные границы, а не количество Django apps, файлов, классов или отдельный слой-обёртку над ORM.

## Основание и уже принятые ограничения

Исходный НИР ../thesis/nir/body.md, разделы 5.1–5.5, перечисляет пять подсистем: сбор/парсинг; нормализация/дедупликация; хранение/JSON; поиск/UI; администрирование. НИР определяет функции, а не обязательное число программных пакетов. Предлагается использовать эти пять понятных границ. Это проектное предложение, не требование университета о структуре кода.

Принято: три площадки; один проект Python/Django/PostgreSQL; исходные публикации отдельно от объектов и предложений; автоматическая дедупликация; фото без постоянного хранения, получение в память и показ по URL; повторный запуск обработки без дублей. Ручного исправления/разделения/очереди ручной проверки в продукте нет. Отдельного координатора/системы задач не добавляем.

## Пять функциональных модулей

| Модуль | Владеет задачей | Что получает и возвращает | Не делает |
|---|---|---|---|
| Сбор и парсинг | Запросы к трём площадкам, выдача/карточки, специфичный разбор полей источника, получение фото по ссылке в память, сетевые ошибки/повторы | Параметры источника → результат получения с внешним ID, URL, временем, исходными значениями, ссылками на фото, версией парсера; отдельно байты фото/ошибка | Не унифицирует предметные значения разных площадок, не сравнивает объекты, не меняет историю |
| Нормализация и дедупликация | Общая трактовка адресов/единиц/полей, характеристики для сравнения, фотохеши, кандидаты, автоматические решения о принадлежности объекту | Сохранённое исходное наблюдение и версии входов → нормализованные значения, признаки, объяснение и результат группировки | Не знает HTML/селекторы площадок; не показывает страницы; не пишет произвольно в чужие таблицы |
| Хранение данных | Django-модели/миграции, исходные наблюдения и обработанные версии, источники/объекты/публикации/сделки/цены/фотоссылки/признаки, журнал; сохранение результатов, выборки и JSON-представление по НИР | Данные/результат обработки → сохранённые записи/версии; запрос выборки → записи/документированные данные | Не вычисляет правила нормализации и сходства; не обращается к площадкам; не формирует HTML |
| Поиск и пользовательский интерфейс | Ввод и проверка фильтров, их пользовательский смысл, каталог/карточка/история/сообщения, HTTP-ответы HTML и JSON | Пользовательские параметры → запрос к хранению → страницы/JSON-ответ | Не повторяет алгоритм совпадений; не парсит площадки; не поддерживает второе независимое определение фильтров для JSON |
| Администрирование | Штатная Django-авторизация/разрешения, управление источниками/справочниками, запуск/остановка и просмотр журнала | Действие администратора → проверка прав/параметров → вызов той же операции запуска/остановки/изменения | Не реализует заново auth; не содержит свою нормализацию/дедупликацию и второй механизм сбора |

Хранение — владелец постоянных записей, обработка — владелец смысла преобразования и решения о дублях. Не создаём универсальные repository/service-обёртки поверх каждого ORM-запроса: границы описывают обязанности, конкретная организация Django-кода обсуждается следующим шагом.

JSON: хранение задаёт представление данных; HTTP-маршрут и пользовательские параметры — интерфейс. Единый запрос/критерии выборки используются HTML и JSON. Административные формы пишут через штатные механизмы Django, соблюдая общие ограничения данных; граница хранения не означает обязательный самописный getter/setter на каждую таблицу.

## Проход одного объявления

Условный пример: Циан, ID X, площадь «45,2 м²», цена «7 000 000 ₽», ссылки на фото.

1. Сбор извлекает исходные поля и происхождение. Привязка HTML/JSON источника к полю площади находится здесь; это ещё не общее правило нормализации разных источников.
2. Хранение сохраняет исходное наблюдение до нормализации. Проверяет публикацию по (source, external_id), операцию приёма по устойчивому ID. Это не решение о совпадении физических объектов.
3. Обработка приводит площадь к числу 45.2/м² и цену к числу/валюте. Получает фото в память через операцию загрузки, предоставленную сбором; рассчитывает признаки, находит кандидатов по сохранённым данным. Код сравнения не содержит сетевых запросов и может проверяться на готовых данных.
4. Хранение сохраняет обработанную версию/признаки. Обработка выдаёт результат совпадения на указанных версиях, хранение проверяет актуальность/ограничения целостности и атомарно записывает связи. Смысловое решение, можно ли объединять, принадлежит обработке. При неопределённости объекты остаются раздельно, нет ручной очереди.
5. Интерфейс показывает объект и его публикации/цены, фото по исходным ссылкам.

Последовательность явно записана в команде запуска проекта. Она вызывает операции модулей; отдельной долговечной очереди/координатора нет, предметные правила в команду не помещаются. Административный экран использует тот же запуск, долгий сбор не выполняется внутри HTTP-запроса. Способ запуска отдельного процесса ещё не принят и не маскируется под готовую инфраструктуру.

## Проверка границ на исключениях

- Изменился HTML Циан: меняется сборщик, алгоритм общих единиц и сравнения не меняется.
- Обновилось общее правило адреса: меняется обработка; сохранённые исходные сведения можно переобработать без обязательной новой карточки.
- Пришло повторное получение: хранение различает повтор доставки операции и новое наблюдение. Новое наблюдение не равно новой публикации.
- Обработка не завершилась: сохранённые наблюдения имеют состояние/версию обработки; следующий запуск повторяет незавершённое на сохранённых данных. Это конкретное состояние записи, а не отдельная система задач.
- Ошибка нормализации/источника не удаляет прошлую успешную версию. Неудачный запрос не является признаком снятия объявления.
- Фото исчезло: состояние доступности сохраняется; предыдущий признак не уничтожается. Без достаточных данных обработка не выдумывает уверенное совпадение. URL не гарантирует неизменность байтов, признак связан с checksum и версией.
- Параллельные изменения: актуальность входов проверяется при сохранении результата; точный протокол блокировок — следующая спецификация. Нельзя считать его реализованным. Предлагается один активный автоматический проход; этот режим также требует подтверждения.

## Что выбирается сейчас

Пять функциональных обязанностей и направление обмена, включая размещение нормализации в обработке. Отдельные сервисы, универсальный фреймворк, ручные функции, архив фото не предлагаются. Подробные типы контрактов/блокировок/запуска и физическое разбиение кода — следующий шаг после подтверждения границ. Требования источника проверяются по реальному НИР; не представлять его пять функций как обязательные пять Django apps.
