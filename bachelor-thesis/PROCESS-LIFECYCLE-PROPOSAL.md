# Пункт 9 — запуск, остановка и освобождение ресурсов

## Запуск

Из каталога `implementation/` оператор запускает сайт командой `docker compose up -d --wait`. Порядок подготовки PostgreSQL для первого запуска приведён в [руководстве](../implementation/README.md). Постоянные сервисы Compose — `app` и `db`.

Для обработки одной поддержанной карточки используется отдельный контейнер из образа `app` с командой Django:

```sh
docker compose run --rm app python -m app.manage collect '<URL карточки Циан>'
```

Текущий срез принимает URL карточки продажи квартиры на `samara.cian.ru`. Полный последовательный обход источников и параметры его области определены в [4.3](COLLECTION-4.3-PROPOSAL.md) и [5.1](SOURCE-PARAMETERS-PROPOSAL.md). Старт сайта не запускает сбор.

## Синхронизация PostgreSQL

- Команда использует штатное соединение Django и захватывает сессионную advisory-блокировку PostgreSQL через `pg_try_advisory_lock`. Если блокировка занята, сбор не запускается. Соединение удерживается до выхода команды из операции сбора.
- Операция удаления регионов и видов недвижимости берёт тот же ключ через `pg_try_advisory_xact_lock` в транзакции удаления. При занятом ключе удаление отклоняется. Используемые записи дополнительно защищены ссылочной целостностью.
- Приём снимка берёт тот же ключ на время транзакции. При записи из той же сессии PostgreSQL позволяет повторно взять ключ. Вызовы из других сессий ждут его освобождения. Чтение страницы и нормализация происходят перед транзакцией каталога. Успешно сохранённые публикации и история цен остаются в PostgreSQL.

## Остановка

В переднем плане оператор нажимает `Ctrl+C`. Для отдельного работающего контейнера сбор можно остановить адресной командой `docker container stop <ID контейнера сбора>`. Обработчики SIGINT и SIGTERM отмечают запрос остановки. Команда проверяет его перед новой сетевой попыткой и перед передачей снимка в каталог. Уже начатая транзакция завершается штатной фиксацией или откатом. Сетевые операции ограничены таймаутами. При выходе закрываются собственные страница, контекст, браузер и соединение PostgreSQL. Сессионная блокировка освобождается при закрытии соединения.

После SIGKILL нельзя опираться на обработчик остановки. Не завершённая транзакция откатывается при завершении сессии PostgreSQL. Для подтверждения остановки проверяется завершение нужного контейнера. Сайт и база продолжают работать при остановке отдельной команды сбора.

Чтобы завершить работу своего стека, оператор сначала завершает свой сбор, затем выполняет `docker compose down` для своего проекта. Постоянный том `db` сохраняется. Чужие контейнеры и общий Docker не останавливаются. Автоматические проверки используют отдельный проект Compose и временные данные. [Проверки](QUALITY-8.4-PROPOSAL.md)

## Проверяемые сценарии

- Две команды сбора конкурируют за одну блокировку, а занятый ключ отклоняет удаление справочника.
- Остановка проверяется по выходу команды и результату в терминале. Сайт продолжает отвечать, зафиксированные данные остаются.
- Ручной повторный запуск использует прежний ключ публикации. Неизменная цена не создаёт дополнительную строку истории.
