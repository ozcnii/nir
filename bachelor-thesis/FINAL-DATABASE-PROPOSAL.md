# Предложение БД ВКР

**Аудит реальных источников:** прежнее обозначение финального проекта отозвано. SOURCE-FIELD-AUDIT.md выявил неподтверждённую необходимость mapping-таблиц, различающиеся виды географии/площади, диапазоны выдачи и отдельные квартиры, общие фото ЖК у разных квартир. Старый логический балл не подтверждает источник данных. Новая схема автоматически не принимается.

Статус: новый проект для согласования; решения не приняты, реализации и испытаний нет. Проверка ниже — логический разбор сценариев.
Основание: только НИР §5.1–5.5 и принятая граница collection → catalog. Python/Django/PostgreSQL; штатные Django auth/admin.

## 1. Что именно хранится

Предлагается семь предметных таблиц: source, region, property_category, source_region, source_property_category, ad, price_history.
Квартира (для дома/комнаты — соответствующий объект недвижимости) представлена явно определённой группой объявлений: все ad с одинаковым group_ad_id.
Отдельной строки квартиры с собственными характеристиками нет: без канонических характеристик или самостоятельных бизнес-данных она была бы запрещённой таблицей только с ID.
Объявление — самостоятельная публикация площадки, строка ad. Нормализованные характеристики принадлежат исключительно этой публикации.
Сохранённый результат matching — связь ad.group_ad_id с настоящим объявлением-представителем. У представителя group_ad_id = id; у одиночки тоже.
Представитель нужен исключительно для идентичности группы, его площадь/цена не становятся истиной квартиры. UI показывает варианты каждого источника.
Неизбежный компромисс: у квартиры нет самостоятельного постоянного ID. Постоянная ссылка ведёт на ad.id и открывает его текущую группу.
Это открытое решение о представлении объекта, а не переименование объявления в квартиру. JSON различает объект-группу и входящие публикации.

## 2. Точный состав

Все имена snake_case. bigint PK генерируются БД, timestamptz — время UTC, numeric — точное десятичное число.
В списках поля обязательны, кроме явно отмеченных NULL. Все FK имеют ON DELETE RESTRICT (в Django — PROTECT); скрытых FK в JSON нет.

**source**
- code varchar(8) PK, CHECK IN ('avito','cian','domclick'): одновременно идентификатор и выбор поддержанного сборщика.
- enabled boolean: участие в запуске. Лимиты и выбранные регионы/типы одного прохода передаются из формы в command; технические задержки находятся в конфигурации сборщика, не в БД.
- Читаемое название формируется из трёх поддержанных code в интерфейсе. Вторые id/name для этих же трёх значений не нужны.

**region**
- id bigint PK; name varchar(200) UNIQUE, CHECK непустое после trim; редактируемое название региона.

**property_category**
- Категория публикации по НИР, а не строгий физический вид недвижимости: «вторичное жильё» и «новостройка» не становятся разными сущностями квартиры.
- id bigint PK; name varchar(100) UNIQUE, CHECK непустое после trim; редактируемые названия: вторичное жильё, новостройка, комната, дом.
- ID не кодируют смысл числом. При выборе типа сборщик получает его явное соответствие источнику из следующей таблицы.

**source_region**
- id bigint PK; source_code varchar(8) FK source.code; region_id bigint FK region.id; external_code varchar(300) CHECK непустое.
- UNIQUE (source_code, region_id). external_code — источник-специфичный код региона для сборщика, а не URL произвольного запроса.

**source_property_category**
- id bigint PK; source_code varchar(8) FK source.code; property_category_id bigint FK property_category.id; external_code varchar(300) CHECK непустое.
- UNIQUE (source_code, property_category_id). external_code — источник-специфичный код типа; отсутствующая пара означает ненастроенное/неподдерживаемое сочетание.
- source_region нужна, чтобы один редактируемый регион сопоставить разным кодам сайтов; source_property_category делает то же для категории публикации. external_code используется сборщиком при построении запроса, не задаёт правила matching.
- Форматы и реальные внешние коды ещё предстоит проверить по источникам; выдуманные значения и произвольные дополнительные параметры не предлагаются.

**ad**
- id bigint PK; source_code varchar(8) FK source.code; external_id varchar(200) CHECK непустое; UNIQUE (source_code, external_id).
- url text CHECK непустое: ссылка площадки; group_ad_id bigint FK ad.id: плоская группа, включая самоссылку корня.
- region_id bigint FK region.id; property_category_id bigint FK property_category.id: значения конкретного источника, выбранные/проверенные по справочникам.
- address text NULL: нормализованный полный адрес без выдуманных частей; CHECK NULL либо непустое.
- latitude numeric(9,6) NULL, longitude numeric(9,6) NULL: CHECK обе NULL либо обе заданы; диапазоны [-90,90] и [-180,180].
- area_m2 numeric(10,2) NULL CHECK > 0; rooms smallint NULL CHECK >= 0 (0 — студия); floor smallint NULL (подвальный этаж может быть отрицательным).
- observed_at timestamptz: момент начала получения этой страницы, определяет порядок принятых снимков, а не дату создания объявления.
- is_active boolean: последнее явно полученное состояние публикации; исчезновение из страницы поиска само по себе не означает снятие.
- photos jsonb NOT NULL DEFAULT []: последний известный список; photos_observed_at timestamptz NULL: время получения именно этого списка; NULL означает, что список ещё не известен (тогда photos=[]).
- Элемент photos строго {url, phash, hash_version}; url — непустая строка; phash/hash_version либо оба NULL, либо строки. Версия определяет алгоритм и формат hash; длина/кодировка не фиксируются до выбора алгоритма.
- catalog валидирует фиксированную схему JSON; БД проверяет верхний тип array. Хеши не являются FK. URL используются UI; хеши — только matching.
- Нет title/description/created_at без функции в задании. Цены и тип сделки не дублируются здесь: текущие значения берутся из последней price_history.

**price_history**
- id bigint PK; ad_id bigint FK ad.id; observed_at timestamptz; UNIQUE (ad_id, observed_at).
- price_rub numeric(16,2) NULL CHECK >= 0; deal_type varchar(10) CHECK IN ('sale','month_rent','day_rent').
- Каждая строка — первое состояние цены/сделки либо изменение хотя бы одного из этих значений. NULL означает действительно неизвестную цену, включая переход известная → неизвестная.
- sale — полная стоимость, month_rent — за месяц, day_rent — за сутки; тип в каждой строке сохраняет смысл старой суммы при смене сделки.
- Записи неизменяемы: права роли приложения разрешают INSERT/SELECT, запрет UPDATE/DELETE дополнительно защищает триггер БД. Исправления задним числом не предусмотрены.
- Снятые объявления и их история сохраняются; штатное удаление предметных публикаций не предоставляется даже через admin.

**Ограничения и индексы**
- Обычные PK у таблиц соответствий и истории нужны для штатного Django admin: модели с composite PK пока нельзя зарегистрировать в нём ([официальная документация](https://docs.djangoproject.com/en/5.2/topics/composite-primary-key/)). Предметная уникальность обеспечена отдельными UNIQUE.
- Отложенный constraint trigger проверяет итоговую плоскость всех затронутых связей, включая входящие ссылки на изменённые ad: целевой ad.group_ad_id = ad.id. Проверки только изменённой строки недостаточно.
- CHECK photos_observed_at IS NULL ⇒ photos=[]; при известном списке photos_observed_at ≤ observed_at. Для корня ID выделяется sequence до INSERT и сразу записывается в id и group_ad_id.
- Ровно одна исходная price_history обязательна для каждого ad: отложенная проверка БД запрещает завершить вставку без неё; позже историю нельзя удалить.
- PK и UNIQUE создают собственные B-tree; второй такой же индекс не добавляется. UNIQUE(ad_id, observed_at) позволяет искать последнюю цену обратным проходом.
- Дополнительные B-tree: ad(group_ad_id); ad(region_id, property_category_id, area_m2); ad(property_category_id); source_region(region_id); source_property_category(property_category_id).
- Уникальный ключ ad начинается с source_code и обслуживает этот FK; существующие индексы покрывают остальные FK. Поля rooms/floor фильтруются после регионального отбора.
- Отдельный индекс цены пока не нужен: индекс всей истории не решает поиск именно текущей цены. При необходимости оптимизация выбирается по реальным планам запросов.

## 3. Строки одной демонстрационной квартиры

Адрес вымышленный: Самара, ул. Примерная, д. 10, кв. 25. region: (1, Самарская область); property_category: (1, Вторичное жильё).
source: (cian, true), (domclick, true), (avito, false).
source_region и source_property_category содержат настроенные сборщиком external_code для соответствующих пар; это не предполагает одинаковые внешние значения у сайтов.

| ad.id | source_code | external_id | group_ad_id | area_m2 | rooms | floor | active |
|---|---|---|---|---|---|---|---|
| 101 | cian | demo-101 | 101 | 45.20 | 2 | 4 | true |
| 102 | domclick | demo-202 | 101 | 45.00 | 2 | 4 | true |

Обе строки имеют region_id=1, property_category_id=1, этот адрес, собственные URL, observed_at=T1 и T2 соответственно; координаты NULL, photos=[], photos_observed_at=NULL: список фото в этом примере не получен.
price_history: (101,T1,6800000.00,sale), (102,T2,6950000.00,sale). Для условия задачи принадлежность одной квартире подтверждена.
Квартира — группа 101, публикаций две, результата цены «квартиры» нет. Никакие 45.10 м² и средняя цена не вычисляются.
Фильтр цена ≤ 6 850 000 И площадь ≤ 45.10: результат пуст. Cian проходит только цену, Domclick — только площадь.
Фильтр цена ≤ 6 850 000 И площадь ≤ 45.30: группа найдена через 101; карточка показывает обе публикации и отмечает совпавшую.

## 4. Контракт collection → catalog

Неисполняемый пример входных данных: source_code=cian, external_id=demo-101, observed_at=2026-11-16T10:00:00Z, state=active;
url=https://example.org/cian/demo-101; region_id=1; property_category_id=1; address=Самара, ул. Примерная, д. 10, кв. 25;
latitude=NULL; longitude=NULL; area_m2=45.20; rooms=2; floor=4; deal_type=sale;
price={status:known, amount:6800000.00, currency:RUB}; photos={status:known, items:[{url:https://example.org/photo/1.jpg, phash:NULL, hash_version:NULL}]}.
Другие состояния цены: {status:unknown}; {status:error, reason:...}. Для error catalog отклоняет снимок целиком; ошибку пишет файловый журнал.
Валюта RUB принимается только при явном указании на странице или документированном договоре конкретного поля источника; это правило сборщика проверяется при реализации.
Иная или неопределённая валюта — отклонение, без конвертации/молчаливого RUB. unknown разрешён только при отсутствии опубликованной суммы, а не при неудачном разборе.
active — полный снимок структурных полей; отсутствие optional означает NULL. Ошибка их разбора означает отклонение, не NULL. Фото имеют отдельный статус:
photos={status:unavailable} — список получить не удалось: прежние photos/photos_observed_at сохраняются, цена и остальные поля могут обновиться; это не известный пустой список.
photos={status:known, items:[]} — список достоверно пуст: очистить photos и установить photos_observed_at=observed_at. Известный непустой список так же заменяет прежний.
При known-списке и ошибке загрузки байтов конкретного фото сохраняются его URL и NULL hash/версия; старый hash даже для того же URL не переносится в свежий снимок.
removed — отдельное событие только с source_code, external_id, observed_at и state; оно не стирает характеристики, фото, историю и группу.
Выход: status=created/updated/unchanged/stale/conflict/rejected; ad_id; group_ad_id; price_changed; diagnostic. Для rejected неизвестного ad оба ID отсутствуют.
collection получает данные, нормализует и вычисляет фото в памяти; catalog проверяет контракт, порядок, matching и атомарно сохраняет результат.
Сеть и обработка фото выполняются до транзакции. collection не записывает таблицы напрямую. Файлы фото на диск/в БД не сохраняются.

## 5. Запись, matching и чтение

1. Одна короткая транзакция приёма использует общий transaction advisory lock каталога: сериализует конкурирующие записи/merge без отдельного сервиса. Чтение не блокируется.
2. Идентичность публикации — только UNIQUE(source_code, external_id). Более старое observed_at отклоняется целиком. Равное время допускает только идентичный повтор; различия дают conflict без записи, с сообщением в журнал.
   Для active при равном времени photos_observed_at=observed_at означает ранее принятый known, меньшее время/NULL — unavailable. Смена статуса или состава известного списка при равном времени — conflict, не обогащение.
3. Более новое active обновляет структуру; фото — по known/unavailable из контракта. При неизменной цене и сделке история не пополняется, включая повторный NULL.
4. Более новое removed выключает существующий ad; неизвестный external_id не создаёт пустую строку. Повтор снятия с новым временем обновляет только observed_at. Более старое active не воскресит снятое.
5. Первая active-вставка создаёт ad, исходную price_history и сначала одиночную группу. Все три операции/последующий merge либо фиксируются вместе, либо откатываются.
6. Интерфейс matching принимает текущие снимки двух публикаций, включая observed_at и отдельный photos_observed_at, возвращает same_property / different / uncertain, объяснение, версию алгоритма и версии использованных входов.
7. По НИР должны рассматриваться адрес/координаты, площадь, комнаты, этаж и perceptual hashes. Правила, веса, пороги и совместимость типов — следующий отдельный пункт проектирования; здесь они не устанавливаются.
8. Фото не могут быть единственным основанием объединения. При unavailable старый список не выдаётся matching за свежий: передаётся его собственная версия; допустимость использования выбирает будущий алгоритм.
9. До выбора и проверки алгоритма автоматическое качество matching не подтверждено. Демонстрационная пара — заданный подтверждённый случай, а не доказательство найденного алгоритмом совпадения.
10. Предлагаемая защита merge: same_property для каждой пары объединяемых групп на актуальных входах; different или uncertain блокируют новое объединение. A≈B≈C не заменяет проверку A↔C. Это новая policy для согласования.
11. После проверки все ad проигравшей группы получают один group_ad_id; выбирается меньший существующий корневой ad.id исключительно ради детерминированности. Признаки/цены не переносятся между объявлениями.
12. Поздние данные позволяют объединить существующие группы тем же merge. Если обновление участника даёт different с членом прежней группы, новый факт сохраняется, конфликт журналируется, FK не меняется. При uncertain прежняя связь также остаётся. Это риск сохранения ошибочной группы без split, не гарантия её корректности.
13. Автоматический split не предложен. Ошибочное объединение или исправленный источником адрес могут оставить неверную группу; это осознанное ограничение, а не гарантия безошибочной дедупликации.
14. Карточка по ad.id читает его group_ad_id, затем все ad этой группы, для каждого — последнюю цену и отдельную историю. Снятый корень остаётся адресуемым, активные источники показываются первыми.
15. Поиск применяет ВСЕ условия к одной активной ad и её последней price_history, затем DISTINCT group_ad_id. NULL не проходит числовые диапазоны. HTML/JSON используют одну выборку.
16. Плоская FK предпочтительнее графа: чтению не нужны рекурсивный CTE/BFS и транзитивное дедублирование. Цена простоты — UPDATE всей группы при merge и проверка всех пар; масштаб НИР ещё не измерен.
17. Перед записью проверяется совпадение версий входов matching с заблокированными текущими строками. Результат принадлежности сохраняется FK; объяснение/версии доступны операции и журналу, отдельный полный аудит не обещан. Смена алгоритма сама не пересобирает группы.

## 6. Проверка сценариев и границы

- Контрольные Cian 45.20/6.8 млн и Domclick 45.00/6.95 млн сохраняются без потерь; смешанный фильтр выше даёт пустой результат.
- Повтор, конфликт равного времени, старый снимок и снятие разобраны правилами 2–4. known→unavailable при новом времени сохраняет старые фото и допускает новую цену; known-empty очищает; ошибка байтов при том же URL не переносит hash.
- При равном времени смена known↔unavailable выявляется по photos_observed_at и даёт conflict; произвольного обогащения нет. Порядок наблюдений сборщика не доказывает свежесть кеша площадки.
- Первая цена, неизменная цена, NULL→число, число→NULL и смена sale→month_rent при той же сумме сохраняют требуемые состояния; parse error не создаёт цену NULL.
- Позднее объединение групп меняет только ссылки; снятие корня не удаляет квартиру/историю; прежняя ссылка на любой ad продолжает работать.
- Конкурентные одинаковые вставки сериализуются и ограничены UNIQUE; авария до commit не оставляет половины группы или строки без первой цены.
- Журнал файловый; управление runner/start/stop вне предметной БД. Отдельных Run/Log/Acceptance/Photo/Offer таблиц, брокера и постоянного архива наблюдений нет.
- Admin изменяет enabled источников, соответствия внешним кодам и справочники; предметные ad/история доступны только для просмотра. Ручное исправление связей/очередь модерации не вводятся.
- Логически проверены перечисленные переходы. Код, SQL-планы, парсинг трёх сайтов и качество matching ещё не проверялись; это отдельные работы после принятия проекта.
