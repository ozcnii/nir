# Два варианта хранения недвижимости и объявлений

Оба варианта — предложения, решения ещё не приняты. Основание: § 5 первичного текста НИР.
Целевая среда — Django/PostgreSQL; collection собирает и нормализует данные; catalog валидирует, сопоставляет и сохраняет результат.
Источники: Авито, Циан, Домклик. Здесь рассматривается только ядро каталога.
Все примеры вымышленные; принадлежность двух объявлений одной квартире для примера уже подтверждена.
Совпадение адреса, комнат и этажа само по себе этого не доказывает.

## Общее для обоих вариантов

- `sources(code PK, enabled)`: три строки с кодами `avito`, `cian`, `domclick`.
- `Ad`: PK `id`, FK `source_code → sources.code`, `external_id`, `url`, тип сделки, цена, статус и `photos`.
- `UNIQUE(source_code, external_id)` отличает обновление объявления от новой публикации.
- `photos` — JSON-массив объектов с URL и необязательным pHash; отдельной таблицы фотографий нет.
- `PriceChange(id, ad_id FK, observed_at, price, deal_type)`: Ad 1:N PriceChange; первая цена тоже образует запись.
- Текущая цена в Ad — кэш последнего изменения; обе записи меняются одной транзакцией.
- Время относится к наблюдению цены; `deal_type` сохраняет контекст продажи/аренды за месяц/сутки на этот момент.
- RUB-only предлагается как ограничение первой версии; для аренды тип сделки определяет месячную/суточную цену.
- Повтор состояния не создаёт запись; изменение цены или `deal_type` создаёт одну запись при сериализации обновлений Ad.
- Автосопоставление использует совокупность характеристик и pHash. Неуверенный результат оставляет объявления раздельными.
- Отсутствие объявления в одной выдаче само по себе не означает снятие; здесь рассматривается подтверждённое снятие.

Обозначения сущностей: `Ad` — таблица `property_ads` в варианте 1 и `ads` в варианте 2; `PriceChange` — `price_history`.

## Вариант 1. Property хранит физические сведения и их расхождения

**Сущности и связи.** К общим сущностям добавляется `Property(id, facts)`; у Ad обязательный FK `property_id`.
Property 1:N Ad; Ad относится ровно к одной Property. Property без объявлений не сохраняется.
Ad содержит только сведения публикации и предложения; площади, адреса, комнат и этажа в Ad нет.
`facts` — JSON с нормализованными физическими характеристиками: тип объекта, регион, адрес, координаты, площади, комнаты, этаж и прочие нужные признаки.
Каждая характеристика содержит варианты значений с идентификаторами объявлений, сообщающих это значение.
Пример: `area: [{value:45.20, ad_ids:[11]}, {value:45.00, ad_ids:[12]}]`.
Общее значение хранится один раз: `rooms: [{value:2, ad_ids:[11,12]}]`.
Это содержательная запись объекта; отдельной копии этих характеристик в Ad нет.

**Политика конфликтов.** Сохраняются все актуальные нормализованные утверждения источников, привязанные к Ad.
Голосование, среднее, первенство поступления и назначение площадки истиной не применяются.
Единственное значение можно показать общим; конфликт показывается как «45.20 м² — Циан; 45.00 м² — Домклик».
При фильтрации значение извлекается именно для проверяемого Ad, а не выбирается из произвольного варианта Property.
Если источник изменил площадь, его Ad удаляется из старого варианта и добавляется в новый; пустой вариант удаляется.
Неизвестное значение не подменяется известным из соседнего объявления. История физических характеристик здесь не заявлена.

**Точные строки примера.**

| Таблица | Содержимое |
| --- | --- |
| Property | `id=7`; адрес «Самара, ул. Учебная, 10», комнаты `2`, этаж `5` имеют `ad_ids=[11,12]`; площадь: `45.20→[11]`, `45.00→[12]` |
| Ad | `id=11, property_id=7, source_code=cian, external_id=C101, price=6800000, status=active` |
| Ad | `id=12, property_id=7, source_code=domclick, external_id=D202, price=6950000, status=active` |
| PriceChange | `id=101, ad_id=11, observed_at=t1, price=6800000, deal_type=sale` |
| PriceChange | `id=102, ad_id=12, observed_at=t1, price=6950000, deal_type=sale` |

При следующей цене Циан `6700000` обновляется Ad 11 и добавляется PriceChange `103→Ad11, t2, 6700000, sale`.
Повторная загрузка оставляет две Ad и три PriceChange. Снятие Циан меняет статус Ad 11; объект остаётся доступен через Ad 12.
При позднем сопоставлении до него существуют Property 7 с Ad 11 и Property 8 с Ad 12.
Одна транзакция объединяет наборы утверждений в Property 7, переносит FK Ad 12 и удаляет Property 8; цены не перепривязываются.

**Цена подхода.** JSON здесь нужен не для произвольного сырого ответа, а для типизированных утверждений о физических характеристиках.
FK внутри JSON база не проверяет: catalog обязан проверять принадлежность Ad объекту и поддерживать ссылки при изменениях.
Фильтрация и индексы сложнее обычных колонок: нужно извлечь физический профиль конкретного Ad из facts.
Без таких утверждений обычная Property с одной площадью потеряет расхождение либо даст неверный фильтр по источникам.
Это жизнеспособный, но существенно более сложный способ выполнить требование «физические сведения только в Property».

## Вариант 2. Характеристики у Ad, плоская связь на реальное объявление

**Сущности и связи.** Property отсутствует; Ad дополнительно содержит нормализованные физические характеристики обычными колонками.
У Ad есть обязательный self-FK `identity_ad_id → Ad.id`: ссылка на реальное объявление, выбранное представителем группы совпадений.
Каждая Ad ссылается ровно на одного представителя; представитель имеет `identity_ad_id=id`; на него ссылаются 1:N Ad.
Одиночная Ad ссылается на себя. Это ссылка на сохраняемую публикацию, а не случайный идентификатор пустой группы.
Представитель задаёт только идентичность; его сведения не объявляются истиной и не заменяют сведения других Ad.

**Точные строки того же примера.**

| Таблица | Содержимое |
| --- | --- |
| Ad | `id=11, identity_ad_id=11, source_code=cian, external_id=C101, area=45.20, rooms=2, floor=5, address=«Самара, ул. Учебная, 10», price=6800000, status=active` |
| Ad | `id=12, identity_ad_id=11, source_code=domclick, external_id=D202, area=45.00, rooms=2, floor=5, address=«Самара, ул. Учебная, 10», price=6950000, status=active` |
| PriceChange | Те же строки `101→Ad11` и `102→Ad12`, что в первом варианте |

Адрес повторяется в двух независимых сообщениях источников; копии «канонических фактов Property» здесь вообще нет.
Цена `6700000`, повтор загрузки и снятие Циан дают те же изменения Ad/PriceChange, что выше.
Снятый представитель Ad 11 сохраняется; активность группы определяется наличием активных Ad, а не его статусом.
При позднем сопоставлении сначала Ad 11 ссылается на 11, Ad 12 — на 12; затем у Ad 12 ссылка меняется на 11.
При объединении уже существующих групп представитель выбирается детерминированно по меньшему PK, все члены второй группы переназначаются транзакцией.

**Цена подхода.** Это материализованная плоская принадлежность; обход графа и транзитивное замыкание при чтении не нужны.
Взамен нужны массовое обновление при объединении групп, блокировка их представителей и повторная проверка состава после блокировки.
FK предотвращает висячую ссылку, но не цепочку `A→B→C`; правило «каждый ссылается прямо на самоссылочный корень» обеспечивает операция catalog.
Представителя нельзя физически удалить, пока на него ссылаются; снятие публикации является сменой статуса.
Подтверждение новой пары не должно без проверки совместимости присоединять все объявления двух уже существующих групп.
Ручной split/merge не предлагается; ошибочное автоматическое объединение остаётся риском качества сопоставления.

## Одинаковая проверка фильтров и рекомендация

Все условия проверяются на одном активном Ad; затем результаты сворачиваются по Property либо identity_ad_id.
В карточке показываются подходящие предложения и остальные источники с их собственными характеристиками и историей цены.
На t1 условие «площадь ≥45.10 и цена ≤6900000» находит только Циан.
Условие «площадь ≤45.10 и цена ≤6900000» не находит ничего: брать площадь Домклик вместе с ценой Циан запрещено.
После снятия Циан первое условие тоже ничего не находит; активный Домклик не получает площадь Циан.
Рекомендую вариант 2: он сохраняет противоречия без специального JSON-формата физических утверждений, а фильтры работают по обычной строке Ad.
Компромисс — обслуживание плоской принадлежности и отсутствие отдельной устойчивой сущности объекта независимо от публикаций.
Одновременно получить одну каноническую Property без вариантов значений, точные исходные расхождения и фильтры по конкретному предложению невозможно.
Выбор не определяется числом таблиц: первый вариант сложнее из-за хранения конфликтов, второй — из-за транзакционного объединения групп.

## Уточнения по независимой проверке (решения не приняты)

Оба варианта сохраняют время последнего принятого наблюдения Ad. Перед изменением фактов/фото/принадлежности/цены применяется единый барьер: более старое наблюдение не записывается; одинаковое время с прежними данными не меняет историю, противоречивое отклоняется. Любое более новое принятое наблюдение продвигает барьер, даже при прежней цене. Сначала проверяется свежесть, затем сопоставление/запись. Поэтому 100@t1,100@t3,200@t2 оставляют100. Первое значение цены и изменения deal_type/price добавляются атомарно с Ad, события неизменяемые; архивная строка не удаляется при снятии.

Для A нельзя считать JSON полностью спроектированным только по приведённым примерам: формат является специальной моделью утверждений. Обязательны фиксированный перечень физических полей и тип значений каждого, явный unknown, единственное текущее значение каждого поля для каждого Ad, все ad_ids принадлежат той же Property. Обновление/позднее объединение блокируют целую Property; FK в JSON нет. Эти ограничения — дополнительная цена A; точная полная схема JSON до реализации потребует утверждения. Это не скрывается как готовая стандартная Property.

Для B идентификатор Ad назначается до вставки (предлагается UUID), чтобы новая одиночная запись могла сразу сослаться на себя без временного нарушения NOT NULL. Числа11/12 в примере — читаемые обозначения ключей. Неявного выделения отдельной пустой группы нет; идентификатор представителя принадлежит реальной публикации. Для реализации дополнительно проверяется плоский инвариант: каждая цель identity_ad_id ссылается на себя, вся группа ссылается сразу на одного представителя; FK сам этого не гарантирует. Запись и объединение выполняет один catalog-сценарий, прямое изменение поля в admin запрещается. Следующий конкретный выбор типов ключей/контрактов не считается принятым данным сравнением.
