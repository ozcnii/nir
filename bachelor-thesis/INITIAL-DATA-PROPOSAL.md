## 2. Как сохраняется смысл без новых полей

Предлагаем один программный реестр известных ID и их смыслов в catalog: три вида и зафиксированный список регионов. Это именованные константы/данные выбранного справочника, не универсальный framework и не вторая рабочая БД. name в БД — редактируемая подпись; по ней не выбираются алгоритм и направление сбора. Например, type1 после переименования «Квартира» в «Квартиры» остаётся flat.

Для collection реестр доступен через уже принятую публичную функцию catalog.queries в виде простых значений; collector не импортирует ORM-модели и не пишет справочники. Native ID/параметр региона площадки берётся только из реальных данных соответствующего адаптера по принятому4.2/4.3/6. Внутренний region_id не вставляется в URL как якобы код площадки. Разрешённые подписи в БД не меняют канонический смысл региона в реестре.

Однозначная роль реестра: по ID определять flat/room/house или конкретный субъект, даже если подпись изменили. Initial migration содержит замороженный снимок данных с историческими моделями; она не импортирует меняющийся runtime-реестр. Историческая копия — условие воспроизведения миграции, не два независимо обновляемых live-справочника. Набор следующего релиза меняется явно новой миграцией/версией реестра, а не пересозданием ID при старте.

Добавленная администратором строка с новым ID допустима по принятому CRUD, но сама подпись не создаёт поддержку нового физического вида/субъекта/маршрута. Перед стартом запрошенное сочетание проверяется: неизвестный программному реестру либо отсутствующий в БД ID не угадывается по похожему name. Ошибка не превращается в молчаливый пропуск направления. Это уточнение существующей проверки поддержанности5.1, не новый редактор mapping.

Каталог и JSON сохраняют контракт5.5: выводят текущий name по FK, известные фильтры не меняют формат. Например, если удалённый type1 не имеет недвижимости (иначе удалить нельзя), поиск flat может дать обычный пустой результат; новый произвольный тип не начинает считаться flat по одному имени. Реестр всех89 не является утверждением, что каждый маршрут каждого источника уже проверен: применение направления опирается на фактический адаптер/4.3, без выдуманных native ID и подмены ошибок доступности отсутствием поддержки площадки.

## 3. Первая подготовка и повторные запуски

1. В первоначальной Django data migration под migrator создать3sources/3вида/89регионов. Это часть уже принятого migrate, до выдачи runtime-прав и запуска web; не network/import/AppConfig.ready. Ни объявления, ни properties/ads/price_history демоданными автоматически не наполняются.
2. Первоначальный seed ожидает пустые эти три прикладные таблицы: при неизвестном прежнем наполнении не присваивает смысл занятому ID по одному совпадению числа/названия. Остановиться с сообщением о конфликте, не удалять/перенумеровывать записи и не переписывать FK. Повтор в уже корректно подготовленной БД не запускает применённую data migration заново.
3. После вставки фиксированных PK начальные последовательности должны выдавать новые ID не ниже4для property_types и90для regions. Настройка штатным PostgreSQL/Django-механизмом под migrator; runtime не получает UPDATE/setval. При повторных операциях последовательность не отматывается назад и удалённые стандартные ID не передаются новым произвольным строкам.
4. Обычный restart и migrate без новой data migration не меняют name/enabled, не восстанавливают удалённое и не сбрасывают данные. Обновления реестра применяются явно, без автоматического пересортирования/захвата уже занятого нового PK. На конфликте новая версия не объявляется готовой.

Числа1–3 и1–89 — предложенные внутренние PK приложения. Они не взяты из кодов ФНС/автономеров или сайтов; например, Самарская область в этом зафиксированном порядке получает наш ID68, Москва82. Это не их код для обращения к площадке.

## 4. Удаление и восстановление без подмены смысла

| Действие | Предлагаемый результат |
|---|---|
| Изменить name | Только подпись; ID/FK/физический смысл не меняются. Используемую строку переименовать можно по принятому CRUD. |
| Удалить запись, на которую ссылается properties | Отказ по уже принятому P6/FK. Каскадного удаления недвижимости/истории нет. |
| Удалить любую запись справочника при активном/не завершённом/неопределённом run | Прежний серверный запрет5.4, одиночный и массовый запрос; новый скрытый запрет добавления/переименования не вводится. |
| Удалить неиспользуемую строку при завершённом сборе | Удаление остаётся разрешённым. Этот ID отсутствует в данных; соответствующий выбор для сбора недоступен/запрошенное направление отклоняется с причиной. Обычный restart строку не возвращает. |
| Через «Добавить» создать прежнее название с новым ID | Это новая строка; прежняя поддержка ID не восстановлена. Нельзя переназначить её по имени или перенести FK автоматически. Для ручного пользовательского ряда это нормальный новый ID, а не восстановление удалённого. |
| Явно восстановить удалённую стандартную запись | Создать только выбранный отсутствующий стандартный PK с исходной подписью. Для type1 вернётся прежний flat; для region68 — прежняя Самарская область. Остальные name/enabled/FK не меняются. |
| Ожидаемый PK уже существует и принадлежит подготовленному реестру | Не менять ни переименованный name, ни выключенный enabled. Сообщить, что восстанавливать нечего. |
| Исходная подпись занята другой записью | Явный конфликт с обоими ID. Ничего не объединять/не удалять/не перепривязывать. Оператор разрешает конфликт через уже существующие rename/delete (удаление лишь если разрешено), затем повторяет восстановление. |

## 5. Минимальный механизм явного восстановления

Предлагаем одну служебную Django management command restore_reference_data в catalog. Это новое небольшое действие оператора на готовом механизме BaseCommand, не новый экран/сервис/очередь. Оно выполняется одноразовым вызовом того же image app под migrator. Числовые ID и source codes выбираются явно из известного реестра; нет автоматического «восстановить всё удалённое» при запуске.

Механика: проверить версию применённых миграций/реестра и происхождение подготовленной БД; выбрать явно запрошенные строки; в одной атомарной операции создать отсутствующие по PK с defaults, существующие оставить. Используется стандартный get_or_create по PK, а не update_or_create и не поиск только по name. UNIQUE в БД защищает гонку вставки; name-конфликт даёт откат всей выбранной операции и причину. Defaults применяются только к отсутствующей строке; пропавший source при явном восстановлении создаётся с enabled=true, существующий выключенный source не включается.

Применённая первоначальная migration и запрет ручного редактирования PK в штатном admin задают контролируемое происхождение ID. При неизвестном legacy/ручном SQL-переназначении ключей команда не угадывает смысл строки: это диагностика и отдельное явное разрешение конфликта, не repair по совпавшему name. Полной защиты от произвольного вмешательства доверенного владельца БД таблица id/name не обещает.

Счётчики auto-PK не сбрасываются при восстановлении. В новой корректно подготовленной БД они уже выше стандартного диапазона; восстановление вставляет только прежние низкие PK. Нарушение этого инварианта диагностируется и исправляется служебно, без выдачи runtime setval и без отматывания счётчика. Удалённые нестандартные строки не хранятся в скрытой таблице tombstones: обычное новое добавление имеет новый ID, автоматического восстановления их потерянных значений нет.

Почему нужен отдельный явный вызов: применённая migration не повторяется, обычный loaddata способен перезаписать текущие значения, а автоматический seed при каждом старте отменил бы намеренное удаление. Механизм стандартный Django, его политика и имя — предложение проекта. Права app из принятого ролевого проекта не расширяются ради восстановления.

## 6. Проверки при будущей реализации

- Новая БД: ровно3поддержанных источника,3физическихвида,89имён snapshot; PK/FK и новые auto-ID корректны. Никакого автоматически запущенного сбора/демопубликаций.
- Rename type1/region68 оставляет выбранную физическую сущность/регион; collection получает канонический смысл через queries, а HTML/JSON — текущую подпись.
- enabled=false сохраняется после restart/migrate/явного восстановления других строк. Нет второго source для Домклик24.
- Пока run работает, нельзя удалить даже неиспользуемую строку; после его завершения можно удалить только неиспользуемую. Проверяются прямой/массовый HTTP и гонка со стартом по5.4.
- Удалённый type1 не превращает новый id4 с именем «Квартира» в flat. Запрошенный отсутствующий/неподдержанный выбор не запускается с ложной областью; каталог/JSON остаются по5.5.
- Восстановление выбранного type1 возвращает1, не создаёт ещё один id; работает аналогично для региона68. Существующие переименованные строки не перезаписываются.
- Name-конфликт и неизвестный занятый PK не приводят к merge/rekey/переносу FK; атомарная операция не оставляет частичных вставок. Auto-PK не откатывается к удалённым стандартным/пользовательским ID.
- Повторная команда без отсутствующих выбранных строк — отсутствие изменений; recovery не заменяет миграции и не возвращает обязательный backup/restore.

Это будущие проверки, не выполненные тесты. F01–F25, правила матчинга/цен/фото/права БД не переопределяются. Предложение пока НЕ ПРИНЯТО; дальнейшие порты/sandbox/init/журнал/restart/ресурсы и сводный комплект9 остаются отдельными вопросами.
