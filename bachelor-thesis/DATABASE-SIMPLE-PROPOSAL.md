# Простая схема базы данных ВКР

Статус: рекомендуемое предложение, не принятое решение. Код и миграции не создаются.
Основание: принятая INDEPENDENT-STRUCTURE.md и раздел 5 НИР.
Один проект Django/PostgreSQL; приложения `collection` и `catalog`, направление `collection → catalog`.
Нормализация и получение фотографий выполняются в collection; matching/catalog не обращаются к сети.

## Таблицы каталога

| Таблица | Основные поля | Зачем нужна |
|---|---|---|
| Region | id, name | Редактируемый справочник регионов. |
| PropertyType | id, name | Редактируемый справочник типов объектов. |
| Source | id, code UNIQUE, name, enabled, settings JSON | Три источника и параметры их сборщиков. |
| Property | id, region_id, property_type_id, address, latitude, longitude, area, rooms, floor | Физический объект с общими характеристиками для карточки, поиска и сопоставления. |
| Publication | id, property_id, source_id, external_id, url, source_features JSON, deal_type, price, currency, price_unit, observed_at, first_seen_at, last_seen_at, photos_list_status | Объявление источника, его текущие условия и происхождение. UNIQUE(source_id, external_id). |
| PriceHistory | id, publication_id, observed_at, price, currency, price_unit, deal_type | Первое полученное состояние цены и последующие изменения с контекстом сравнения. |
| Photo | id, publication_id, url, checksum, perceptual_hash, hash_version, fetch_status | Ссылки и признаки фотографий; UNIQUE(publication_id, url). |

FK публикации на объект и источник обязательны; характеристики Property, включая region_id/property_type_id, допускают NULL.
Это следует из предлагаемой политики конфликтов ниже, а не означает её принятие пользователем.
Тип сделки и единица цены — ограниченные значения, отдельные справочники им не нужны.
Примеры единиц: за объект, за месяц, за сутки; сумма — decimal, не float.
`source_features` содержит только фиксированный набор характеристик Property и состояния их получения.
Это последние нормализованные сведения источника, не EAV и не архив наблюдений.

## Почему Publication содержит условия сделки

**Рекомендуется пересмотр размещения данных A4: объединить Offer с Publication. Он ещё не принят.**
Условие предложения: одна публикация описывает одно текущее предложение.
Отдельный Offer со связью 1:1 повторяет ту же идентичность и не даёт необходимой самостоятельности.
Смысловые различия сохраняются: Property — физический объект; Publication — сообщение источника;
поля deal_type/price/currency/price_unit — условия сделки этого сообщения.
Цена не переносится в Property: источники могут предлагать один объект на разных условиях.
Отдельный Offer нужен при нескольких одновременных предложениях внутри одной публикации;
такого требования в разделе 5 НИР нет. До согласования это предложение, а не замена принятого A4.

## Общие характеристики без выбора любимого источника

Предлагаемое, пока не принятое правило: Property хранит согласованные известные значения публикаций.
Для каждого поля берутся последние известные значения из `source_features`.
Если они одинаковы после нормализации, значение записывается в Property; при конфликте — NULL.
Единственное известное значение используется; отсутствие данных у другого источника не считается опровержением.
Равенство проверяется без округления ради искусственного согласия; веса и голосование не вводятся.
Характеристики повторяются намеренно: Property хранит общее представление,
а ограниченный JSON Publication сохраняет показания источника для пересчёта и объяснения расхождений.
При обновлении публикации общие поля объекта пересчитываются в той же транзакции.
Карточка показывает расхождения с названиями источников.
**Риск этой политики:** объект с конфликтным полем выпадает из точного фильтра по этому полю.
Следовательно, правило NULL требует отдельного согласования вместе с этим ограничением поиска.
Matching использует также признаки публикаций и фотохеши; конфликт общих полей не стирает исходные сведения.
Пороги сопоставления остаются отдельным решением; ручная очередь дублей не вводится.

## Контракт приёма нормализованного объявления

Предлагаемый вход: source, external_id, url, observed_at, характеристики, условия сделки, результат списка фото.
`observed_at` — время фактического получения исходных данных, не время их поздней записи в БД.
Для необязательного поля передаётся `value(v)`, `unknown` или `error`.
`value` заменяет значение; `unknown` подтверждает отсутствие и очищает его; `error` сохраняет прежнее значение.
Для нового объявления при error значение остаётся неизвестным; ошибка записывается в CollectionLog.
Состояния характеристик сохраняются в фиксированном JSON; сохранённое после error значение остаётся последним известным.
Цена/валюта/единица/тип сделки принимаются согласованным набором: error в нём сохраняет весь прежний набор.
В неизвестной цене price=NULL; известная сумма требует известных валюты, единицы и типа сделки.
Некорректный набор отклоняется целиком; цена из одного наблюдения не соединяется с валютой другого.
Под блокировкой строки Publication сообщение с более старым observed_at возвращает `stale`, ничего не меняя.
Равное время допускает идентичный повтор (`unchanged`); противоречащие данные возвращают `rejected`.
Новое корректное наблюдение возвращает `updated`, если изменены предметные данные, иначе `unchanged`;
в обоих случаях продвигаются observed_at/last_seen_at. Недопустимые данные дают `rejected` без частичной записи.
Частичные ошибки необязательных полей обрабатываются по правилу error выше и сами по себе не отклоняют объявление.
Отдельная Acceptance не нужна: результат описывает текущий приём; точный replay прежнего ответа не требуется.

## Цена и сохранность истории

Фильтры цены и типа сделки проверяют одну Publication; совпавший Property выдаётся один раз.
Нельзя удовлетворить фильтр продажи типом сделки одной публикации, а ценой аренды другой.
История карточки разделена по источникам и публикациям, единой выдуманной «цены объекта» нет.
При первом приёме записывается состояние цены; затем сравнивается набор price/currency/price_unit/deal_type.
Изменение набора добавляет снимок, включая переход к неизвестной цене; неизменный повтор ничего не добавляет.
Контекст сохраняется, чтобы смена единицы или сделки не переписала смысл старой суммы.
Текущая цена повторяет последний снимок намеренно: по ней выполняются обычные фильтры.
История допускает только INSERT: UPDATE/DELETE запрещаются в БД для роли приложения и в Django admin.
FK истории запрещает удаление Publication; используемые Property, Source и справочники также защищены от удаления.
Вместо удаления источника используется enabled; автоматическое снятие объявления после пропуска обхода не вводится.

## Фотографии

Результат списка различает успешный список (включая пустой) и ошибку получения списка.
Успешный список заменяет текущий набор ссылок; пустой очищает его; ошибка сохраняет прежние Photo.
Для каждой ссылки fetch_status отличает успешное чтение bytes от ошибки; ошибка не равна отсутствию фото.
При успехе checksum=SHA-256 полученных bytes, perceptual_hash и hash_version описывают вычисленный признак.
При ошибке bytes ссылка остаётся, checksum/хеш очищаются; такой Photo не участвует в сопоставлении.
Это исключает использование старого хеша для изменившегося содержимого того же URL; сравниваются совместимые версии хешей.
Оригиналы фотографий постоянно не сохраняются; интерфейс использует внешние URL.

## Минимальный служебный учёт collection

| Таблица | Поля | Назначение |
|---|---|---|
| CollectionRun | id, started_at, finished_at, status, stop_requested | Запуск и остановка единственного последовательного сбора. |
| CollectionLog | id, run_id, created_at, level, source_id nullable, message | Ход работы и ошибки в админке. |

PostgreSQL-блокировка ограничивает одновременный сбор; status не заменяет блокировку.
Сеть предшествует транзакции; публикация, условия, фото, общие характеристики и история записываются атомарно.
Повтор после прерывания использует уникальный ключ публикации; новый ключ проходит matching по объектам.
JSON и HTML используют общие выборки. Таблицы наблюдений, журнал ответов API, брокер и новые очереди не нужны.
