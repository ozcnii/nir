# Пункт 9 — журнал, служебное состояние и перезапуск

**ПРИНЯТО.** 18 ноября 2026. Остановка/аренды/launcher и профиль браузера уже приняты. Ниже конкретизация файлового состояния и журнала, предусмотренных4.3/5.4; приложение, конфигурации, файлы рабочего состояния и volumes не создавались, процессы не запускались.

## 1. Где и что хранить

| Место | Содержимое и срок жизни |
|---|---|
| Принятый volume PostgreSQL | Объявления, недвижимость, цены, справочники и штатные таблицы Django. Схема не меняется. |
| Предлагаемый named volume app_data, mount /var/lib/app | Каталоги runs/<run_id>/, в каждом state.json и events.jsonl с ротацией. Это служебные файлы, не новая БД; сохраняются при restart/пересоздании app. |
| Предлагаемый tmpfs /run/app | Control Unix socket и временные файлы управления текущим launcher. При новом контейнерном запуске создаются заново. Каталог0700/socket0600 принадлежат appUID10001. |
| Предлагаемый host runtime-каталог .local/runtime/ вне Git | Уже принятый реестр аренд/общая блокировка/идентичность управляемых контейнеров. Не смешивать с app_data и не монтировать Docker socket в web. |

В образе путь /var/lib/app заранее принадлежит10001:10001; пустой новый volume получает подготовленное содержимое/права штатным Docker copy-up. Для существующего volume права проверяются: пересборка сама их не исправляет, не выполнять слепой recursivechown чужих данных. Невозможность записать служебное состояние — ошибка подготовки, не тихий переход к /tmp.

app_data сохраняется обычным освобождением стека, как и db volume. Это требование сохранности между запусками, не возврат обязательного резервирования. Точное место host-каталога указано относительно текущего checkout; существующий общий реестр runner переиспользуется, если при реализации уже есть подходящий. Поиск аналога обязателен до создания нового механизма.

## 2. Что находится в state.json

Один файл на run; единственный писатель — launcher. Предлагаемые поля служебного формата: schema_version, run_id, instance_id, status, outcome, reason, started_at, updated_at, finished_at, selection, progress, cleanup_confirmed.

- run_id — уникальный идентификатор запуска, не PID. instance_id — новая идентичность конкретного launcher; она не переиспользуется после restart. schema_version=1 позволяет обнаружить несовместимый служебный формат.
- selection — принятый снимок выбранных source codes, region/type IDs и сделок. progress — текущий источник/этап и ранее принятые счётчики уникальных обработанных карточек/результатов. Не хранить копии характеристик квартир или объявлений.
- status: starting, running, stopping, finished, unknown. Внутренний finished допускается только после подтверждённой очистки; outcome передаёт принятый итог4.3: completed, completed_with_errors, stopped, error. Перезапуск незавершённогоrun отражается outcome=error, reason=app_restarted; в UI — «Сбор прерван перезапуском», а не новый вид успешного результата.
- finished_at может отсутствовать при unknown; cleanup_confirmed не становится true от одного exitcode/PID/освобожденияPGlock. Поле — сохранённое свидетельство решения launcher, не самостоятельная проверка живых процессов.

Текущее состояние страницы сбора запрашивается у живого launcher через уже принятый status IPC. Файл нужен для сохранённого последнего состояния и истории запусков, но не даёт права сигналить старомуPID, разрешить start/delete или считать running живым. Если launcher недоступен, показывается неизвестное состояние плюс последнее сохранённое с явной пометкой.

## 3. Один писатель и безопасная запись

Runner передаёт launcher ограниченные структурированные ready/progress/event/finish сообщения через stdout PIPE. Отдельный reader-поток постоянно читает его; stderr наследует поток контейнера. Ограничиваются длина строки/размер пакета, произвольные stdout данные не исполняются как команды или пути. Смысл стадий/reason/результатов определяет collection.runner по4.3, launcher не пересчитывает matching/цены/результатыБД.

**Управление и файловый I/O разделены.** Главный цикл launcher обслуживает stop/status, монотонные deadlines и pidfdTERM/KILL, используя короткие блокировки только для памяти. Он не пишет/flush/fsync/читает volume, не захватывает lock файлового handler, не ждёт EOF PIPE или завершения writer. Reader также не пишет файлы. Переход в stopping, отправка сигнала и отсчёт40/45секунд выполняются независимо от подтверждения записи события/снимка.

Единственный writer-поток того же процесса последовательно выполняет JSONL/logging/rotation и атомарные snapshots. Передача ему — ограниченный буфер стандартной queue.Queue, до256сообщений, только put_nowait. Это очередь внутренних сообщений в памяти одного процесса, не очередь фоновых заданий/новый сервис. При заполнении reader продолжает опустошать PIPE с отбрасыванием последующих диагностических сообщений, отмечает потерю и сообщает storage_fault главному циклу; producer/control никогда не ждут свободного места. Смысл события и его допустимый размер валидируются до очереди; никакого растущего списка на стороне producer.

Предлагаемый предел ожидания подтверждения операции writer —5секунд, проверяемый главным циклом по monotonic clock. Подтверждения помечаются run_id/instance_id и номером операции; поздний ACK не отменяет уже установленный storage_fault/остановку. Ошибка/таймаут/переполнение немедленно запрещают новые шаги и инициируют принятую остановку. Счётчики/журнал отмечаются неполными; сохранённые DBданные не откатываются. При таком отказе старые сообщения не считаются надёжно доставленными.

Финальный сохранённый outcome подтверждается только после cleanup и ACK записи финального snapshot. До этого UI показывает остановку/ошибку хранения, а не «всё сохранено». Новые run не допускаются при незавершённом writer или неизвестной сохранности. Writer не прерывается внутри файловой операции произвольным удалением файлов; eventualcleanup app выполняется по принятому условию hostаренд. Reader/writer завершаются кооперативно с ограниченным ожиданием; join/очередь/sentinel/logging.shutdown не могут стать неограниченным ожиданием в пути stop/status. Если поток не завершился, это unknown, а окончательная граница — разрешённая остановка appконтейнера с принятым Dockergrace60секунд, не заявление о выполненномfinally. На этапе реализации нужно исключить также неограниченный atexit/loggingshutdown; при I/Oзависании нормальныйвыход не обещается.

До старта ребёнка initialstate должен получить ACK; если writer недоступен, runner не запускается. Операция может оставаться starting с быстрым ответом управления, пока главный цикл проверяет её deadline; не блокировать HTTPhandler ожиданиемfsync. На штатном работающем writer сохраняется один процесс-писатель файлов, никакого RotatingFileHandler в runner/HTTPworkers. Выбранные pipeline/ACK — новое предложение, не уже реализованный протокол. Unix control socket сохраняет start/stop/status; публичныйJSON5.5 не меняется.

state.json обновляется через временный файл в том же каталоге: записать полный валидный JSON, flush/fsync, os.replace, fsync родительского каталога. При ошибке до replace сохраняется старый корректный snapshot; если replace уже прошёл, а fsyncкаталога отказал, новый файл может читаться, но его сохранность после сбоя не подтверждена. Такая ошибка не считается успешнымACK. Остатки временных файлов после падения не являются состоянием; их можно удалить лишь после подтверждения отсутствия прежнего писателя. Атомарный rename не объявляется общей транзакцией с PostgreSQL или гарантией любого диска.

Порядок для progress: сначала реальный результат catalog.services/commit, затем событие/счётчик. При падении между ними DBданные могут быть новее журнала/snapshot: прежние committedзаписи не откатывать, точные счётчики и успешный итог не восстанавливать по догадке. Для аварийногоrun UI отмечает итог/счётчики как неполные. Исследовательские измерения7 не заменяются этим техническим журналом.

## 4. Журнал и ограничения объёма

Каждое событие — JSONLстрока с time, run_id, seq, source при наличии, stage, level, publication_key при наличии, outcome/reason и коротким message. seq монотонен внутри run и задаёт порядок; фильтры source/level и выбор run по уже принятому5.4. Просмотр только для администратора, строки выводятся как текст с HTMLэкранированием. run_id валидируется, путь выбирает сервер из реестра: пользователь не передаёт произвольный filesystempath.

Не записывать пароли, cookies, токены, полные HTML/APIответы, исходный текст объявления, фото или безусловный str(exception). Сообщение строится из понятного reason и разрешённых технических полей. Пример: «Циан, карточка123: таймаут; повторная попытка неуспешна». Это диагностика сбора, не копия сайта и не отдельный аудит всех действий администратора.

Предлагаемые простые пределы: один сериализованный event до4KiB; events.jsonl примерно5MiB плюс2резервных сегмента ротации — около15MiB на run. Храним последние10завершённых запусков плюс текущие/unknown; активный, повреждённый или неподтверждённыйrun не удаляется ради лимита. Поэтому это не строгая общая квотаvolume: защищённые каталоги могут накапливаться; при исчерпании места действует политика ошибкиwriter ниже. Это ограничение технического журнала, не объёма БД/собранных объявлений и не обязательный бессрочный архив. Ротация отбрасывает самые старые события; UI показывает, что начало журнала удалено. Последние события и snapshot остаются, итог запуска не вычисляется по числу оставшихся строк.

Очистка только целых старых завершённых run-каталогов под координацией launcher после подтверждённогоcleanup. Сохранить текущий иunknown, не идти по symlink за пределы app_data, не трогать db/hostleases/исследовательские файлы. При просмотре совпавшая с очисткой смена набора файлов отражается как «Журнал изменился/удалён по сроку хранения», не как пустой успешный журнал. Очистка не является правкой properties/ads/history.

JSONLпосле аварии может иметь оборванную последнюю строку: валидные строки показываются, журнал помечается неполным; старый событийный файл после аварии не дописывается, прерывание отражается в state.json. Повреждение в середине, недоступныйфайл и пустойжурнал различаются. Нечитаемый state.json не заменяется пустымidle; неизвестнаяschema/corruptsnapshot сохраняются для разбора и показываются с ошибкой. Исторические файлы не исполняются и не содержат пригодных для восстановления pidfd.

Служебные сообщения launcher/web и stderrконтейнера отдельно направляются в Docker logging с предлагаемым localdriver/max-size10m/max-file3, mode=non-blocking/max-buffer-size1m; PostgreSQLтакже имеет ограниченныйDockerлог. Неблокирующая Dockerдиагностика может терятьстроки при переполнениибуфера; она не заменяет файловыйжурнал/state и не является надёжнымаудитом. Ротация stdout не удаляет events.jsonl и наоборот. События каждого объявления не дублируются автоматически во все потоки. Файловыйжурнал collection остаётся источником экрана5.4, dockerlogs — диагностика запуска/ошибки самого хранилища журнала.

Если запись журнала/state перестала работать (diskfull/permission/I/O), launcher сообщает это через живойstatus иstderr, прекращает новые шаги и инициирует принятую остановкуrun. Стандартное logging.handleError не считать исключением, автоматически дошедшим до caller: ошибка writer должна явно менять состояние, не проглатываться. Текущая атомарная запись завершается/откатывается штатно; уже committedданные сохраняются. При неудачной записи финального snapshot нельзя показывать «всё сохранено». Чтениежурнала не должно тайно запускать новыйсбор/восстанавливать данные.

## 5. Первый старт и перезапуск

Предлагаем restart:no для app/db: локальный стек запускает только проектныйrunner, без бесконечного самостоятельного перезапуска/сбора после ошибки. Это новое предложение эксплуатации, не изменение принятого правила ручного повторного запуска4.3.

1. Hostrunner под уже принятой координацией аренд проверяет, что прежний управляемыйapp данного app_data действительно остановлен. Одного heartbeat/PID/state.instance_id недостаточно. Если старыйapp жив либо проверка неизвестна — не начинать recovery/не запускать второго писателя общего volume. Предыдущие результаты и текущие аренды не удалять.
2. Новый launcher получает эксклюзивный flock на app_data/.owner.lock на весь срок жизни, создаёт новыйinstance_id и новый control socket в/run/app. LockFD не наследуют web/runner. generationидентифицирует экземпляр, но не подменяет исключение старого владельца; файлlockне удаляется/не заменяется ради захвата занятойблокировки.
3. Сначала обычные принятые проверки доступностиБД/migrate--check и правvolume. Нет автоматических migrate/reset/seed/сбора. Runtimeпроверкипроцессов иDBlock нужны независимо от последнегостатусафайла.
4. При подтверждённой остановке прежнего app/очистке его namespace старые starting/running/stopping/unknown отмечаются как прерванные: finished/error/app_restarted, cleanup_confirmed=true именно на основании подтверждённого прекращения старого контейнера. Не считать прежнюю работу успешной, не присваивать точные счётчики. Уже корректный терминальныйoutcome не менять.
5. Если прежний snapshotповреждён/неизвестнойверсии, сохраняется ошибка истории без догадки о прежнемoutcome. После подтверждённойочисткистарогоapp можно создать новыйrun с новымID; это не восстановлениестарогосостояния. Покаочистка/ownershipнеподтверждены — unknown, start/deleteнедоступны по принятому правилу.
6. Каталог/цены/справочники/настройки сохраняются вdbvolume. ФотоURLсохраняются по принятомуконтракту; доступностьвнешнихкартинок послеrestart не гарантируется. Журнал сохраняется вapp_data в пределахретенции.
7. Сбор запускается только вручную, выдачи обходятся сначала. Известныйключ обновляетпрежнийads, неизменнаяпарацены не плодитисторию. Старыеstopсrun_id не затрагивают новыйrun. Возобновления с checkpoint/очереди работы не появляется.

Перезапуск толькоdb при живомapp — потерясоединения/PGlock и ошибкаrun по4.3, не разрешение продолжать запись безlock. После восстановленияdb нуженновыйручнойrun; очисткастарогоисполнителя подтверждается отдельно. ПокаБДнедоступна каталог показываетошибку, не пустые/стёртые данные.

## 6. Будущие проверки

Сейчас проверены документы/первоисточники, не программа. При разрешённой реализации нужны:

- Обычный stop/start и пересозданиеapp: DBданные иapp_data сохраняются, socket/instanceобновляются, сбор сам не начинается.
- Crash в starting/running/stopping и междуDBcommit/event/state: прежнийrun не «работает»/неуспешен по догадке, результатыБД сохранены, счётчикипомечены неполными; старыйstop не влияетна новыйID.
- Атомарный snapshot/остаточныйtemp/повреждённыйstate/обрывпоследнейJSONLстроки/ошибкавсередине: разные UIсостояния, безложногоidle/пустогожурнала/скрытогосброса.
- Дваwebworker/дваstart иrotation: файлыпишеттольколauncher; PIPEпостоянночитается; зависшийотправитель/слишкомдлиннаястрокане блокируютstop/status. Метаданные/runid/фильтры иHTMLэкранированиесохраняютконтракты5.4/5.5.
- Достижение5MiB/несколькихротаций/11завершённыхrun: удаляютсятолькостарыетерминальныежурналы, активные/unknownиDB/исследованияне затронуты; частичностьвидна. Чтениеприrotation/cleanup не изображаетсяпустымуспехом.
- Diskfull/permissionerror: сохраняетсявалидностьатомарногоснимка с учётомошибкипослеreplace, ошибкаwriterнепроглатывается; runостанавливаетсяпо принятому40/60сроку, committedданныеостаются. Ошибкафинишнойзаписинемаскируетсяуспешнымитогом.
