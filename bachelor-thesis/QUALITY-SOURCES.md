# Готовые практики качества Python/Django: предложения для согласования

Статус: исследование первичных источников от 16 ноября 2026 года. Все рекомендации ниже — предложения, не принятые решения. Инструменты не установлены, конфигурации и правила агента не включены. Применимость Django проверена для предлагаемой версии 5.2; стек Python/Django/PostgreSQL уже принят владельцем; конкретные версии и новые инструменты ещё предложены.

## Что предлагают официальные источники

| Область | Подтверждённая практика и источник | Предложение для проекта и граница применения |
| --- | --- | --- |
| Python: поиск типичных ошибок | Ruff предоставляет `ruff check`, выбор правил и автоматические исправления. Небезопасные исправления могут менять поведение; по умолчанию применяются только безопасные. [Документация Ruff](https://docs.astral.sh/ruff/linter/) | Предлагается один Ruff для Python. Сначала согласовать небольшой фиксированный набор правил; не включать все правила и preview автоматически. При проверке использовать `ruff check .` без исправления файлов. |
| Python: форматирование | `ruff format --check` проверяет формат без записи. Форматтер ориентирован на совместимость с Black, но сам не сортирует импорты: это делает правило `I` линтера. [Форматтер Ruff](https://docs.astral.sh/ruff/formatter/) | Предлагается Ruff formatter вместо параллельной установки Black и isort. Правила импортов и длину строки согласовать в одном месте. Это рекомендация по сокращению дублирования инструментов, а не требование Django. |
| Django: стиль | Django описывает PEP 8, 4 пробела для Python, 2 для HTML, Black, flake8, isort и pre-commit. Страница прямо относится к коду, включаемому **в сам Django**, и просит учитывать окружающий стиль. [Coding style](https://docs.djangoproject.com/en/5.2/internals/contributing/writing-code/coding-style/) | Предлагается использовать соглашения о читаемости, именовании и организации Django-кода как ориентир. Нельзя выдавать весь набор инструментов разработчиков фреймворка за обязательный стандарт любого Django-приложения. Ruff — отдельный предложенный выбор. |
| Django: проверка поведения | Django использует стандартный `unittest`; `django.test.TestCase` даёт изоляцию работы с БД. Штатный runner запускается через `manage.py test` и поддерживает выбор конкретных тестов. [Writing and running tests](https://docs.djangoproject.com/en/5.2/topics/testing/overview/) | Предлагается начать со штатного runner, без обязательного pytest-плагина. Тестировать результаты сбора/нормализации/сопоставления на контролируемых данных и пользовательские права/формы/просмотры по затронутым сценариям. Точный состав тестов — после утверждения требований к реализации. |
| Django: конфигурация | System check framework выявляет распространённые проблемы проекта статическими проверками. [System checks](https://docs.djangoproject.com/en/5.2/ref/checks/) | Предлагается штатный `manage.py check`. Успешная проверка не доказывает корректность алгоритмов, страниц или доступа к внешней площадке. Собственные проверки пока не предлагаются. |
| Django: безопасность | Django документирует ограничения экранирования шаблонов, осторожность с `safe`/`mark_safe`, защиту CSRF и особенности SQL. Перед развёртыванием рекомендует checklist; `check --deploy` выполняет только часть проверок и должен запускаться с production settings. [Security in Django](https://docs.djangoproject.com/en/5.2/topics/security/), [Deployment checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/) | Предлагается опираться на встроенные формы, ORM и защиту шаблонов, проверять права доступа отдельными сценариями. `check --deploy` — при подготовке развёртывания, не обязательный барьер для каждого локального изменения. Этот список не является полным аудитом безопасности. |
| Автозапуск проверок | pre-commit управляет готовыми Git hooks. По умолчанию `pre-commit run` проверяет staged-файлы; `--all-files` подходит для полного запуска и CI. Во время commit незаписанные в index изменения временно убираются. [Документация pre-commit](https://pre-commit.com/#usage) | Предлагается как отдельная опция удобства после выбора проверок. Если принят — одни правила локально и в CI, фиксированные версии hooks. Hooks не заменяют CI и не должны автоматически добавлять изменения в index. |
| Зависимости | uv разделяет описание зависимостей, lockfile и синхронизацию окружения. `uv run --locked` отказывает при устаревшем lockfile, `--frozen` пропускает проверку актуальности; `uv lock --check` проверяет соответствие. `uv sync` по умолчанию удаляет лишние пакеты из проектного окружения. [Locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/) | Предлагается uv с сохраняемым в Git `uv.lock`, если владелец выбирает этот менеджер. В CI — locked-режим; обновления зависимостей — отдельным изменением. Lockfile фиксирует разрешение зависимостей, но не доказывает отсутствие уязвимостей и не воспроизводит внешние сервисы. |
| Проверка типов | mypy рекомендует начинать с части кода, хранить единые настройки и версию, предотвращать новые ошибки через CI. [Using mypy with an existing codebase](https://mypy.readthedocs.io/en/stable/existing_code.html) | Предлагается отдельно рассмотреть типизацию границ модулей сбора/обработки. Полный strict-режим всего проекта с первого дня пока не предлагается. Непроверенные динамические участки и `Any` ограничивают пользу анализа. |
| Типы Django ORM | django-stubs предоставляет stubs и mypy plugin, таблицу совместимости версий. Авторы прямо пишут, что это независимый проект, **не официальный проект Django**. Plugin использует Django runtime для получения сведений о моделях и может падать при неработающем приложении. [Официальный репозиторий django-stubs](https://github.com/typeddjango/django-stubs#readme) | Предлагается только совместно с решением о mypy и после проверки совместимости выбранных Python/Django/mypy. Слово «официальный» здесь означает документацию самих авторов инструмента, а не одобрение Django. |
| Django templates | djLint поддерживает lint, проверку/исправление форматирования и профиль `django`. [Официальный репозиторий djLint](https://github.com/djlint/djLint#readme) | Предлагается как отдельная опция, если будут выбраны Django templates. Ruff не покрывает HTML-шаблоны. Проверка шаблонов не заменяет просмотр целых страниц в браузере и проверку форм. |

## Предлагаемый минимальный набор для первого решения владельца

Для принятого Django предлагается согласовать: Ruff lint/format; штатные Django tests и system checks; фиксируемое окружение зависимостей. uv — рекомендуемый кандидат менеджера, а не уже выбранная технология. pre-commit, mypy/django-stubs и djLint можно утвердить отдельно; оснований делать весь перечень обязательным сейчас нет.

Обязательность команд, наборы правил, версии, длина строки и уровень типизации пока не установлены. Команды в таблице — иллюстрации готовых механизмов, не разрешение их запускать или создавать инфраструктуру проекта.

## Предлагаемая основа правил агента

[AGENTS.md](https://agents.md/) — открытый Markdown-формат инструкций для coding agents; обязательных полей у него нет. Рекомендуемые темы: контекст проекта, команды установки/проверки, стиль, тестирование, безопасность. Это формат передачи правил, не самостоятельный стандарт качества Django и не техническое средство запрета изменений. Точное наследование зависит от клиента; [документация Codex](https://developers.openai.com/codex/guides/agents-md/) описывает чтение глобальных и проектных инструкций и приоритет вложенных файлов.

Для согласования предлагается короткий корневой `AGENTS.md` будущего приложения со следующими правилами:

1. Реализовывать только утверждённый пакет требований и решений; новые зависимости, изменение стека, полей, алгоритмов и критериев качества сначала предлагать владельцу.
2. Сначала находить существующий механизм; сохранять соседнее поведение и изменения владельца. Не добавлять отдельный слой ради самого слоя.
3. Использовать утверждённые конфигурации инструментов как источник механических правил; не дублировать длинные перечни линтера в инструкции агенту.
4. Проверять затронутые сценарии; до запуска называть риск, после — фактический результат и непроверенное. Успешный lint не называть проверкой поведения.
5. Отличать fixtures от реального внешнего источника, локальные результаты от production и предположения от решений.
6. Не ослаблять проверки и не добавлять подавления ради зелёного результата без объяснения конкретной причины.
7. После изменения пользовательских страниц просматривать результат в целевом браузере; перед работой с данными и секретами учитывать утверждённые границы доступа.

Это текст предложений, а не активная инструкция. Создание действующего `AGENTS.md`, настроек Ruff, hooks, CI и lockfile возможно после решения владельца.

Для Django ссылки закреплены на 5.2, поскольку эта версия фигурирует в техническом предложении; версии остальных инструментов здесь намеренно не утверждены.
