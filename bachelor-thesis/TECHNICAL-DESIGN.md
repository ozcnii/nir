## Что является основанием

Функционал — НИР и PLAN.md; учебные документы — requirements/. Django, PostgreSQL и прочие перечисленные инструменты дают готовые механизмы. Разбиение нашей программы, схема предметных данных, правила сопоставления и цели эксперимента являются адаптацией под задачу и требуют подтверждения. ## D1 Структура и выполнение

Предлагается стандартный Django project без собственного фреймворка и отдельного клиентского приложения:

```text
app/
  config/                 настройки, URL, WSGI/ASGI
  collection/             источники, задания, три сборщика, сохранение наблюдений
  catalog/                объявления, объекты, сделки, нормализация, каталог
  matching/               признаки, кандидаты, сравнения, ручные решения
  templates/              страницы Django
  static/                 стили и необходимые скрипты
  tests/                  общие сценарии; тесты модулей рядом с модулями
  manage.py
  pyproject.toml
  uv.lock
  .pre-commit-config.yaml
  AGENTS.md
  CODING.md
```

Фото/сырьё — отдельный каталог media, не Git; ссылки и контрольные суммы — в PostgreSQL. Названия файлов здесь являются проектом, эти папки пока не создаются.

HTTP-запрос страницы не выполняет долгий сбор. Отдельный процесс через стандартную management command Django забирает задания из PostgreSQL. Задания: queued → running → completed/failed; запрос остановки → stopping → stopped. Короткая транзакция и блокировка строки закрепляют задание за исполнителем; heartbeat, идентификатор попытки и контрольная точка позволяют обнаружить оборванную попытку. Повторные записи защищены уникальными ключами. Остановка кооперативная между операциями с заданным тайм-аутом, не мгновенное убийство процесса. Альтернатива — Celery с брокером; для выбора предлагается процесс Django и PostgreSQL без дополнительного брокера. Это новое решение D1.

Два интерфейса сборщика: перечисление ссылок со следующей контрольной точкой и получение карточки по ссылке. Результат карточки: source/external_id/url, момент наблюдения, исходные поля, категория, сделка, цена/валюта/период, характеристики, фото, происхождение полей. Ошибки транспорта, разбора и валидации различаются. Сетевая ошибка не является признаком снятия объявления. Парсер имеет версию, исходный ответ и ссылка сохраняются для повторной проверки.

## D2 База данных

Во всех таблицах ID bigint; время timestamptz/UTC; деньги numeric, не float. Предлагаемые основные таблицы:

| Таблица | Поля и связи |
|---|---|
| Source | code unique, name, base_url, enabled, параметры сбора без секретов |
| CollectionRun | source FK, состояние, started/finished, heartbeat, попытка, контрольная точка, счётчики, ошибка, stop_requested |
| Publication | source FK, external_id, url, first_seen, last_seen, last_success, состояние, последняя успешная версия |
| Observation | publication FK, run FK, captured_at, payload_hash, исходные поля JSONB, нормализованные поля, версия парсера/нормализации, причина ошибки |
| Property | категория, адрес по частям, координаты, площади с обозначением вида площади, комнаты, этаж/этажность; источник каждого выбранного значения |
| Membership | publication FK unique, property FK, основание связи, manual/auto, версия решения |
| Offer | publication FK, вид сделки, активный интервал; отдельная сущность от физического объекта |
| PriceObservation | offer FK, observation FK, цена numeric, валюта, период оплаты, момент наблюдения |
| Photo / ObservationPhoto | SHA256 unique, путь, размер, perceptual hash/версия; связь с наблюдением, исходный URL и позиция |
| MatchRun / MatchPair | версия метода/параметры; два publication FK в упорядоченной паре, признаки, оценка, решение и причина |
| ManualDecision | пара/публикация, same/different/assign/split, пользователь, причина, время; история неизменяема |
| DictionaryEntry / Event | справочники с уникальным типом/кодом; события задания/операции/ошибки с уровнем и контекстом |

Пользователи и разрешения — штатные Django auth. Внешние ключи сохраняют целостность; исходные наблюдения не удаляются при объединении или разделении объектов. Состав нормализованных полей Observation: регион, населённый пункт, улица, дом/корпус, координаты, вид недвижимости, рынок первичный/вторичный, общая/жилая/кухонная/земельная площадь по отдельности, комнаты, этаж и этажность. Неизвестное значение — NULL, не ноль. Новостройка — признак рынка, а не предположение о типе сделки.

Уникальность: (source, external_id); (publication, run) для успешного наблюдения в пределах прохода; (observation, offer) для цены; (match_run, left_publication, right_publication). Повторная доставка одной операции не создаёт дубль. Следующий проход сохраняет новое наблюдение даже при прежней цене: это доказательство повторного наблюдения. График может сворачивать неизменные участки, база их не теряет.

Индексы: внешние ключи; publication(source,last_seen); observation(publication,captured_at); price(offer,captured_at); property(region,category,rooms), адрес и площадь; состояние/время заданий; обе стороны пар. Индексы уточняются по реальным запросам, без индекса на каждое поле. Невозможные отрицательные цены/площади отвергаются; противоречивые положительные значения сохраняются с признаком конфликта.

## D3 Нормализация и обновление

Поток: ссылка → исходная карточка → проверка идентификатора → нормализованное наблюдение → цена/фото → кандидаты на совпадение. Сохранение одного наблюдения и связанных строк — короткая атомарная транзакция; сетевые запросы вне неё.

Адрес: Unicode/пробелы/сокращения по редактируемому справочнику; корпус и строение сохраняются отдельно. Координаты используются из источника; при отсутствии остаются пустыми. Внешний геокодер не добавляется без отдельного выбора.

Рубли, месяц и сутки не смешиваются; отображается исходная единица. Противоречие площадей 110/103.5 сохраняется с указанием вида поля и источника. Предлагается автоматически выбирать значение только при непротиворечивых наблюдениях; конфликт показывать в карточке, а ручной выбор записывать отдельно.

Отсутствие в выдаче → не наблюдалось; ошибка загрузки → временно недоступно; явное сообщение карточки о снятии → снято. Последнее успешное наблюдение сохраняется при любой ошибке.

## D4 Сопоставление и формирование объектов

Готовые основы: blocking (отбор кандидатов, Splink), строковая близость pg_trgm, pHash из ImageHash, сравнение хешей расстоянием Хэмминга. Установка Splink не предлагается: используем описанный приём, не его обучаемую модель.

Предлагаемый алгоритм:

1. Объединение нескольких наборов кандидатов: одинаковый нормализованный дом; близкие координаты и совместимый тип; сходные фото и совместимая география. Пропуск поля не равен несовпадению. Потери каждого отбора измеряются.
2. Проверка признаков: дом/корпус, комнаты, этаж, тип, относительная разница площади, координаты, сходство нескольких фото. Цена — вспомогательная информация, не основание идентичности.
3. Объяснимый набор правил даёт same / different / uncertain и силу свидетельств. Это не калиброванная вероятность. Точные допуски/пороги предлагаются отдельной таблицей по разработочной выборке и подтверждаются до итогового теста.
4. Одно совпавшее фото не является достаточным основанием: возможны общие фото дома или планировки. Разные квартиры в одном доме и сходные планировки — обязательные негативные примеры.
5. Сначала применяются ручные same/different, затем автоматические связи. Предлагается проверять совместимость всех членов при добавлении в группу; цепочка A=B, B=C без проверки A/C не объединяется автоматически. Противоречие отправляется в очередь проверки. Альтернатива — простые компоненты связности, но они чувствительны к ошибочной связи.
6. Повторный расчёт не отменяет ручные разделения и назначения. Все изменения членства журналируются. Разные сделки остаются отдельными предложениями одного объекта.

D4 не заявляет завершённую настройку алгоритма: пороги требуют данных. Это исследовательские параметры, не выдуманные универсальные константы.

## D5 Экраны и маршруты

| Маршрут | Содержание и действия |
|---|---|
| /catalog/ | фильтры региона/категории/сделки/цены/площади/комнат/этажа; сортировка, пагинация, сброс; счётчик объектов |
| /objects/<id>/ | характеристики и конфликты, все публикации, предложения и исходные ссылки, фотографии, история цены по каждому предложению |
| /review/ и /review/<pair>/ | очередь спорных совпадений, сравнение признаков/фото, same/different; объединение/разделение с подтверждением и причиной |
| /collection/ и /collection/<run>/ | источники, запуск/остановка, прогресс/контрольная точка, последние ошибки и журнал |
| /admin/ | штатная авторизация, параметры источников, справочники, пользователи/разрешения |
| /data/v1/objects/ и /data/v1/objects/<id>/ | JSON: версия, пагинация, фильтры как в каталоге, объекты и раздельные предложения с единицами цены и источниками |

Роли: посетитель читает каталог/карточки/JSON; администратор управляет сбором, справочниками и исправлениями. Изменения только авторизованными POST с CSRF. Для каждого экрана: данные/пусто/ошибка, ошибочные фильтры с объяснением; прекращённое задание с причиной. Внешний HTML экранируется. Фильтр цены применяется к одному и тому же предложению выбранной сделки, а не к минимальной цене другой сделки в объекте.

## D6 Проверка и исследование

Функциональные критерии: повтор одного прохода не создаёт публикаций/наблюдений-дублей; новый проход сохраняет наблюдение; новая цена добавляется без изменения старой; ошибка одной карточки не теряет остальные; остановка сохраняет контрольную точку; восстановление не удваивает записи; исправление группы переживает пересчёт; фильтры и JSON дают одинаковые ID на одном срезе; резервная копия восстанавливает данные и фото; доступ к изменениям проверен для обеих ролей. Все сценарии имеют фиксированные входные данные и ожидаемые результаты.

Предлагаемые исследовательские цели, не норматив университета: precision автоматического объединения ≥0.95 и recall ≥0.90 на отложенной разметке. Показываются 95% доверительные интервалы, число объектов/пар, ошибки групп и доля uncertain; неопределённые решения не прячутся из знаменателей. Цели не являются обещанием результата: при недостижении сообщается измеренный результат и причины.

До теста отдельно подтверждаются корпус, география, баланс категорий и источников, объём разметки, правила спорных случаев, разбиение по физическим объектам/связанным фото и численные пороги. Корпус не заменяется специально подобранными удачными примерами. Сравнение: точное структурное правило → расширенные структурные признаки → добавление фото; одинаковые разбиения и кандидаты либо явное измерение влияния их изменения. Метрики отбора кандидатов, пар, групп, времени/памяти/объёма и практического поиска сохраняются с конфигурациями и исходными результатами.

## D7 Качество кода и готовые инструменты

Предлагается Python3.13/Django5.2/PostgreSQL17 (конкретные ветки дополнительно к принятому стеку). Версии библиотек и lock-файл фиксируются при подготовке реализации, установка сейчас не производится.

Первый вариант набора: Ruff check + Ruff format (единый Python линтер/форматтер); pre-commit (автоматические проверки перед коммитом); Django unittest/TestCase (штатные тесты); Playwright (основные браузерные сценарии); uv и uv.lock (воспроизводимые зависимости). Дополнительно на выбор: mypy с django-stubs для типов и djLint для Django-шаблонов. Источники и ограничения — QUALITY-SOURCES.md. Новые инструменты не установлены и не считаются выбранными.

Предлагаемые проверки перед приёмкой изменений: lint/format/typecheck, если принят; Django check; проверка отсутствия забытых миграций; затронутые содержательные тесты; для UI — браузерный сценарий, для выпуска — установка/восстановление. Проверки безопасности настройки Django — перед развёртыванием с реальной конфигурацией. Один и тот же набор автоматизируется локально и в CI; платформа CI выбирается после определения места репозитория. Процент покрытия сам по себе не является критерием качества.

## D8 CODING.md и правила для агентов

Предлагается CODING.md как краткий профиль официальных соглашений Django/Python, а не новый стиль языка: форматирование автоматическое; имена по PEP8; разделение представления и обработки; встроенные ORM/формы/auth; типы на интерфейсах обработки; небольшие функции по смыслу; ошибки с контекстом без молчаливого проглатывания; тайм-ауты сетевых вызовов; секреты вне кода/логов; миграции для изменения схемы. Абстракции вводятся при фактической необходимости, без собственного универсального repository/framework поверх ORM.

AGENTS.md — проектные инструкции агентам, а не общепринятый стандарт качества: официальная документация описывает формат и область действия, наши ограничения берём из прямых указаний пользователя. Проект: сначала читать DECISIONS/CODING/затронутый модуль; не принимать новые решения вместо владельца; режим проектирования не даёт права реализации; сохранять чужие правки; не добавлять зависимости без подтверждения; проверять реальный сценарий; не отключать lint/tests ради успеха; отдельно сообщать проверенное и непроверенное; актуализировать документацию после принятого изменения. Текст AGENTS/CODING пока является предложением, файлы с активными инструкциями не создаются.

## D9 Готовность к реализации

После подтверждения D1–D8 остаётся конкретизация исследовательской части: корпус, правила разметки, пороги, измерительная среда. Эти параметры фиксируются отдельным пакетом на основании данных, а не придумываются в качестве фактов. До реализации также требуется просмотр владельцем схемы/макетов и итоговой таблицы контрактов после его замечаний. Независимая оценка старой версии плана не является оценкой этого проекта.
