# Пункт 2 — текущая минимальная схема и контракт

Статус: весь пакет предложен, НЕ ПРИНЯТ. Код/DDL/миграции не создаются. Пять собственных таблиц, помимо штатных Django auth/admin. Названия/группировка/рублёвая политика/JSON и отказ от Run/Log моделей требуют подтверждения. Предыдущие схемы и их оценки не применяются.

## Таблицы
1. sources: code TEXT PK, enabled BOOLEAN NOT NULL. Поддерживаются avito/cian/domclick; code выбирает сборщик, отображаемый бренд задан его регистрацией. Нет отдельного id/name/settings/timeout. Технические тайм-ауты в конфигурации, не БД. Добавление неподдержанного кода не создаёт нового сборщика.
2. regions: id BIGINT PK, name TEXT UNIQUE NOT NULL. Редактируемые названия регионов; id не меняется при переименовании.
3. property_categories: id BIGINT PK, name TEXT UNIQUE NOT NULL. Категории НИР: квартира вторичного рынка, новостройка, комната, дом. Это категории поиска, не строгая классификация всех физических типов. Справочник редактируемый; id отделён от отображаемого имени. Поля для каждого языка не создаются, переводы динамических имён пока не заявлены.
4. property_ads: id BIGINT PK; property_group_id UUID NOT NULL; source_code TEXT FK sources.code; external_id TEXT NOT NULL; url TEXT NOT NULL; region_id BIGINT FK regions.id NULL; property_category_id BIGINT FK property_categories.id NOT NULL; address TEXT NULL; latitude/longitude NUMERIC NULL как совместная пара; area_m2 NUMERIC NULL CHECK>0; rooms SMALLINT NULL CHECK>=0 (0=студия); floor SMALLINT NULL (подвальные этажи допускают отрицательное); floors_total SMALLINT NULL CHECK>0; deal_type TEXT CHECK sale/rent_month/rent_day; price_rub NUMERIC(18,2) NULL CHECK>=0; photos JSONB NOT NULL (массив); photos_observed_at TIMESTAMPTZ NULL; observed_at TIMESTAMPTZ NOT NULL; status TEXT CHECK active/removed. Все поля кроме явно NULL обязательны. UNIQUE(source_code,external_id).
5. price_history: id BIGINT PK; ad_id BIGINT NOT NULL FK property_ads.id; observed_at TIMESTAMPTZ NOT NULL; deal_type TEXT NOT NULL с теми же значениями; price_rub NUMERIC(18,2) NULL CHECK>=0; UNIQUE(ad_id,observed_at). Записывается первая цена (в том числе неизвестная) и далее только изменение пары deal_type/price_rub. Текущая цена в ad — последнее известное наблюдение, история — прошлые изменения, это различающиеся состояния. События не обновляются/не удаляются, в admin read-only; рабочие операции и права БД должны защищать историю. Связанные записи справочников/источников/объявлений защищены от удаления; источники выключаются, объявления помечаются removed.

Начальные индексы: уникальные ключи выше; property_ads(property_group_id); внешние ключи регионов/категорий; UNIQUE(ad_id,observed_at) поддерживает историю. Лишний индекс source_code поверх ведущего столбца UNIQUE не нужен; JSON-индекс не нужен без запроса. Другие индексы выбирать по фактическим запросам, не на каждый столбец.

## Смысл группировки
property_group_id — UUID-метка, не FK. Характеристики существуют только в property_ads. Совпавшие объявления получают одну метку, неподтверждённое объявление — новую. Нет отдельной таблицы объекта, первой главной публикации, кэша общих полей, корневой публикации и цепей. Поиск применяет все фильтры к одной активной строке ad, затем выдаёт группу один раз. Карточка показывает значения с источниками, расхождения не скрывает и не усредняет. Цена и площадь разных ads не образуют вымышленное предложение.

Карточка открывается по стабильному property_ads.id, например /ads/101/. Из его актуальной метки выбираются остальные участники. UUID группы не является постоянной публичной ссылкой. При новых фактах/фото matching может пересмотреть принадлежность и объединить две существующие группы: в одной транзакции выбрать один UUID и перепривязать участников обеих групп. Постоянные ad.id сохраняются. Один последовательный процесс выполняет сопоставление/запись; публичные/admin формы не разрешают менять группу напрямую. При появлении параллельных писателей потребуется общий протокол блокировки. До merge проверяется совместимость групп, а не только цепочка отдельных пар. Ручное исправление и автоматическое разделение ошибочно объединённых групп не добавляются.

## Рубли
price_rub — сумма в RUB: sale за объект, rent_month за месяц, rent_day за сутки. Валюту сборщик обязан проверить по источнику перед заполнением. Нерублёвая или нераспознанная валюта при известной цене — ошибка нормализации и пропуск пакета с диагностикой; нет молчаливого назначения RUB и конвертации. Явно неуказанная цена — NULL. Это ограничение проекта, а не факт, что источники никогда не публикуют другие валюты.

## Фото
photos — фиксированный JSON-массив [{url,phash,hash_version}]; url обязательно, phash и hash_version либо обе строки, либо обе NULL. Порядок массива сохраняет порядок источника; дубли URL отклоняются валидатором. Формат хеша/совместимость определяются hash_version, конкретная версия/порог выбираются в проекте matching, не считаются принятыми здесь. pHash — вспомогательный признак НИР, межплощадочная эффективность не проверена. Одно похожее фото не является основанием автоматического объединения.

Обновление фото передаётся блоком known(items) либо unavailable. known([]) очищает список; known(items) заменяет весь список и ставит photos_observed_at=observed_at; нескачанное фото сохраняет URL и NULL признаки без подстановки старого хеша. unavailable сохраняет прежний список/его время, не блокирует изменение цены. Ранее полученные фото не выдаются за проверенные текущим наблюдением. Файлы и SHA256 не хранятся. Отдельная таблица Photo не нужна для текущего режима чтения списка после отбора кандидатов; самостоятельный поиск по всем фотохешам этой схемой не заявлен.

## Контракт collection → catalog
catalog.accept_ad(data) — обычный внутренний вызов, не HTTP API. Все ключи передаются явно; неизвестное разрешённое значение NULL. Input: source_code, external_id, url, observed_at; region_id, property_category_id; address, latitude, longitude, area_m2, rooms, floor, floors_total; deal_type, price_rub; photos={state:known,items:[...]} либо {state:unavailable}. collection разрешает ID через существующий справочник catalog, новые справочники автоматически не создаёт. Внутренние id и property_group_id вычисляет catalog.

collection получает/нормализует данные и проверяет RUB; catalog проверяет типы, FK, диапазоны, фото-схему, целостность, время. Неизвестное допустимо как NULL; ошибка чтения не становится неизвестным значением: повреждённые обязательные данные/неверная сумма отклоняются, прежние данные остаются. Частичная ошибка списка фото специально поддержана блоком unavailable.

Для имеющегося ad: вход старше observed_at → stale без записи; равное время с теми же эффективными данными → unchanged; равное время с конфликтующими данными → conflict без записи. Любое более новое принятое наблюдение продвигает observed_at, даже если цена/поля не изменились. Поэтому price100@t1, price100@t3, затем price200@t2 оставляют100. Уникальность source/external_id препятствует новому ad при повторе. Проверка времени/изменения/история/слияние атомарны. Точное воспроизведение старого ответа не требуется, таблицы Acceptance нет.

Result: status created/updated/unchanged/stale/conflict/rejected; ad_id; property_group_id; price_changed; errors[{field,code}]. status/IDs могут отсутствовать при инфраструктурном исключении — это не успешный ответ, транзакция откатывается. При rejected IDs nullable. Повтор после commit не добавляет новую цену, повтор после rollback можно обработать заново.

Подтверждённое снятие: catalog.mark_removed(source_code,external_id,observed_at) без остальных полей. Для известного ключа применяются те же проверки времени; меняется status и observed_at, факты/цены/фото сохраняются, истории цены не добавляется. Неуспешный запрос/CAPTCHA/одиночный404/пропуск выдачи не означают снятие без однозначного ответа предусмотренного сборщиком. Для неизвестного ключа not_found, запись не создаётся; защиты будущего неизвестного ключа tombstone-журналом нет. Свежий accept_ad повторно активирует снятое объявление, устаревший — нет.

НИР5.1 сборщики в collection; 5.2 matching и группа; 5.3 текущие данные+историяцены+JSON; 5.4 фильтры по одной ad и карточка группы; 5.5 Django auth/admin, включение трёх поддержанных источников, редактирование справочников, запуск/остановка runner и просмотр файлового журнала. Таблицы логов/запусков не требуются; техническая конфигурация сборщиков живёт вне БД. Управление параметрами сборщика не исчезает, но не означает, что все параметры обязаны редактироваться из admin; полный набор доступных административных параметров остаётся частью проектирования запуска, не объявляется завершённым данным пунктом.

Это явный пересмотр физического хранения A4 и наличия collection Run/Log моделей в детализации A10; семантические функции и два приложения сохраняются. Схема и контракт на согласование, не приняты и не реализованы.

## Уточнение равных времён без digest
Для upsert с равным observed_at повтор определяется сравнением всех передаваемых предметных полей с сохранёнными, с ожидаемым status=active; внутренние id/group_id не сравниваются, поскольку их задаёт каталог. Для photos=known дополнительно необходимы точное равенство массива и photos_observed_at=observed_at. Для photos=unavailable необходимо photos_observed_at IS NULL либо photos_observed_at<observed_at. Иначе результат conflict, записи нет. Поэтому unavailable@t3 после known@t1, затем known(P)@t3 не считается повтором даже при том же массиве: состояние подтверждения фото отличается, нужен новый observed_at. Обратный порядок known@t3 затем unavailable@t3 тоже conflict. Повтор known@t3/known@t3 и unavailable@t3/unavailable@t3 распознаётся без дополнительного поля. mark_removed с равным временем возвращает unchanged только для уже removed, для active это conflict. Новое время обрабатывается по обычным правилам; при равном времени не разрешено обогащение.
Для более нового upsert сравнение предметных значений исключает обновляемые временные поля; одинаковое содержание может вернуть unchanged, при этом observed_at/photos_observed_at обновляются по известности блока. Это не обещание точного replay входного сообщения или старого ответа.

## Параметры сбора без колонки настроек
Административная форма запуска получает выбранные поддержанные источники, регион/регионы, категории и типы сделки и передаёт их существующей management command как параметры текущего прохода. Сборщики формируют из них запросы площадок. Сохранение набора настроек как профиля не требуется НИР и не вводится. Технические timeout остаются в конфигурации. Возможность просмотра и изменения этих параметров формы, включение источников и просмотр файлового журнала покрывают управление списком и параметрами в НИР5.5 без тайм-аута/JSON-настроек в sources. Это предложение взаимодействия формы и команды, не реализованная функция и не автоматическое принятие следующего пункта проектирования.
