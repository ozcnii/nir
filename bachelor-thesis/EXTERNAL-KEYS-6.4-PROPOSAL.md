# 6.4 — ключи новых форматов: принятое решение

Статус: ПРИНЯТО владельцем 17 ноября 2026: «Ок, принимаю ключи, зафиксируй». Приняты все правила этого документа, включая K1/K2. Схема и обработка повторов не меняются. Код приложения не пишется. Это спецификация нашего нормализующего правила, а не новые поля API.

## 1. Идентичность и реальные примеры

Уникальна прежняя пара (source_code, external_id). Новых источников, таблиц и колонок нет.

## 2. Уточнение K1: точный адрес и единый путь

Сначала распознаётся семейство по разобранному hostname И полному пути карточки, затем извлекается ключ. Не ищем вхождение бренда в строке URL или произвольную числовую подстроку.

- cian.sutochno.ru и domclick.sutochno.ru — только эти точные hostname; полный путь /detail/<положительный десятичный ID> с единственным необязательным завершающим slash. В ключе slash в конце отсутствует. ID начинается с1–9, далее только цифры; ведущие нули и суффиксы не поддерживаются.
- 24.domclick.ru — только этот точный hostname; полный путь /card/<UUID> с единственным необязательным завершающим slash. UUID — 8-4-4-4-12 шестнадцатеричных символов; буквы A–F приводятся к нижнему регистру. Не задаём неподтверждённых ограничений версии UUID. Ключ — /card/<UUID в нижнем регистре>.
- Основные сайты cian.ru/domclick.ru и их подтверждённые региональные поддомены сохраняют принятые правила своих конкретных карточных семейств. Специальный24.domclick.ru распознаётся отдельно, а не как региональный основной сайт. Новый неизвестный поддомен не становится региональным по одному суффиксу. Конкретные native-пути карточек и числовыеID проверяются внутри существующего адаптера; формат новых партнёров на них не переносится.
- Для новых семейств принимаются HTTP(S) URL без userinfo и нестандартного порта. Hostname сравнивается без учёта регистра. Дополнительные сегменты пути, percent-encoding идентификатора, dot-сегменты, обратные слеши и неоднозначный путь не восстанавливаются догадкой. Принимается только явно поддержанный полный путь. Query и fragment не входят в идентичность карточки; даты/гости/UTM/adt не создают новый ключ.

Реальный важный пример: публичный https://cian.sutochno.ru/detail/1906598 даёт /detail/1906598. Встроенное поле url=https://sutochno.ru/front/searchapp/detail/1906598 служит дополнительным подтверждением ID; его pathname НЕ становится вторым ключом и не меняет source_code. Источник определяет проверенный вход адаптера, а не произвольная строка или конечный хост редиректа.

Ссылки cian.sutochno.ru.example.org или /detail/1906598/other не проходят это правило. Это контрпримеры спецификации, не утверждения о реально обнаруженных объявлениях.

## 3. Уточнение K2: подтверждение ID и переходы

Для полученной активной карточки согласуются: проверенная входная публичная ссылка, фактически открывшийся публичный URL после переходов и ID самой полученной карточки из проверенного встроенного состояния.

- Партнёр Циан: ID публичного /detail/<ID> совпадает с развёрнутым data['detail:<ID>'].id. Встроенный служебный /front/searchapp/detail/<ID> не заменяет публичный путь. Не оцениваем индексы Nuxt-массива как ID.
- Домклик24: UUID публичного /card/<UUID> совпадает с inventory.searchData.id после той же нормализации регистра. inventory.data.uid не используется. Данные читаются из inline window.__SSR_STATE__, даже если одноимённое глобальное свойство уже удалено после гидратации.
- Нормальный переход с изменением query, протокола или завершающего slash сохраняет ключ при совпадении распознанного семейства, source_code и ID. Региональные переходы основного сайта допускаются по его принятому правилу, не путём отключения проверки hostname.
- Если редирект ведёт к другому ID/семейству, URL и ID расходятся либо подтвердить ID полученной карточки не удалось: результат НЕ считается active/removed исходной публикации. Для известного проверенного входного ключа — unavailable с диагностикой по существующему P4: никаких изменений ads, property_id, observed_at, цены или фото. Данные другого назначения не сохраняются вместо исходного и публикации автоматически не сливаются/не перенумеровываются.
- Если корректный входной ключ вообще не определён, конверт в catalog не создаётся; проблема журналируется в collection. Не генерируется external_id-заглушка. Невалидный конверт, всё же поступивший в catalog, обрабатывается прежним rejected.
- Явное снятие — отдельный принятый P4: достаточно достоверной отметки снятия именно для проверенного входного ключа; требовать от снятой страницы отсутствующий active-ID нельзя. CAPTCHA, выдача, главная или общий404 сами по себе таким подтверждением не являются. При неясном назначении после редиректа — unavailable.

Эти исходы не создают нового механизма алиасов/слияний/ручных исправлений. Коллектор не передаёт данные чужой карточки под исходным ключом.

## 4. Повторы и отсутствие коллизий между известными форматами

Принятый повтор той же пары обновляет прежнюю ads с прежним property_id; старое observed_at → stale, равное → ignored, более новое несовместимое deal_type → conflict после проверки времени. Смена query не создаёт копию. Разные публикации одной квартиры остаются разными ads; их физическое сопоставление отдельно.

Число основного Циан отличается от /detail/<ID>. У Домклик /detail/<ID>, /card/sale__… и /card/<UUID> — структурно разные строки. Разные площадки дополнительно разделяет source_code. Это конструктивное разделение известных форматов, а не доказательство вечной уникальности сайта на выборке. Самостоятельное повторное использование источником прежнего URL для другой публикации остаётся известным ограничением; новых полей для гипотетической защиты не вводим.
