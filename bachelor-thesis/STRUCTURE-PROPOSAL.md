# Пункт 1 — структура модульного монолита

Статус: полный пакет структуры на согласование, НЕ принят. Приложения и рабочие конфигурации не создаются. Старые варианты структуры заменены этим предложением; их оценки не переносятся.

## 1 Основание и масштаб

Одно веб-приложение: Django-проект с двумя Django apps и отдельным Python-пакетом алгоритмов; один репозиторий, одна PostgreSQL, один выпуск. Подсистемы НИР 5.1–5.5 реализуются без механического превращения каждой в Django app. Функциональный охват исходного ../thesis/nir/body.md сохраняется: три источника, нормализация, автоматическая дедупликация, хранение/история/JSON, поиск/UI, администрирование. Ручных исправлений и очереди ручной проверки нет. Фото в память, показ по URL, без постоянных оригиналов. После прерывания повторный запуск без дублей; отдельного сервиса-координатора/брокера/универсального framework не вводится.

## 2 Дерево (проект, а не созданный код)

```text
project/
  manage.py
  config/                       Django settings, urls, wsgi/asgi; только подключение
  collection/                   Django app: источники и получение данных
    models.py                   Source, CollectionRun, события прохода
    sources/                    avito.py, cian.py, domclick.py
    api.py                      получение выдачи/карточки/фото, управление проходом
    admin.py                    штатные формы источников и журнала
    management/commands/collect.py  CLI-вход в общий сценарий
    migrations/
    tests/
  realestate/                   Django app: недвижимость как предметная область
    models.py                   объект, публикация, предложение, наблюдение, цена, фотоссылка/признак
    commands.py                 приём наблюдения, запись обработки и группировки
    queries.py                  выборки для обработки/поиска/карточки
    contracts.py                простые данные обмена (без ORM/HTTP)
    views.py, urls.py, forms.py  пользовательские страницы, фильтры, JSON-ответ
    admin.py                    справочники и необходимые штатные формы
    templates/realestate/
    static/realestate/
    migrations/
    tests/
  processing/                   Python package: чистые алгоритмы, не Django app
    normalization.py            общий формат адресов, площадей, цен и категорий
    matching.py                 кандидаты, сравнение и решение о дублях
    photos.py                   признаки фото из переданных байтов
    tests/
  operations.py                 явная последовательность получения/обработки/сохранения
  tests/                        сквозные и архитектурные проверки
  docs/                         принятые решения, описание запуска/использования
  pyproject.toml                зависимости и будущие настройки после их принятия
  AGENTS.md, CODING.md           будущие утверждённые правила, пока не создаются
```

Это три модуля: collection, realestate, processing. operations.py — одна точка сборки сценария, не самостоятельная предметная подсистема/отдельный исполнитель/система задач. config — инфраструктурная конфигурация. Разбиение models.py на файлы понадобится только при фактическом росте; одинаковые папки services/repositories/utils везде не создаются.

## 3 Почему именно такие границы

collection содержит всё, зависящее от устройств площадок. realestate содержит понятную предметную область и её пользовательские действия: модели, хранение, поиск, карточки/история. Не разрываем одну предметную задачу на listings/storage/catalog. processing выделяет заменяемые исследуемые алгоритмы, чтобы они проверялись на данных без Django, сети и браузера. Нормализация находится в processing, не в каталоге/хранении. Отдельного administration нет: используем django.contrib.admin и admin.py владельцев данных; управление сбором вызывает общую операцию запуска/остановки, а не второй сборщик.

## 4 Владелец записи и зависимости

- collection единолично изменяет Source/CollectionRun/его события. Source — техническая конфигурация источника; параметры подключения не попадают в объявления.
- realestate единолично изменяет объект/публикацию/сделку/наблюдения/цены/ссылки и сохранённые признаки/решения. Физически хранит фотопризнак, но вычисление и смысл принадлежит processing. Все объявления сохраняют исходные сведения и происхождение.
- processing не имеет таблиц/ORM/записи в БД/HTTP/веб-представлений и не импортирует collection или realestate. Принимает обычные значения и возвращает значения/объяснения. На границе operations.py переводит contracts в аргументы алгоритма без собственного доменного фреймворка.
- operations.py может обращаться к публичным api.py collection, commands.py/queries.py realestate и функциям processing. Не импортирует модели для обхода владельцев, не содержит правил нормализации/совпадений. Это последовательность вызовов.
- realestate не импортирует collection и processing для запуска побочных действий. Источник публикации хранится как стабильный source_code/идентификатор, проверяемый точкой приёма; не создаётся зависимость миграций на таблицы collection. Имя/URL и прочие отображаемые сведения о происхождении сохраняются с наблюдением. Изменение технической конфигурации не стирает происхождение. Удаление источника — деактивация, не потеря записей.
- Сетевой код в collection; фото запрашиваются через него, байты передаются processing и не сохраняются. Пользовательский браузер показывает внешний URL.
- admin.py и CLI/представления — входы, не часть низкоуровневого алгоритма. CLI entrypoint и административное действие могут импортировать operations.py; операции получения/модели collection не импортируют его. Нет скрытых save-сигналов.

Граф зависимостей основных реализаций: operations → collection.api; operations → realestate.commands/queries; operations → processing. Три внутренних модуля не импортируют друг друга. Граф входов: config → views/admin/CLI → operations → публичные операции. Запрет импорта рассматривает конкретный пакет/файл, а не неверное правило, будто management command не может вызвать сценарий своего приложения. Штатные Django auth/admin подключаются без собственного модуля пользователей.

## 5 Минимальные контракты на уровне структуры

collection: получить карточку/ссылки/фото → результат или типизированная ошибка, без записи недвижимого объекта. Успех содержит source_code, external_id, URL, fetched_at, значения источника, происхождение, версию парсера.
realestate: принять исходное наблюдение с operation_id → ID/версия; выбрать необработанные → данные/версии; сохранить нормализацию/признаки → новая версия; применить автоматическое решение на ожидаемых версиях → применено/устарело; найти объекты по проверенным фильтрам → единая выборка для HTML/JSON.
processing: нормализовать исходные значения → общий формат/ошибки; вычислить признаки фото → признак/версия/checksum; сопоставить подготовленные записи/кандидатов → решение и объяснение, без изменения БД. Пороговые числа не выбираются этим пунктом.

Внутри realestate обычный ORM, без универсального repository над каждой моделью. commands/queries группируют операции, в которых есть реальная целостность или общая выборка, не дублируют каждое поле getter/setter. Публичные контракты и словарь полей версионируются при дальнейшем детальном проектировании.

## 6 Путь объявления и исключения

operations вызывает collection → realestate сохраняет исходное наблюдение → processing нормализует → realestate сохраняет результат → collection при необходимости получает фото в память → processing вычисляет признаки/сравнения на сохранённых данных → realestate сохраняет признаки и применяет решение → views выбирают и показывают объект.

При отсутствии уверенного совпадения объект остаётся отдельным; ручного экрана нет. Сетевые ошибки не означают снятие объявления. Исходное наблюдение сохраняется до нормализации. Новое наблюдение не создаёт новую публикацию: ключ (source_code, external_id). Повтор доставки одной операции отличен от следующего прохода; конкретная схема ключей — шаг проектирования БД.

Сохраняется версия/состояние обработки наблюдения. После прерывания заново запускаем проход и повторяем незавершённую обработку сохранённых данных, даже если карточка уже недоступна. Отдельной durable-очереди нет. Не обещаем возобновление с точной страницы выдачи: повторный обход допустим по решению пользователя. Операции сохранения короткие/атомарные; сеть и вычисления вне транзакций. Конкретная схема блокировок/одновременных проходов — шаг БД и исполнения, не скрыто принятое решение структуры.

## 7 Покрытие и проверка самой структуры до кода

НИР5.1 → collection; 5.2 → processing; 5.3 → realestate; 5.4 → realestate views/forms/queries; 5.5 → штатный admin + admin.py владельцев и общие операции запуска/остановки. Ничего из пяти функций не исчезло, но их число не определяет число папок.

Проверки архитектуры при реализации: запрещённые импорты между внутренними модулями; отсутствие ORM/сети в processing; отсутствие HTML-парсинга вне collection; только realestate меняет данные недвижимости; одинаковая выборка HTML/JSON; штатные admin/CLI используют одни операции. Это планы содержательных проверок, сейчас нет кода для их запуска.

До реализации независимый критик должен пройти дерево и граф зависимостей на сценариях: изменение HTML источника; новое правило адреса; новая метрика фото; новая страница фильтров; повтор после нормализации/сравнения; смена цены; деактивация источника. Проверить циклы entrypoint/operations, владельцев таблиц и границу вычисления/записи. Проверка документа не доказывает работоспособность программы.


## Уточнённые сценарии взаимодействия

- **Журнал:** collection хранит события прохода, но не разбирает чужие ошибки. operations получает результат этапа и вызывает collection.api.record_event(run_id, stage, observation_id, outcome). Ошибки нормализации/сопоставления записываются туда с этапом и ссылкой на наблюдение. realestate отдельно хранит состояние/ошибку обработки конкретного наблюдения. Это разные сведения: журнал выполнения и предметное состояние; алгоритмы processing возвращают ошибки/объяснения без собственной записи журнала. Операции повторной обработки также имеют проход/события в collection; так collection отвечает за приобретение данных и учёт запусков, но не управляет вычислениями.
- **Источник:** operations получает разрешённую техническую конфигурацию через collection.api, проверяет source_code и формирует вход приёма. realestate.commands проверяет формат и неизменность source_code существующей публикации, а не обращается к collection. Новое получение требует активного источника; повторная обработка сохранённого наблюдения разрешена и после его деактивации, использует сохранённое происхождение. Только доверенные входы operations вызывают внешнюю приёмку.
- **Недоступные фото:** состояния различаются: нормализация завершена; признаки фото полные/частичные/недоступные; сопоставление выполнено/неопределённо/не завершено. Полностью обработанным результат без необходимых данных не помечается. Ранее рассчитанные признаки можно использовать с указанием версии; новый алгоритм невозможно вычислить по исчезнувшему оригиналу. operations фиксирует ограничение, processing возвращает допустимый результат на доступных сведениях либо неопределённость, realestate сохраняет это состояние. Никакой архив фото автоматически не добавляется.
- **Повторная обработка:** отдельный CLI-вход `collection/management/commands/reprocess.py` вызывает операцию в operations. Она выбирает сохранённые наблюдения через realestate, запускает выбранную версию processing и сохраняет новую обработанную версию. Карточки источников не запрашиваются; если новая фотометрика требует байтов, получение фото запрашивается через collection по прежним URL, а недоступность фиксируется как выше. Исходные наблюдения и прежняя история цен не переписываются. Изменение справочника адресов/категорий, влияющее на нормализацию, делает затронутую версию обработки требующей пересчёта; изменение только названия отображения — нет. Конкретные версии/поля определяются в проекте БД.

Последние уточнения: деактивация источника останавливает новые сетевые обращения в том числе к фото при исторической переобработке; доступны сохранённые поля и прежние признаки, нехватка фото фиксируется. Это предлагаемая семантика настройки, пока не принятое поведение. Справочники принадлежат realestate; operations получает их значения/версию через realestate.queries и передаёт processing обычными данными, без ORM внутри алгоритма.

## 8 Критерий закрытия пункта 1

Определены корень/папки, принадлежность моделей и алгоритмов, входы/публичные операции, разрешённые импорты, путь данных/повторного запуска, размещение admin и фото, соответствие всем функциям НИР, ограничения структуры и проверки соблюдения. Пункт закрывается как ПРИНЯТЫЙ только после подтверждения пользователя. Не переносить принятие структуры на физическую схему БД, пороги сопоставления, конкретный запуск процесса, инструменты качества или реализацию.
