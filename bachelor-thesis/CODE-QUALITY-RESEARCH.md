# Качество кода модульного монолита

Исследовательская записка к [правилам реализации](../CODING.md) и [пункту 8.3](QUALITY-8.3-PROPOSAL.md). Срез кода — `8c732ae5dfd0a2e8d243bf8058dbc4053f2aee16`. Версии платформы взяты из [pyproject.toml](../implementation/pyproject.toml) и [compose.yaml](../implementation/compose.yaml). Внешние источники объясняют свойства инструментов. Границы и порядок предметных операций определяет [принятый проект](CONSOLIDATED-DESIGN-9.md). Практические выводы служат материалом для согласования правил ревью.

## Владелец правила и точки входа

- Публичный интерфейс стоит определять по вызывающим и обещанному поведению. PEP 8 рекомендует явно обозначать публичные интерфейсы и использовать `_` для внутренних имён. Django рекомендует связывать близкую логику, сокращать зависимости между слоями и держать каждое самостоятельное правило в одном месте. Для проекта это означает сохранять один путь принятия P3 и одну общую выборку для HTML и JSON, когда условия выборки совпадают. Вынос функции оправдан, если она скрывает связанное решение или устраняет повтор одного правила. [PEP 8](https://peps.python.org/pep-0008/#public-and-internal-interfaces), [философия Django](https://docs.djangoproject.com/en/5.2/misc/design-philosophies/#overall).
- Разбирать форму и маршрут следует на границе HTTP, исходные данные площадки — в адаптере collection, предметный переход — в catalog, сопоставление — на простых данных без ввода-вывода. CLI-адаптеру достаточно разобрать аргументы, применить окружение, вызвать существующий сценарий и передать его результат. В Python есть `main()` и `__main__.py`, а Django обнаруживает команды из `management/commands`. В текущем дереве уже есть [host runner](../implementation/host_runner/__main__.py), [команда восстановления справочников](../implementation/catalog/management/commands/restore_reference_data.py) и [URLconf с Django admin](../implementation/config/urls.py). [Python: `__main__`](https://docs.python.org/3.13/library/__main__.html), [Django: команды](https://docs.djangoproject.com/en/5.2/howto/custom-management-commands/), [Django: маршрутизация](https://docs.djangoproject.com/en/5.2/topics/http/urls/).
- При проверке границы проследить реальный маршрут и зависимости в обе стороны. Например, [one_card](../implementation/collection/one_card.py) извлекает карточку до записи и вызывает `accept_snapshot` через [BrowserWork.write](../implementation/collection/runner.py). Функции [matching](../implementation/catalog/matching.py) получают значения, собранные catalog. Отдельные сервисные фасады или запрет на все импорты `collection → catalog` для такого маршрута создадут лишний обход принятого контракта. [Контракт слоёв проекта](QUALITY-8.3-PROPOSAL.md).

## Валидация и блокировки

| Где | Какой результат нужен |
| --- | --- |
| Адаптер площадки, форма, CLI | Перевести внешнее представление в допустимый ввод. Сохранить различия отсутствия, `NULL`, нуля и ошибки там, где их различает контракт. |
| Операция записи | Проверить входной контракт и бизнес-инвариант в порядке, который видят вызывающие. Правила, зависящие от сохранённых данных, проверять в транзакции при нужной блокировке. |
| PostgreSQL | Защитить целостность данных для каждого пути записи с помощью применимых `CHECK`, `UNIQUE`, `NOT NULL` и внешних ключей. |

`ModelForm.is_valid()` запускает проверку включённых полей модели. `Model.save()` самостоятельно `full_clean()` не вызывает. `BaseConstraint.validate()` может сделать запрос и пропустить проверку при исключённом поле. Поэтому `full_clean()` полезен при обработке пользовательского ввода, где нужна соответствующая ошибка, а ограничения БД обеспечивают целостность при записи, в том числе при гонке. Проверка входной формы и ограничение БД могут выражать один инвариант на разных границах. Копирование предметной проверки между двумя Python-входами с одинаковым контрактом стоит проверять на возможность переиспользования. [Django: проверка модели](https://docs.djangoproject.com/en/5.2/ref/models/instances/#validating-objects), [Django: ModelForm](https://docs.djangoproject.com/en/5.2/topics/forms/modelforms/#validation-on-a-modelform), [Django: ограничения](https://docs.djangoproject.com/en/5.2/ref/models/constraints/#baseconstraint-validate), [PostgreSQL: ограничения](https://www.postgresql.org/docs/17/ddl-constraints.html).

Для записи P3 текущий [сервис](../implementation/catalog/services.py) сохраняет наблюдаемый порядок «время → конфликт типа сделки → тело снимка». Проверка тела до сверки времени изменила бы результат для устаревшего снимка с ошибочным телом. Полезно читать [регрессионный сценарий](../implementation/tests/catalog_accept/check_snapshot.py) вместе с [контрактом P3](DB-POINT2-VERIFIED-DRAFT.md), прежде чем переносить такие условия из транзакции.

В цепочке сбора и записи применяются два advisory lock, то есть блокировки по ключу, смысл которого задаёт приложение. Подготовка ролей и БД использует отдельный ключ в служебной БД.

- [Сбор и удаление справочников](https://github.com/ozcnii/nir/blob/8c732ae5dfd0a2e8d243bf8058dbc4053f2aee16/implementation/config/collection_lock.py) используют общий ключ. Сбор удерживает сессионную блокировку на физическом соединении и записывает через него. Удаление берёт конфликтующую транзакционную блокировку через `pg_try_advisory_xact_lock` и повторно читает статус launcher внутри неё по [lifecycle](PROCESS-LIFECYCLE-PROPOSAL.md). Недоступное или неподтверждённое состояние приводит к отказу. Проверку владельца соединения и повторную проверку статуса нельзя оценивать как дубликат по внешнему сходству. [PostgreSQL: advisory locks](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS), [функции блокировок](https://www.postgresql.org/docs/17/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS).
- [Приём P3](../implementation/catalog/services.py) берёт отдельный транзакционный ключ до чтения предыдущей публикации. Это сериализует решение и запись у участников протокола. PostgreSQL не заставляет другие транзакции брать advisory lock, поэтому нужно проследить всех писателей. При `READ COMMITTED` следующий запрос получает свой снимок уже после ожидания блокировки. При нескольких блокировках важен одинаковый порядок их взятия. Сетевое чтение площадки выполняется до операции записи. [PostgreSQL: advisory locks](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS), [взаимные блокировки](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-DEADLOCKS), [READ COMMITTED](https://www.postgresql.org/docs/17/transaction-iso.html#XACT-READ-COMMITTED).
- В штатном пути `BrowserWork.write` открывает внешнюю транзакцию на соединении, удерживающем ключ запуска. `accept_snapshot` на том же соединении входит во вложенный `connection.transaction()`, который Psycopg выполняет через savepoint. Выход из внутреннего блока сам по себе не фиксирует запись. При рефакторинге нужно найти внешний commit/rollback и проверить, что запись, владение ключом и сообщение об успехе следуют в прежнем порядке. [Psycopg: вложенные транзакции](https://www.psycopg.org/psycopg3/docs/basic/transactions.html#nested-transactions), [Django: `atomic`](https://docs.djangoproject.com/en/5.2/topics/db/transactions/#controlling-transactions-explicitly).

## Числа

- Точный десятичный текст или JSON-число для денег и площадей разбирается в `Decimal` до арифметики. Так уже сделано в [адаптере Циана](../implementation/collection/collectors/cian.py), где оба разбора JSON передают `parse_float=Decimal`. Обычный JSON-декодер возвращает `float` для дробного числа. `Decimal(float)` сохраняет двоичное приближение, а `Decimal(str(float))` преобразует его текстовое представление и не восстанавливает исходный текст площадки. Текущий [нормализатор](../implementation/collection/normalization.py) также принимает `float`, поэтому при изменении этого входа сначала надо проверить вызывающих и источники значений. Для монотонных таймеров продолжает подходить `float`. [Python: `json`](https://docs.python.org/3.13/library/json.html#json.JSONDecoder), [Python: `decimal`](https://docs.python.org/3.13/library/decimal.html#decimal.Decimal.from_float), [Python: `time.monotonic`](https://docs.python.org/3.13/library/time.html#time.monotonic).
- Принятый [контракт 4.2](NORMALIZATION-4.2-PROPOSAL.md) требует отклонять лишние значащие дробные разряды у денег и площадей и округлять подтверждённые координаты до семи знаков с `ROUND_HALF_EVEN`. PostgreSQL при записи в `numeric(p,s)` приводит дробную часть к заданному масштабу и округляет половины от нуля. Замена прикладной проверки приведением к типу изменит поведение. При изменении числового разбора проверить применимые случаи лишней точности, пределов, нуля, пропуска, `NaN`/бесконечности и координаты ровно на середине. [PostgreSQL: `numeric`](https://www.postgresql.org/docs/17/datatype-numeric.html), [Python: `quantize`](https://docs.python.org/3.13/library/decimal.html#decimal.Decimal.quantize), [Python: `is_finite`](https://docs.python.org/3.13/library/decimal.html#decimal.Decimal.is_finite).

## Тесты по изменённому поведению

| Риск | Чем проверить |
| --- | --- |
| Ошибка чистого преобразования, сопоставления или граничного условия | Тест с входом и наблюдаемым выходом на простых данных. Существующие примеры есть в [тестах matching](../implementation/catalog/tests/test_matching.py) и [тестах адаптера](../implementation/collection/tests/test_cian.py). |
| Нарушение commit/rollback, порядка записи, блокировки или прав | Реальный PostgreSQL. Для гонки — отдельные соединения и наблюдение за результатом после commit. Django `TestCase` оборачивает тест в транзакцию, поэтому для проверки эффектов commit/rollback в Django предусмотрен `TransactionTestCase`. Для P3 уже есть самостоятельный [сценарий PostgreSQL](../implementation/tests/catalog_accept/check_snapshot.py) с реальной ролью `app`, барьером, двумя одновременными подачами одного снимка и проверкой истории. |
| Нарушение HTTP-ответа/прав или браузерного перехода | Django client для ответа HTTP. Playwright для поведения страницы, изолированного контекста и ожидания наблюдаемого состояния. Локальная проекция карточки доказывает воспроизводимое поведение адаптера, а доступность и текущие данные площадки проверяет отдельный живой сценарий. |

Разметка Arrange/Act/Assert и минимальный выбор сценариев по риску установлены в [правилах проекта](../CODING.md#тесты-и-доказательства). Если используются двойники, проверяемое утверждение должно описывать результат сценария. Для ветки ошибки достаточно управляемо вызвать этот сбой, а свойства транзакций, прав и браузера подтверждать в соответствующем окружении. [Django: тестовый клиент и классы тестов](https://docs.djangoproject.com/en/5.2/topics/testing/tools/), [Playwright: локаторы](https://playwright.dev/python/docs/locators), [ожидания](https://playwright.dev/python/docs/actionability).

## Сложность и неиспользуемый код

| Средство | Что проверяет и как применить |
| --- | --- |
| Ruff `C901`, `PLR0912` | `C901` измеряет цикломатическую сложность функции, `PLR0912` считает ветви. Оба пригодны для разовой навигации по изменённому модулю. В существующем `[tool.ruff.lint].select` этих правил нет. Оценивать конкретное последствие: трудно восстановить порядок, одно изменение требует править несколько ветвей или важные условия разнесены. Порог линтера — его настройка, а не доказательство проблемы. [C901](https://docs.astral.sh/ruff/rules/complex-structure/), [PLR0912](https://docs.astral.sh/ruff/rules/too-many-branches/), [выбор правил Ruff](https://docs.astral.sh/ruff/linter/#rule-selection). |
| Ruff `F401`, `F841`, mypy `warn_unreachable` | Уже включены через `F` и настройку mypy. Ruff находит неиспользуемые импорты и локальные переменные, mypy предупреждает о недостижимости по результатам своего анализа типов. Перед удалением импорта проверить экспорт и регистрацию, перед удалением ветки сверить возможный внешний ввод. [F401](https://docs.astral.sh/ruff/rules/unused-import/), [F841](https://docs.astral.sh/ruff/rules/unused-variable/), [mypy 1.19.1](https://github.com/python/mypy/blob/v1.19.1/docs/source/command_line.rst). |
| Vulture | Ищет кандидатов среди функций и классов. Авторы прямо указывают на пропуски и ложные срабатывания для неявных вызовов Python. Для удаления нужно проследить Django-регистрацию, миграции, CLI, строки настроек, callbacks и публичных вызывающих. Текущего Ruff, mypy и `rg` достаточно для проверки конкретного кандидата в ревью. [Vulture](https://github.com/jendrikseipp/vulture#readme). |
| Import Linter | Умеет проверять объявленные ограничения графа импортов. Для текущего ревью можно проследить изменённые импорты и вызывающих вручную. Даже корректный граф импортов сам по себе не подтверждает, что `matching` получает только простые данные или что принятие P3 происходит в нужном порядке. [Import Linter: контракты](https://import-linter.readthedocs.io/en/stable/). |

В действующем [правиле проекта](../CODING.md#читаемость-и-границы-модулей) есть отдельная оценка файла от 800 физических строк. Она локальная и относится к размеру, тогда как правила Ruff измеряют ветвление функций. Для ревью полезнее указать, какие правила смешаны, какой путь трудно проследить и какой вызов рискует измениться. Небольшие функции-переадресаторы и сокращение строк без упрощения сценария этих проблем не решают. Практический вывод исследования — использовать имеющиеся инструменты по конкретному риску, а изменение обязательного профиля рассматривать отдельно. [Философия Django](https://docs.djangoproject.com/en/5.2/misc/design-philosophies/#overall), [Ruff: C901](https://docs.astral.sh/ruff/rules/complex-structure/).
