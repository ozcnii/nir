**Статус: проект для обсуждения. Новые решения этого документа НЕ ПРИНЯТЫ. Код, миграции и конфигурации не создавались.**

Основание: принятая структура `INDEPENDENT-STRUCTURE.md` и требования НИР, разделы 5.1–5.5. Два приложения, направления зависимостей, отсутствие сети в каталоге и постоянного хранения файлов фотографий уже приняты. Конкретные таблицы, ограничения, поля и политики ниже — предложения автора, а не требования PostgreSQL или Django.

## 1. Сущности и ответственность

| Владелец | Сущность | Зачем нужна и что хранит |
|---|---|---|
| `catalog` | `Source` | Авито, Циан, Домклик: уникальный `code`, название, признак включения, разрешённые домены, параметры обращения к источнику. Способы получения страниц остаются в сборщике. |
| `catalog` | `Region` | Справочник регионов для одинаковой фильтрации разных источников: уникальный код и название. |
| `catalog` | `PropertyType` | Справочник типов: вторичная квартира, новостройка, комната, дом. Стабильный уникальный код и редактируемое название. |
| `catalog` | `Property` | Идентичность физического объекта: объединяет относящиеся к одной квартире/комнате/дому публикации; содержит ссылку на основную публикацию для общего описания. |
| `catalog` | `Publication` | Публикация конкретного источника: внешний ID, текущий URL, текущие нормализованные характеристики объекта, их происхождение и время последнего наблюдения. |
| `catalog` | `Offer` | Условия сделки конкретной публикации: продажа, месячная либо суточная аренда, текущая цена, валюта, залог, комиссия, минимальный срок. Продажа и аренда одной квартиры не объединяются. |
| `catalog` | `PriceChange` | Начальная известная цена и последующие изменения цены, включая переход к явно неизвестной цене, отдельно для каждого предложения. |
| `catalog` | `PublicationPhoto` | Текущий набор внешних URL фотографий, порядок, контрольная сумма байтов и перцептивный хеш с версией алгоритма; файлов нет. |
| `catalog` | `Acceptance` | Квитанция обработки сообщения: ключ доставки, контрольная сумма сообщения, итог и ссылки на созданные/найденные записи. Защищает от повторного применения старого сообщения. |
| `collection` | `Run` | Запуск сбора: UUID, начало, конец, состояние, запрос остановки и итоговые счётчики. Один запуск обходит выбранные источники. |
| `collection` | `Log` | Ошибки и ход запуска: ссылка на запуск, источник, время, уровень, код, URL/внешний ID при наличии, понятное сообщение. |

Все предметные первичные ключи предлагаются UUID. Справочники дополнительно имеют стабильные текстовые коды. Тип сделки — три фиксированных значения, а не отдельная таблица. Единицы площади и периода цены фиксирует контракт; таблицы для каждого атрибута не нужны. Пользователи и авторизация — штатные Django auth/admin, отдельной модели пользователя для этой задачи нет.

### Связи

```text
Source 1 ── N Publication N ── 1 Property
Region 1 ── N Publication
PropertyType 1 ── N Publication
Property 1 ── 0..1 основная Publication из собственных публикаций
Publication 1 ── 1..3 Offer              # по одному на тип сделки
Publication 1 ── 0..N PublicationPhoto
Offer 1 ── 0..N PriceChange
Source 1 ── N Acceptance
Run 1 ── N Log; Log N ── 0..1 Source
```

После успешного приёма у публикации ровно одно текущее предложение; остальные её предложения сохраняются как прежние типы сделки. У объекта есть основная публикация. Нулевое значение в кардинальности основной публикации нужно только для порядка вставок внутри атомарной транзакции. После фиксации транзакции оно недопустимо.

**Предложение об описании объекта.** Физические характеристики хранятся в публикациях, потому что источники могут противоречить друг другу. `Property` хранит объединяющую идентичность и основную публикацию; её поля дают общее описание объекта, используются в общей карточке и фильтрах. Это позволяет сохранить расхождения и происхождение без второй копии всех характеристик и таблиц значений каждого поля. В карточке источников видны собственные сведения каждой публикации. Отдельное объединение отдельных полей разных источников сейчас не предлагается.

**Предложение выбора основной публикации.** Первая успешно присоединённая публикация остаётся основной. Новая публикация из другого источника не перезаписывает общее описание. Новые успешно прочитанные поля основной публикации обновляют описание; ошибка чтения его не затирает. При недостатке данных сопоставление создаёт отдельный объект, а не очередь ручного разбора. Это консервативная политика; она может сохранить пропущенные дубли и ошибочные сведения основного источника. Порог и точные правила автоматического сопоставления — следующий отдельный пункт проектирования. Без номера квартиры одинаковый дом, площадь и этаж сами по себе не доказывают тождество квартир.

## 2. Поля и ограничения

### Publication: источник и характеристики

- Обязательные: `source_id`, `external_id`, `property_id`, `url`, `property_type_id`, `created_at`, `last_seen_at`, `last_applied_observed_at`.
- Характеристики, допускающие неизвестное значение: регион, нормализованный адрес и его компоненты (населённый пункт, улица, дом, корпус, квартира), широта/долгота, общая/жилая/кухонная площадь, площадь участка, комнаты, этаж, этажность. Для дома и комнаты заполняются только применимые поля. Квартира может отсутствовать в публичном адресе.
- Строки адреса — текст; площадь — десятичное число в м², участок также в м²; комнаты, этаж и этажность — целые числа; координаты — десятичные WGS84. Номер дома/квартиры — строки, чтобы сохранить `12А` и `3/1`. Значение `rooms=0` означает явно указанную студию; неизвестное число комнат — `null`.
- `field_provenance`: ограниченный JSON-объект только для перечисленных полей. Для каждого сохранённого значения: исходное значение/единица, время его успешного наблюдения, версия нормализатора и ключ сообщения. Это не произвольные дополнительные атрибуты и не копия HTML. Источник и внешний ID берутся из самой публикации.
- `field_issues`: текущие признаки `unavailable`/`invalid` для полей, которые последний раз не удалось прочитать, с кодом причины. Предыдущее успешное значение сохраняется; интерфейс/JSON различают последнее известное и подтверждённое текущим наблюдением значение.

Уникальность публикации: **`(source_id, external_id)`**. URL не является идентификатором: он может измениться и обновляется у той же публикации. Повторное использование внешнего ID самим источником — ограничение этой модели; автоматическую смену физического объекта без дополнительных признаков и правил не обещаем.

### Offer: условия и цена

- `publication_id`, `deal_type` из `sale | rent_month | rent_day`, `is_current`, время первого/последнего наблюдения данного типа сделки.
- `price_amount`: `numeric(18,2)`, положительное значение либо `null`; `currency`: трёхбуквенный код, например `RUB`. Нулём неизвестную цену не кодируем.
- `price_state`: `known | unknown`; `price_observed_at` — время последнего успешно прочитанного значения/явного отсутствия цены. Ошибка чтения не является переходом в `unknown`.
- Период цены однозначно задан типом сделки: вся продажа, один календарный месяц, одни сутки. Он не вводится второй независимой колонкой. Цена за м² в контракт основной цены не принимается: сборщик должен получить/вычислить общую цену при наличии достаточных исходных данных и записать происхождение вычисления.
- Дополнительные условия: залог в валюте цены, комиссия в процентах, минимальный срок в целых сутках. Они допускают неизвестное значение. Неизвестный залог отличается от подтверждённого нулевого. Происхождение и текущие ошибки условий фиксируются так же, как у полей публикации.
- Уникальность **`(publication_id, deal_type)`**; частичная уникальность по `publication_id WHERE is_current` обеспечивает не более одного текущего предложения. При смене типа сделки предыдущее выключается, соответствующее новому типу создаётся или снова становится текущим. При возврате к ранее встречавшемуся типу сохраняется его история цены.

**Граница истории:** текущие залог, комиссия и срок обновляются, но полная история этих условий и интервалов переключения типов сделки не хранится. Если для ВКР требуется восстанавливать все условия на любую дату, понадобится полная история наблюдений вместо предложенного ниже минимального варианта.

**Предложение атомарности денежных полей:** сумма цены, валюта и залог составляют одну группу обновления. Если хотя бы одно из трёх полей имеет `invalid`/`unavailable` или их сочетание противоречиво, сохраняется вся прежняя группа со своей прежней валютой и происхождением; вся группа отмечается не подтверждённой текущим наблюдением. Комиссия в процентах и срок могут обновиться независимо. Для новой записи вместо отсутствующей прежней группы сохраняются неизвестные денежные значения и предупреждение. Нового события цены при непринятой группе нет.

| Полученная группа | Результат |
|---|---|
| Сумма `value`, валюта `value`, залог `value` либо `unknown` | Все три значения принимаются одновременно; `unknown` залога очищает прежний залог, а не переносит его в новую валюту. |
| RUB → USD, сумма или залог `invalid`/`unavailable` | Сохраняется вся прежняя группа в RUB с отметкой ошибки; старые числа не становятся суммами в USD. |
| Валюта `invalid`/`unavailable`, сумма и залог успешно прочитаны | Новые числа не применяются; сохраняется вся прежняя группа. |
| Сумма `unknown`, валюта `value`, залог `value` либо `unknown` | Атомарно принимаются неизвестная цена, указанная валюта и новый залог/его неизвестность; переход цены к `unknown` отражается в истории. |
| Сумма, валюта и залог — `unknown` | Группа атомарно очищается до неизвестной; прежние деньги не сохраняются как текущие. |
| Валюта `unknown`, но сумма или залог — `value` | Группа противоречива и не принимается; предупреждение `money_currency_required`, сохранение прежней группы. |

Это уточнение группового применения имеет приоритет над общим правилом независимого обновления необязательных полей ниже.

### PriceChange: история цены

`offer_id`, `observed_at`, `message_id`, прежние и новые `(price_state, amount, currency)`. Для первой известной цены прежнее состояние отсутствует; при первом неизвестном значении события нет. Когда значение впервые становится известным, создаётся начальное событие. Известная цена → явно неизвестная → известная — три разных состояния, два перехода после начальной записи.

Ключ сравнения цены — **`(offer_id, price_state, amount, currency)`**; период уже задан `Offer.deal_type`. Время само по себе не создаёт изменение. Уникальность **`(offer_id, message_id)`** дополнительно запрещает повтор события одного сообщения. Цена сравнивается в десятичной арифметике; `100000` и `100000.00` одинаковы. Смена валюты — изменение; конвертация и сравнение разных валют по числу без валюты не выполняются. Фильтр цены задаёт валюту, без автоматического курса.

**Предложение сохранности истории:** `PriceChange` — неизменяемые события: после вставки запрещены `UPDATE` и `DELETE`, в том числе через админку, сервисы и массовые операции ORM. При реализации запрет должен обеспечиваться и правами рабочего пользователя БД, а не только скрытием кнопок. Связи `PriceChange → Offer`, `Offer → Publication`, `Publication → Source` защищают связанные записи от удаления (`PROTECT` в Django и запрет каскадного удаления в БД). Источник выключается, публикация архивируется, предложение становится нетекущим; административное удаление цепочки с историей не допускается. Архивация публикации — отдельный служебный признак, а не автоматический вывод о снятии объявления с рынка.

### PublicationPhoto: признаки фотографий

`publication_id`, внешний `url`, позиция, `content_sha256`, `perceptual_hash`, `hash_algorithm_version`, время вычисления, исходный URL и код последней ошибки обработки. Уникальность `(publication_id, position)`; один URL внутри набора не повторяется. Хеши допускают `null`, если фотографию загрузить нельзя. Одинаковый URL при новом содержимом получает новые хеши; смена URL при одинаковом содержимом не создаёт новый объект. Новая версия алгоритма не сравнивается с несовместимой старой версией.

Набор заменяется только при полном успешном извлечении списка URL, включая явно пустой список. При ошибке извлечения списка сохраняется прежний набор с признаком неактуальности. В полном новом списке отдельная ошибка загрузки фотографии не отменяет карточку: для её URL сохраняются отсутствие новых хешей и причина. Старый хеш того же URL не выдаётся за проверенный новый. Для сопоставления используются только пригодные признаки, без обращения к URL из каталога.

### Run, Log и Acceptance

`Run`: UUID, состояния `running | completed | failed | stopped | interrupted`, времена, `stop_requested`, счётчики обработанных/отклонённых карточек. Блокировка одного процесса в PostgreSQL уже принята структурой; отдельные очередь, брокер и таблица блокировок здесь не предлагаются. `Log` хранит эксплуатационную диагностику, а не снимки всех объявлений.

`Acceptance`: уникальный `message_id`, `source_id`, `external_id`, `observed_at`, `received_at`, `run_id` как UUID для корреляции без внешнего ключа в `collection`, контрольная сумма полного содержимого сообщения и неизменяемый `response` — ограниченный JSON-снимок полного минимального ответа. Он содержит `message_id`, исходный `replayed=false`, `status`, `publication_id`, `property_id`, `offer_id`, `price_changed`, `warnings[]` и `errors[]` с путями полей/кодами; отсутствующие ID записываются как `null`, отсутствующие предупреждения/ошибки — как пустые массивы. ID в снимке — сохранённые значения ответа, а не результат повторной выборки текущих моделей. Исходное объявление целиком не сохраняется. История эксплуатации `Log` не заменяет эту квитанцию: журнал может иметь несколько строк на карточку и не обеспечивает атомарную уникальность применения сообщения.

Квитанции предлагается сохранять без автоматического удаления в рамках ВКР. Иначе гарантия повтора ограничивается сроком хранения квитанций. Поиск по `message_id` выполняется до применения данных; запись результата и предметные изменения фиксируются одной транзакцией. Отказ соединения до фиксации позволяет повторить сообщение, после фиксации — получить сохранённый результат.

Помимо уникальностей нужны проверки положительности площадей/цены, допустимого диапазона координат, согласованности пары координат и состояния цены; при известных значениях `floor <= floors_total`. Необычные/ошибочные поля отклоняются как поля, а не превращаются молча в другое значение. Проверка принадлежности основной публикации своему объекту и обязательности одного текущего предложения выполняется сервисом приёма в транзакции. Фильтры используют индексы по полям реального поиска, в первую очередь типу объекта/региону и текущей цене/типу сделки; точный набор составных индексов определяется запросами и объёмом, а не объявляется проверенным проектом заранее.

## 3. Контракт collection → catalog

Это вызов функции сервиса внутри монолита, не новый HTTP-сервис. JSON ниже показывает переносимую форму данных. `collection` извлекает и нормализует; `catalog` проверяет типы, обязательность, коды справочников, единицы и ограничения. Каталог не распознаёт адрес из сырой строки, не пересчитывает сотки/валюты и не загружает фотографии.

**Предлагаемая версия контракта — `1`, ещё не принята.** Неизвестная версия отклоняется целиком. `normalizer_version` указывает версию преобразования, `hash_algorithm_version` — версию сопоставимых фото-признаков; это разные версии с разным назначением.

| Поле | Тип и обязательность |
|---|---|
| `schema_version` | Целое, обязательно; пока поддерживается только предложенное `1`. |
| `message_id` | UUID, обязательно; создаётся один раз на полученное наблюдение и сохраняется при повторе доставки. |
| `run_id` | UUID запуска, обязательно, только для корреляции. |
| `source_code`, `external_id` | Непустые строки, обязательно; существующий включённый источник и стабильный ID карточки. |
| `observed_at` | ISO 8601 с часовым поясом, обязательно; момент получения карточки, не время повторной доставки. |
| `normalizer_version` | Непустая строка, обязательно. |
| `url` | Абсолютный HTTP(S) URL разрешённого домена, обязательно. |
| `property_type`, `deal_type` | Известные стабильные коды, обязательно; без них карточка не принимается. |
| `facts` | Объект с перечисленными в разделе 2 физическими полями, обязательно. Каждый ключ имеет состояние; произвольные дополнительные поля запрещены. |
| `terms` | Объект с ценой, валютой и дополнительными условиями; цена и валюта представлены явно, даже если неизвестны. |
| `photos` | Состояние списка и массив URL/хешей; обязательно, но допустима ошибка списка или отдельных файлов. |

Для каждого необязательного факта/условия передаётся одно из состояний:

- `value`: нормализованное `value` требуемого типа и `raw` с исходным значением/единицей; успешно наблюдаемое значение заменяет прежнее.
- `unknown`: источник явно не сообщает значение либо оно неприменимо; `reason=not_specified | not_applicable`. Принимаемое значение становится `null`; это не ошибка. Для цены это подтверждённое состояние `unknown`.
- `unavailable`: поле не удалось получить из-за частичного отказа карточки; обязателен `error_code`, сохранённое значение не стирается.
- `invalid`: исходное значение извлечено, но не нормализуется/не проходит ограничения; обязательны `raw` и `error_code`, сохранённое значение не стирается.

`raw` — исходная строка либо небольшой объект исходных операндов вычисления, не HTML и не универсальные дополнительные сведения. У успешно полученного адреса сохраняется исходная строка адреса; у вычисленной общей цены — исходная цена за м² и площадь. Десятичные значения в JSON передаются строками, чтобы избежать двоичного округления. Даты приводятся к UTC без изменения самого момента наблюдения. Неизвестная валюта допустима только при неизвестной/недоступной цене; известная цена без известной валюты не принимается как новое значение цены.

### Один пример сообщения

Ниже компактно показан смысл формы; остальные перечисленные физические поля и дополнительные условия должны быть явно переданы со своим состоянием. Это не готовый JSON для вызова, потому что пропущенные поля отмечены текстом.

```json
{
  "schema_version": 1,
  "message_id": "626fc3e1-371b-4299-befe-59189f43d14b",
  "run_id": "1bb889fc-43dc-4545-bd87-0a46ab31e9ba",
  "source_code": "cian",
  "external_id": "123456789",
  "observed_at": "2026-11-16T10:00:00Z",

  "deal_type": "sale",

    "address": {"state": "value", "value": "Самара, улица Примерная, дом 10", "raw": "г. Самара, Примерная ул., 10"},
    "total_area_m2": {"state": "value", "value": "42.50", "raw": "42,5 м²"},

```

Адрес, URL и цена в примере вымышлены; это пример контракта, не результат сбора. Для полного сообщения отсутствующие компоненты адреса, координаты, площади и условия передаются как `unknown`/`unavailable`, а не угадываются. Форма фотографии в непустом массиве: `position` (целое), `url` (строка), `processing_state=hashed|unavailable|invalid`, `content_sha256` (64 шестнадцатеричных символа при успехе), `perceptual_hash` (строка формата выбранного алгоритма), `hash_algorithm_version`, `error_code` при ошибке. Фото-признаки не являются обязательным условием принятия карточки.

### Результат приёма и частичный отказ

Результат содержит `message_id`, `replayed`, `status`, `publication_id`, `property_id`, `offer_id`, `price_changed`, `warnings[]`; при отказе — `errors[]` с путями полей и кодами. Предлагаемые статусы:

- `created`: новая публикация, сопоставленная существующему либо новому объекту;
- `updated`: изменились принятые текущие поля, условия или фотографии;
- `unchanged`: новое успешное наблюдение с прежними предметными значениями; обновлены времена наблюдения, нового события цены нет;
- `stale`: сообщение старее последнего применённого наблюдения этой публикации; предметные данные не изменены;
- `rejected`: неверна версия/идентичность/обязательный тип либо сообщение структурно непригодно.

`replayed=true` означает повтор доставки: из неизменяемого `Acceptance.response` возвращаются прежние статус, ID, `price_changed`, предупреждения и ошибки; только признак `replayed` в возвращаемой копии становится `true`. Ответ не восстанавливается из текущих предметных моделей, и сохранённый снимок не изменяется. Повтор `message_id` с иным содержимым возвращает ошибку `message_id_payload_conflict` и не меняет существующую квитанцию. Сбой БД/транзакции — временная ошибка вызова, а не `rejected` и не успешная квитанция; сборщик может повторить исходное сообщение.

Ошибки дополнительных полей дают предупреждения и сохраняют пригодную часть. Если сведения слишком бедны для сопоставления, создаётся самостоятельный объект. Если отсутствуют внешний ID, тип объекта или тип сделки, отклоняется вся карточка; при отсутствии даже идентичности сообщения ошибка остаётся в `collection.Log`, поскольку надёжной квитанции приёма создать нельзя. HTTP-отказ карточки до извлечения данных также журналируется сборщиком и не превращается в неизвестную цену, пустой набор фото или снятие публикации.

## 4. Наблюдение, доставка и последовательность

1. Сборщик один раз получает карточку, назначает `message_id` и `observed_at`, выполняет нормализацию и фото-обработку. Повтор вызова после технического сбоя использует то же сообщение. Новое получение карточки, даже с прежними значениями, получает новый `message_id`.
2. Каталог ищет квитанцию. Найденная квитанция с той же контрольной суммой возвращается без повторного применения. С иной суммой — конфликт ключа.
3. После проверки обязательных полей каталог в транзакции блокирует существующую публикацию, проверяет порядок времени, принимает пригодные значения и сохраняет результат. Одновременное создание одной публикации дополнительно защищено уникальным ключом источника и внешнего ID.
4. Более старое наблюдение получает `stale`. Равное время разных сообщений с отличающимся содержимым получает `rejected` с кодом `observation_time_conflict`; одинаковое содержание при равном времени — `unchanged`. Время получения задаёт сборщик, а не источник; он должен выдавать строго возрастающие времена новых наблюдений одной публикации. Внешняя дата обновления страницы не подменяет это время.
5. Неизменные поля не создают `PriceChange`. Времена успешно прочитанных полей обновляются, признаки ошибок обновляются отдельно. После коммита возвращается квитанция; `collection` записывает эксплуатационный итог в свой журнал.

`Acceptance` — минимальный постоянный журнал **применения сообщений**, а не полная история наблюдавшихся данных: он доказывает, что сообщение уже обработано, и позволяет вернуть тот же результат. Он не позволяет восстановить старые площади, адрес, URL, фотографии или условия.

## 5. Какую историю предлагается хранить

| Вариант | Что можно восстановить | Цена сложности |
|---|---|---|
| Полная история наблюдений | Все значения, их ошибки и происхождение при каждом получении карточки; можно повторно рассчитать прошлое сопоставление | Нужны неизменяемые снимки объявления/фото-признаков, правила выбора текущего состояния, объём растёт при каждом обходе |
| Текущее состояние + история изменений цены + квитанции | Текущее последнее известное описание, текущее происхождение/ошибки, последовательность реально менявшейся цены и факт обработки сообщений | Нельзя восстановить старое описание, все прежние условия и фото; старую карточку после изменения удалённого URL показать достоверно нельзя |

**Предложение: второй вариант.** Он соответствует прямо названной в НИР истории изменения цены и принятой структуре, не создаёт снимки на каждом повторе. Термин «история» в интерфейсе и тексте работы должен означать именно историю цены. Переключение типа сделки видно по сохранённым предложениям, но полная временная история условий не заявляется. Если требуется полная воспроизводимость каждого наблюдения, это отдельное расширение требований, а не свойство текущего предложения.

## 6. Проверка сценариев на проекте

Это мысленная проверка правил, не испытание реализации.

| Сценарий | Предлагаемый результат |
|---|---|
| Первый проход | Одна публикация по ключу источника/ID; один объект при отсутствии уверенного совпадения; одно текущее предложение; начальная запись известной цены; фото-признаки и квитанция. |
| Новый обход, всё прежнее | Новый UUID наблюдения и квитанция, прежние предметные ID, свежие времена; история цены не растёт. |
| Повтор доставки того же сообщения | Прежняя квитанция с `replayed=true`; времена/цены/связи не меняются. Повтор старой доставки после более нового сообщения также не откатывает данные. |
| Другое новое, но запоздавшее наблюдение | `stale`, без отката текущего состояния и без вставки события цены в прошлое. |
| Цена изменилась | Обновление цены того же предложения и одна запись перехода; обычный повтор его не дублирует. |
| Изменились залог/комиссия/минимальный срок | Обновление текущих условий и происхождения, без фиктивного изменения цены; прошлые условия полностью не восстанавливаются. |
| Продажа стала месячной арендой | Продажа остаётся отдельным нетекущим предложением с прежней историей; аренда имеет свою цену и историю, сравнения их сумм нет. Возврат продажи снова активирует её предложение. |
| URL изменился, внешний ID прежний | Та же публикация; обновление URL без новой публикации/объекта. Прежний URL полностью не архивируется. |
| URL фото прежний, байты другие | По результатам новой загрузки заменяются checksum/хеш; совпадение старого URL не считается совпадением фотографии. |
| Фото недоступно / список недоступен | Для отдельного файла — текущий URL без пригодного нового хеша; для не полученного списка — прежний набор с отметкой неактуальности. Карточка принимается, каталог не идёт в сеть. |
| Цена явно неизвестна | Новая карточка принимается с `unknown`; при переходе от известной цены создаётся событие. Неизвестная цена не равна нулю. |
| Цена не распарсилась | Предыдущая известная цена сохраняется как последнее известное значение с ошибкой актуальности; нового события цены нет. В стандартный ценовой фильтр такие устаревшие значения не входят. |
| Квартира в двух источниках | Две публикации и два предложения со своими ценами/происхождением; при уверенном совпадении один `Property`, иначе два. |
| Квартира продаётся и сдаётся | Один `Property` при уверенном совпадении, отдельные публикации/предложения; условия и истории цен не смешиваются. |
| Источники противоречат по площади/этажу | Каждая публикация сохраняет своё значение; основное описание не перезаписывается вторым источником. Неубедительное совпадение не объединяется автоматически. |
| Полный отказ карточки / остановка запуска | Диагностика в `Log`; старые данные не удаляются и не объявляются неактивными. Уже принятые карточки сохранены атомарно; повторный запуск проходит их без дублей. |

Снятие объявлений с публикации не выводится из единичного пропуска или HTTP-ошибки. Автоматическая политика определения снятых объявлений в НИР не описана и этим проектом не вводится. Состояние «текущее предложение» означает последнее успешно наблюдавшееся условие данной публикации, а не подтверждённое наличие объекта на рынке в данный момент.

## 7. Конкретные новые выборы для согласования

1. Описанные одиннадцать сущностей; `Property` как общая идентичность с основной публикацией, физические поля и происхождение — у публикаций.
2. Стабильная первая основная публикация; конфликты не разрешаются смешиванием значений; неуверенное совпадение создаёт самостоятельный объект без ручной очереди.
3. Один `Offer` на пару публикация/тип сделки и ровно один текущий; история цены привязана к этому предложению.
4. Текущее состояние и история только изменений цены, без полных снимков наблюдений и прошлых условий/фото.
5. Постоянная квитанция `Acceptance`, UUID сообщения, проверка содержимого повтора, порядок наблюдений и атомарность применения.
6. Предложенная версия контракта `1`, явные состояния необязательных полей и раздельные версии нормализатора/фото-алгоритма.
7. Перечисленные единицы, десятичные денежные значения, валюта без конвертации, `unknown` для цены и исключение устаревшей цены из обычного ценового фильтра.
8. Текущий набор URL фотографий с checksum и версионированным перцептивным хешем; ошибки списка и отдельного файла различаются.

Ни один из этих восьми пунктов не считается принятым из-за появления этого файла. Реализация и точные правила сопоставления остаются за пределами данного проекта.
