## 2. Сборка и доступ к файлам

- Системные библиотеки и ровно Chromium выбранной версии Playwright устанавливаются при будущей сборке под root; runtime никаких apt/download/install не делает. Используется штатный install Chromium с dependencies и без headless shell, поскольку выбран channel=chromium.
- Общий фиксированный browser path /ms-playwright задаётся одинаково при install и runtime; бинарники/библиотеки доступны app на чтение/исполнение. Кэш root в /root/.cache не выдаётся за доступный nonroot путь. Browser directory и код не требуют world-writable прав.
- /home/app и временные каталоги доступны app для записи; временный профиль браузера создаётся отдельно на запуск. Нет persistent user-data-dir, подключения пользовательского профиля/Downloads, host.venv или macOS-браузера. Постоянное хранение фотографий/хешей не возвращается.
- Принятый volume db сохраняется. Не добавляется постоянный browser volume. Место журнала/служебного состояния не выбирается этим документом и будет согласовано отдельно; произвольная очистка общих каталогов/томов не разрешается.
- Официальный seccomp-профиль берётся из проверенного первичного артефакта и фиксируется с исходным commit/hash при реализации; не копируется только короткий фрагмент allow-list вместо полного default-based профиля. Это готовый полный официальный профиль, не самостоятельно синтезированное дополнение к текущему Engine default; совпадение с default Engine29.9.3 не обещается. Точная версия использованного файла будет записана в первичные доказательства при реализации. Наличие файла ещё не доказывает работоспособность Linux user namespaces в фактической Docker VM.

## 3. Работа и остановка

Сохраняется4.3: собственный браузер на один последовательный run; список выдачи и переиспользуемая страница карточки, ресурсы закрываются в finally только владельцем. Браузер создаётся по запросу сбора и закрывается после run; startup web не запускает сбор. Явное завершение/фатальная ошибка браузера завершает текущий run с причиной, ранее committed данные остаются; повторный старт отдельный.

При запуске сбора browser-init/ошибка sandbox не приводит к root или chromium_sandbox=false. Это ошибка запуска сбора с причиной; web-каталог может оставаться доступным. Выбранный порт8000 не влияет на правила URLконтекста5.5. Использованиеhost-прокси не включается автоматически: существующие параметры источников/явная локальная конфигурация не меняются.

init:true — только элемент управления процессами. Конкретная аренда ресурсов задач, PID+birth/ownership, shutdown-последовательность runner/web, точный grace period, перезапуск и журнал остаются отдельной согласуемой частью9.6. Не обещать завершение всего дерева от одного init, не объявлять новый heartbeat/runner реализованным. Нельзя останавливать чужие контейнеры/весьDocker; пользовательский браузер не затрагивается.

## 4. Что проверить после разрешения реализации

До запуска этих проверок требуется отдельное разрешение писать/собирать приложение; сейчас проверены только проект и первичные источники.

1. Через опубликованный127.0.0.1:8000 открываются каталог/admin/JSON; из app подключениеdb:5432 успешно, db не имеет host PortBindings. При занятом8000 Docker назначает свободный loopbackhost-порт, фактический адрес показан оператору; чужой процесс не изменён, APP_PORT меняет только host-адрес.
2. web/runner/Chromium действительно неroot, UID/GID10001, HOME/temp/browser paths доступны без777. Одноразовая миграция от migrator не оставляет ownercredentials в web. Не подменять роли БД Linux-пользователем.
3. В собранной Linuxarm64 средеMac и Linuxamd64 при используемой машине запускается именно bundled полный Chromium выбранной версии с sandboxtrue, без --no-sandbox; подтвердить фактические namespace/seccomp/sandbox состояния браузера, а не только переданный bool. Отрицательный сценарий ошибки sandbox не вызывает небезопасный fallback. Проверка браузера конкретного сайта отдельно от проверки локального запуска.
4. Один run проходит контролируемую выдачу/карточку; browser crash и обычная остановка освобождают только его ресурсы. После реализации будущего shutdown-механизма отдельно проверить SIGTERM и отсутствие оставленных процессов. init/config сами по себе не доказательство.
5. На принятом последовательном проходе измерить RAM/peak и свободное место/tmp, а не назначать выдуманные обязательные CPU/RAM-квоты. Если штатнойtmp-стратегии недостаточно — отдельно согласовать измеренное изменение. Не добавлять shm_size как якобы работающий фикс без учёта --disable-dev-shm-usage.

Нет runtime-результатов: Docker Desktop/хост не обновлялись, образ не собирался, сайт/Chromium в этом профиле не запускались. Это не пересмотр8.4CI и не новый постоянный сервис. Источники и точные границы: [CONTAINER-RUNTIME-PRIMARY-SOURCES](evidence/CONTAINER-RUNTIME-PRIMARY-SOURCES.md).

## Принятие и уточнение владельца

18 ноября 2026 владелец принял порты, OS-пользователя и браузер, отдельно попросил автоматически подбирать свободный порт при занятом локальном. Поэтому прежний отказ на занятый8000 заменён: сначала использовать8000, а при подтверждённом конфликте hostbinding — Docker-назначение свободного loopbackпорта и чтение фактического mapping. Не искать порт через bind/close с гонкой, не повторять после произвольной ошибки app. При переиспользовании уже работающего проектного стека сохраняется его адрес/порт, без пересоздания ради8000. Ошибка выделения/неоднозначная ошибка запуска сообщается как ошибка, не запускает бесконечный перебор. Это пользовательское уточнение принятого проекта; код и Dockerпрофиль ещё не реализованы.
