# Предложение структуры модульного монолита

**Статус: структура принята пользователем 16 ноября 2026, решение A10. Пункт 1 закрыт. Реализация не разрешена; следующие пункты проектирования согласуются отдельно.**

Принятая структура: два Django-приложения внутри одного проекта Python/Django/PostgreSQL. Граница проходит между получением внешних данных и каталогом недвижимости, а не между пятью функциями НИР.

Дерево ниже относится к папке [implementation/](../implementation/README.md).

```text
manage.py
config/                         # настройки и корневые URL
catalog/
  models.py                     # предметные данные
  services.py                   # принятие объявления и запись результата
  matching.py                   # сопоставление структурных признаков и текста, без сети
  queries.py                    # общие выборки HTML и JSON
  views.py, urls.py, admin.py
  templates/catalog/
  migrations/, tests/
collection/
  runner.py                     # последовательный обход источников
  normalization.py              # единицы измерения, адреса, значения полей
  collectors/
    avito.py
    cian.py
    domclick.py
  management/commands/collect.py
  admin.py
  migrations/, tests/
```

**Данные и ответственность.** `catalog` владеет физическими объектами, публикациями источников, предложениями сделки, историей цен, URL фотографий, источниками и справочниками. Источник здесь — запись единого каталога; способы обращения к нему находятся в `collection`. Сопоставление объекта не означает объединение всех его предложений: продажа и аренда, разные условия сохраняются отдельно. `collection` владеет состоянием процесса запуска и файловым/служебным журналом; это не ORM-таблицы. Отдельный collection.models для них отменён принятым пунктом 2/5.4; наличие apps не означает обязательность models.py или миграций без моделей.

**Взаимодействие.** `collection` получает параметры источников простыми данными через публичную функцию `catalog.queries` и передаёт P3 функции приёма из `catalog.services`, согласно принятому 8.3. Прямых предметных ORM-запросов и ORM-моделей на этой границе нет; техническая PostgreSQL-блокировка runner сохраняется. Она принимает нормализованные данные и URL фото, вызывает `matching`, сохраняет результат. `catalog` не импортирует `collection`; сборщики не обращаются к моделям каталога напрямую. `queries.py` реализует фильтры по типу сделки и объекта, региону, цене, площади, комнатам и этажу; `views.py` и шаблоны — каталог и карточку с источниками и историей цен. JSON использует те же выборки.

**Путь объявления.** Сборщик получает страницу через HTTP или браузер, извлекает поля и ссылки. Затем выполняются нормализация полей и списка URL фотографий. Каталог находит публикацию по паре «источник, внешний идентификатор», автоматически сопоставляет объект по структурным признакам и текстам, связывает предложение и сохраняет изменение цены. Файлы фотографий не сохраняются; интерфейс показывает внешние ссылки.

**Запуск и восстановление.** Админка запускает management command отдельным процессом того же приложения; остановка записывает запрос, проверяемый между объявлениями. Одновременно работает один сбор с блокировкой PostgreSQL, освобождаемой при завершении процесса. Сетевая обработка предшествует транзакции; запись одного объявления атомарна. После прерывания повторный обход обновляет существующую публикацию благодаря уникальному ключу и не добавляет историю при неизменной цене.

**Администрирование и проверка схемы.** Авторизация администратора — штатные Django auth/admin. `catalog.admin` управляет источниками, их параметрами из `catalog.models` и справочниками; `collection.admin` — запуском, остановкой и журналом. Предметные записи доступны без ручного исправления связей. Мысленно прослежены новое объявление, повтор, изменение цены, второй источник и прерывание; это проверка предложения, не испытание реализации. Пороги сопоставления остаются отдельным решением.
